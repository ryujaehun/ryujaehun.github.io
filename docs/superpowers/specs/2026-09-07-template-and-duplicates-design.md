# 제목 중복과 URL 충돌 정리

- 날짜: 2026-09-07
- 상태: 구현 완료 (블로그 `9788868`, `6a677dc`, `ba6998e` / `blog-automation` `4261279`)
- 범위: 서브프로젝트 5

## 처음 생각한 것보다 컸다

"템플릿 일원화 + 기존 중복 25쌍" 으로 시작했는데, 조사해 보니 **25편이
사이트에 존재하지 않고 있었다.**

`hugo.yaml` 의 `permalinks: posts: /posts/:slug/` 이고 slug 는 제목에서
나온다. 같은 논문을 두 번 리뷰한 글들이 제목이 같아 permalink 가 겹쳤고,
Hugo 는 **경고 없이** 한쪽만 렌더했다. `hugo list all` 로 확인한 결과
충돌 25건 / 관련 글 50편이었다.

정리 작업이 아니라 손실 복구였다.

## 왜 permalink 를 안 바꿨나

충돌 자체를 없애려면 `permalinks` 를 파일명 기반(`/posts/:filename/`)으로
바꾸면 된다. 하지만 **기존 500개 URL 이 전부 바뀐다.** 외부 링크와 검색
색인이 다 깨진다. 고칠 곳은 콘텐츠 쪽이다.

## 중복 22편 삭제 — 기준을 한 번 바꿨다

처음엔 "최신본이 더 철저하다" 고 가정하고 오래된 쪽을 지우려 했다.
확인해 보니 틀렸다.

- 18쌍 **전부 같은 모델**(`with-gpt`)로 쓰였다. 모델이 좋아진 게 아니다.
- **11쌍에서 오래된 쪽이 더 컸다.** 생성 날짜는 품질 지표가 아니고,
  크기 차이는 생성 편차였다.

그래서 기준을 바꿨다.

| 우선순위 | 기준 | 근거 |
|---|---|---|
| 1 | 새 arXiv 버전을 다룬 쪽 | v1 vs v2 인 4쌍. 새 버전 리뷰가 맞다 |
| 2 | 파일명에 arXiv ID 가 있는 쪽 | `paper-Discard.md` 같은 이름은 `reviewed_ids` 가 파일명 정규식으로 잡지 못한다. 중복 검사가 본문 링크에만 의존하게 된다 |
| 3 | 분량이 많은 쪽 | 같은 모델·같은 버전이면 더 철저한 쪽 |

`2505.09343` 은 이 기준으로 `gemini-2.5-pro` 로 쓴 110KB 리뷰가 살아남고
`gpt` 로 쓴 52KB 가 지워졌다. 날짜 기준이었다면 반대였다.

### 삭제해도 잃지 않는 것

- **URL**: 삭제한 22편의 URL 은 하나도 사라지지 않는다. 겹쳐 있던 것이라
  남긴 쪽이 같은 URL 을 쓴다. 확인했다.
- **중복 검사**: 삭제된 논문 ID 18개가 전부 `reviewed_ids` 에 그대로
  잡힌다(376개). 파이프라인이 그 논문을 다시 리뷰하지 않는다.
- **내용**: git 히스토리에 남는다.

## 제목이 잘못 붙은 글

충돌 25건 중 7건은 중복이 아니라 다른 문제였다.

| 파일 | 문제 | 처리 |
|---|---|---|
| `2021-2-11-virtualenv.md` | 제목이 `elementry-os` 글의 것 | **고쳤다** — 본문이 명백히 virtualenv 가이드다 |
| `2024-11-03-paper-HardDiskDrive.md` | 링크는 HDD 고장 분석 논문인데 본문 답변은 reasoning 논문 내용 | **남겼다** — 본문이 섞여 있어 제목 교체로 안 된다 |
| `2025-03-10-paper-2502.16949.md` | 제목이 Comet 인데 `2502.19811v3` 도 Comet | **남겼다** — 어느 링크가 맞는지 작성자만 안다 |
| 나머지 4건 | 같은 논문, 파일명만 다름 | 중복으로 처리 |

남은 충돌 2건은 그래서 남아 있다. 그 2편은 아직 사이트에서 안 보인다.

## h1 중복

테마가 front matter 의 `title` 로 h1 을 만드는데 본문도 `# ...` 으로
시작해서 h1 이 둘 생기고 있었다. 그리고 **둘의 내용이 다르다.**

```
<h1> Hardware-Aware FP4 FlashAttention-4          ← arXiv 원제
<h1> Direct-P: FP4 어텐션의 진짜 병목은 …          ← 모델의 편집 헤드라인
```

편집 헤드라인이 arXiv 원제보다 읽기 좋은 경우가 많아서 **지우지 않고
레벨만 내렸다**(H1 → H2). 제목을 편집 헤드라인으로 바꾸는 안도 있었지만
URL 이 한국어 슬러그로 바뀌고 이미 게시된 글의 링크가 깨진다.

### 범위를 좁힌 이유

본문에 H1 이 있는 글은 441편이지만, 성격이 다르다.

| 유형 | 편수 | 처리 |
|---|---|---|
| H1 1개 · 맨 앞 = 제목 중복 | **56편** | 고쳤다 |
| H1 여러 개 · 섹션 제목으로 사용 (`# Q :` / `# Answer`) | 373편 | **남겼다** |
| H1 없음 / 중간 | 108편 | 해당 없음 |

373편은 문서 전체의 헤딩 레벨을 한 단씩 내려야 하는 별개의
마이그레이션이다. H1 만 H2 로 바꾸면 기존 H2 와 같은 레벨이 되어 구조가
뒤틀린다.

### 파이프라인 쪽

`render.demote_leading_h1()` 이 초안을 쓸 때 맨 앞 H1 하나만 H2 로
내린다. 프롬프트로 "H1 을 쓰지 마라" 고 지시하는 대신 코드에서
정규화했다 — 프롬프트가 지켜지길 기대하는 것보다 확실하다. 번역 경로에도
같이 적용했다.

맨 앞의 것 하나만 건드린다. 본문 중간의 H1 은 섹션 제목일 수 있다.

## 검증

- `hugo list all`: 충돌 25건 → **2건** (남긴 2건은 위 표의 판단 보류분)
- 한국어 글 502편 / 고유 URL 500개
- 렌더된 파이프라인 글의 `<h1>`: 2개 → **1개**, 편집 헤드라인은 H2 로 유지
- `reviewed_ids` 376개 — 삭제된 ID 18개 전부 유지
- `hugo --gc --minify` KO 960 / EN 196
- `blog-automation` 테스트 135 → 143

## 남은 것

- 충돌 2건 (작성자 판단 필요)
- H1 을 섹션 제목으로 쓰는 373편의 헤딩 레벨 마이그레이션
- URL 이 겹치지는 않지만 같은 논문을 두 번 다룬 쌍이 몇 개 더 있다
  (`2411.19379`, `2405.21060` 등 — 제목이 달라 충돌하지 않았다)
- `archetypes/posts.md` 와 `create_post.front_matter()` 의 필드 통일은
  손대지 않았다. `archetypes` 는 `hugo new` 로 손으로 글을 쓸 때만 쓰이고
  파이프라인과 경로가 겹치지 않아 급하지 않다.
