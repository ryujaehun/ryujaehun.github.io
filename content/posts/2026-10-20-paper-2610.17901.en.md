Training on long documents across several GPUs creates more than a compute problem. Each GPU also needs the right **attention mask**: the rules that determine which tokens may attend to which other tokens. If those rules leave one GPU with more work than the others, the entire training step waits for it.

FlashMask-3 starts with how masks are stored, then uses that representation to select work, distribute it, and overlap communication with computation. The paper reports a **7.3–11.0%** improvement in full training throughput for a MoE model with a 128K context on 128 H100 GPUs. That result must be distinguished from the speedup of the attention kernel alone (§4.3, Table 1).

## Splitting a long sequence also creates a mask problem

Attention computes how much information each token takes from other tokens. A mask rules out relationships that are not allowed. For example, when several documents are packed into one input, tokens from different documents can be prevented from attending to each other. Sliding-window attention, which only allows nearby tokens, is another example.

Representing a mask as a large table becomes expensive. With $n$ tokens there are $n^2$ token pairs, so storing and processing the mask grows costly as the input gets longer. The earlier FlashMask reduces storage to $O(n)$ by representing structured masks with interval boundaries (§2.2).

Using several GPUs adds another challenge. **Context Parallelism (CP)** distributes attention work for a long sequence across GPUs. Each GPU needs a mask for its assigned tokens, and equal token counts do not imply equal amounts of computation. Simply splitting the sequence into equally sized pieces does not guarantee balanced work (§2.3).

FlashMask-3 connects these two problems. It aims to use compressed masks efficiently inside a GPU kernel while preventing mask processing and communication from becoming bottlenecks when work is distributed across GPUs.

## Store boundaries instead of a large table

In an attention matrix, rows correspond to **queries**, the tokens requesting information, and columns to **keys**, the tokens being attended to. FlashMask stores the query intervals that are masked out for each key. For masks that fit this representation, each key requires at most two masked intervals, or four boundary values (§2.2).

A small example shows why this helps construct per-GPU masks. This is an **illustrative example**, not a measurement from the paper.

Suppose eight tokens are split across two GPUs, and the masked query interval for one key is $[6,8)$ in global coordinates. GPU A handles queries 0–3, while GPU B handles queries 4–7.

| GPU | Assigned global query interval | Overlap with masked interval | GPU-local coordinates |
|---|---|---|---|
| A | $[0,4)$ | None | Empty interval |
| B | $[4,8)$ | $[6,8)$ | $[2,4)$ |

GPU B only needs to subtract its starting offset, 4. GPU A clips the out-of-range boundaries to the end of its range, obtaining an empty interval. If both already know the global boundaries and their own assignments, they need no communication to perform this conversion.

The paper extends this idea to cases where one GPU owns several noncontiguous chunks. It clips boundaries to the assigned chunks, shifts them into local coordinates, and merges them with a maximum operation. Theorem 1 establishes that this conversion preserves the original masking relationships (§3.2, Appendix C.1).

Here, **zero communication refers only to converting mask boundaries into local coordinates.** GPUs still need to exchange key and value data for attention computation.

## Reuse the boundaries to choose and distribute work

Compact mask storage alone does not make a GPU fast. FlashMask-3 uses the same boundaries to skip unnecessary work and distribute the remaining work more evenly.

### Filter blocks before computing them

The GPU kernel processes the attention matrix in small blocks. If an entire block is masked, it needs neither a data load nor a matrix multiplication. A partially masked block still needs computation with masking applied.

FlashMask-3’s **KV Index Generator** identifies these cases and produces a list of blocks to compute. The loader fetches blocks from that list, while the matrix-multiplication threads concentrate on computation. This separates mask inspection from the main compute path while using Hopper’s asynchronous data transfers (TMA) and matrix-multiplication instructions (WGMMA) (§3.1).

A simple porting experiment illustrates why this separation matters. For a 128K Document mask, forward throughput was 19.0 TFLOPs/s for a FA3-style Hopper port without the KV Index Generator, versus 577.6 TFLOPs/s for the complete FlashMask-3 implementation. The full implementation includes other optimizations, however, so the entire difference cannot be attributed to this component alone (Appendix D.4, Table 7).

### Balance actual computation rather than token counts

Two equally long chunks can require different amounts of work if one has more masked blocks. FlashMask-3’s HCC-IPO algorithm accounts for that difference. It first balances computation across GPUs, adjusts assignments to reduce cross-node transfers, then rebalances within each node (§3.3).

A similar imbalance can occur inside one GPU: some execution units finish early while others remain occupied. The PPT scheduler lets a GPU thread block take another task when it finishes its current one. These two scheduling mechanisms reduce waiting across GPUs and within each GPU, respectively (§3.1).

### Overlap necessary communication with computation

Even with context parallelism, each GPU needs key and value data held by other GPUs. FlashMask-3 skips transfers of chunks that the mask makes entirely unnecessary and separates inter-node and intra-node communication routes. During backward computation, it divides work into segments so that communication for one segment overlaps computation for the next (§3.4).

## Overall pipeline

Saying “the mask is a bottleneck” combines three operations: **building a large table of masked entries, selecting blocks to compute, and assigning work to GPUs**. Slow preparation or uneven assignments can delay the next training step.

The figure uses small **illustrative examples** to make those operations visible. Its three panels are independent examples, not performance measurements from the paper.

![FlashMask-3 illustrative examples: encode document masks as boundaries, derive GPU-local intervals, and balance actual computation.](/assets/images/papers/2610.17901/operations-en.svg)

In the first panel, green entries are token pairs to compute; gray entries can be skipped. For key 6, rows 0–3 are masked, which can be recorded as the interval `[0, 4)`. The kernel uses such boundaries to **avoid loading or computing fully masked blocks** (§2.2, §3.1).

The second panel converts boundaries into GPU-local coordinates. Global interval `[6, 8)` becomes `[2, 4)` on GPU B. This conversion needs no communication between GPUs, but attention still requires key and value data transfers (§3.2).

In the third panel, assigning the same number of tasks to each GPU produces costs of 14 and 6. Reassigning the tasks yields 10 each. The actual HCC-IPO also considers cross-node transfer costs. **The change from 14 to 10 uses arbitrary illustrative work units, not measured speedups** (§3.3).

Finally, necessary transfers overlap computation. For example, the system can fetch data for a subsequent segment while computing a ready segment, reducing waiting. The figure shows storage, coordinate conversion, and assignment; it does not depict the detailed communication-overlap implementation (§3.4).

## How much faster is actual training?

The most useful result to examine first is full training throughput. Faster attention can produce a smaller overall gain when other training operations remain unchanged.

The experiment trained a MoE model with 118B total and 14B active parameters at a 128K context length. It used 128 H100 GPUs, CP degree 16, and an 8K local sequence per GPU. The baseline below already uses the FlashMask-3 kernel, but retains Dual Chunk assignment and all-gather communication with the proposed balancing and overlap disabled. This table therefore measures the **additional benefit of distributed execution optimizations**, rather than simply replacing the attention kernel (§4.3, Table 1).

| Mask sparsity | Baseline throughput | FlashMask-3 throughput | Full training gain | Attention forward+backward gain |
|---|---:|---:|---:|---:|
| 70% | 712.6 tokens/s/GPU | 764.7 tokens/s/GPU | 7.3% | 24.5% |
| 80% | 753.3 tokens/s/GPU | 811.4 tokens/s/GPU | 7.7% | 42.1% |
| 86% | 812.4 tokens/s/GPU | 902.1 tokens/s/GPU | 11.0% | 44.9% |

The table reproduces the paper’s mean values. Standard deviations and component-level experiments are available in the collapsed source tables below.

The distinction between the final two columns matters. Attention computation improved by up to 44.9%, but full training throughput improved by up to 11.0%. Training also includes operations this method does not change, such as gradient synchronization and optimizer updates. Reading the result as “44.9% faster training” would misstate its scope.

In a separate distributed attention experiment, total forward+backward throughput was 1.09–1.46 times that of MagiAttention. That experiment kept the local sequence length at 8K per GPU while varying CP degree from 4 to 32. Its results should not be treated as the same metric as full training throughput above (§4.2, Table 5).

Does FlashMask-3 beat FlashAttention-3 on one GPU? Not for the five masks compared in Table 6: its throughput was 0.71–1.00 times FA3’s. Its value lies in supporting a broader range of structured masks alongside distributed execution, rather than winning every FA3 comparison (Appendix D.4).

## Limitations to check before adoption

The first question is **whether the mask fits this representation**. If the masked queries for a key cannot be expressed as two intervals, the current format cannot be used directly. The kernel also targets Hopper’s TMA and WGMMA facilities; matching these gains on another GPU requires implementation work and validation. Both are limitations acknowledged by the authors (Appendix A).

The communication optimizations also depend on hardware layout. They exploit fast intra-node NVLink and slower inter-node links, and hierarchical routing currently applies to forward all-gather. Other topologies and an extension to backward reduce-scatter need further validation (Appendix A, C.4).

From a reviewer’s perspective, assignment overhead deserves attention too. The paper precomputes scheduling decisions and prefetches them to hide their cost during execution. If masks change too often to reuse this preparation, the benefit may shrink. In Figure 7(b), IPO’s load-balance advantage over the simpler LPT is only about 0.01 where it improves the result. Whether that extra scheduling complexity is useful for a particular workload needs separate evaluation (§4.4, Appendix D.5).

The scope of quality validation also matters. The mask conversion preserves the original masking relationships, and the paper compares training losses across 1,581 steps. It does not provide a separate downstream benchmark evaluation (Theorem 1, Appendix D.3).

FlashMask-3 is worth examining when long documents, structured masks, and multi-GPU training on Hopper are all required. Its central contribution is to use mask boundaries as information for deciding actual computation and communication, beyond merely storing the mask compactly. An adoption assessment should check mask compatibility, GPU and network layout, then full training throughput.
