## Verified claims

- `request-process-flow` — 초고가 그린 순서(API server → Tokenizer → Scheduler
  rank 0 → 나머지 rank → DeTokenizer → API server)를 네 지점에서 확인했다.
  `python/minisgl/server/api_server.py:265-278` 이 `TokenizeMsg` 를 보내고,
  `python/minisgl/tokenizer/server.py:87-101` 이 그것을 `UserMsg` 로 바꿔
  backend 로 넘기며, `python/minisgl/scheduler/io.py:96-107` 이 rank 0 에서 원시
  바이트를 재전송하고, `python/minisgl/tokenizer/server.py:71-85` 가 `UserReply`
  로 되돌린다. 메시지 타입 정의도 `message/tokenizer.py:27-38` 과
  `message/backend.py:32-36` 에서 확인했다.
- `process-roles` — 표의 네 행을 각각 소스에서 확인했다. 스케줄러 개수는
  `launch.py:54-69` 의 `for i in range(world_size)`, 디토크나이저 1 개는
  `launch.py:72-87`, 토크나이저 `num_tokenizer` 개는 `launch.py:88-103` 이다.
  듣는 주소도 전부 맞다. 스케줄러가 `zmq_backend_addr` 를 PULL 로 여는 것은
  `scheduler/io.py:36-37`, API server 가 `zmq_frontend_addr` 를 여는 것은
  `api_server.py:433-434` 에서 확인된다.
- ack 수 주장 — `launch.py:105-111` 의 `num_tokenizers + 2` 루프와
  `launch.py:24-25` 의 primary rank 만 ack 한다는 조건이 초고의 설명과 맞는다.
- 직렬화 주장 — `message/utils.py:20-35` 가 `__dict__` 를 훑어 `__type__` 에
  클래스 이름을 적고, 1 차원 텐서만 허용하는 단언을 갖는다는 설명이 원문과
  일치한다. 왕복 테스트는 `tests/misc/test_serialize.py:32-33` 이 맞다.

인용 16 곳을 원본과 대조했고 전부 해당 줄 범위에 존재했다. 코드 블록 10 개는
인용한 범위의 실제 텍스트와 문자 단위로 일치한다.

## Problems

- **저장소가 인용하지 않은 외부 출처를 링크했다.** 초안의 "더 읽을거리"가
  ZeroMQ 공식 가이드(zguide)를 가리켰다. `guide.md` 는 독자에게 넘길 출처를
  저장소가 이미 인용한 것으로 한정한다. 저장소는 `docs/structures.md:16` 에서
  ZMQ 와 NCCL 의 역할 분담을 밝히기만 하고 zguide 를 링크하지 않는다. 검토 중
  저장소 문서를 가리키도록 고쳤고, 최종본에는 위반이 남아 있지 않다.
- **표에서 rank 사이 브로드캐스트 주소가 빠졌다.** `scheduler/io.py:52-59` 의
  `zmq_scheduler_broadcast_addr` 는 표에 없다. 다만 본문이 rank 재전송을 설명할
  때 그 존재를 다루고 있고, TP rank 사이의 규약 자체는 8 편이 맡기로 선언돼
  있으므로 의도적 제외로 판단한다. 8 편이 이 주소를 반드시 표로 세워야 한다.
