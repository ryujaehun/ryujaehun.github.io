# tiny-vllm Chapter 8 · Continuous batching and the scheduler

Chapter 7 read the batch as a skeleton of two slots, `BATCH_SIZE=2`, confirmed that slots
are freed at EOT/EOT_ID or `MAX_SEQ_LEN-1` (`src/main.cpp:1015-1031`), and that at that
moment the physical blocks return to `free_blocks`. This chapter follows **where those
freed slots go**. When the tiny-vllm decode loop finds a free slot, it pulls the next
prompt from the queue, immediately prefills that slot, and includes it in the decode batch
of the same iteration. That is the "continuous batching" this repository implements.

The word "scheduler" in the title needs to be addressed first to avoid confusion. There is
no separate scheduler object in the source. There is no priority or preemption policy, and
no separate component that manages the queue. The only thing this chapter can call
"scheduling" is the slot-reuse rule embedded in the reconstruction phase of the decode loop
(`briefs.md:182`).

The main claims owned by this chapter are Claim 9 (immediate reuse of free slots) and
Claim 10 (per-layer `block_table` resynchronization); Claim 6 (decode KV scatter) is pulled
in by reference. Following the series' evidence rules, every claim cites the source path
and line range of the pinned commit (`guide.md:11-16`).

## Files and scope covered by this chapter

The target file for chapter 8 in `series.yaml` is a single file, `src/main.cpp`
(`series.yaml:25-27`). The claims used and their evidence are as follows.

- **Claim 9 (owned)** — In the decode loop, if there is a free slot, the next prompt from
  the queue is prefilled and immediately included in the decode of the same iteration.
  Evidence: `src/main.cpp:726-737` (`evidence/claims.md:90-100`).
- **Claim 10 (owned)** — In each layer of decode, after KV scatter changes `block_table`,
  the entire `block_table_gpu` is re-copied H2D and only then is `pagedAttention` called.
  A full synchronization also happens at the end of prefill and when a slot is freed.
  Evidence: `src/main.cpp:876`, `:552`, `:1030` (`evidence/claims.md:102-110`).
- **Claim 6 (reference)** — In decode, a new physical block is popped only when writing
  the first token of a block. Evidence: `src/main.cpp:851-873`.

The boundaries are clearly drawn. When this chapter discusses the "scheduler", it does not
describe any separate scheduler object, priority, or preemption, because none of these
support any claim; it describes only the slot-reuse logic (`briefs.md:182`). The internals
of the `pagedAttention` kernel (block table traversal, online softmax) are deferred to
chapters 9 and 10.

## The starting point of continuous batching: slot release

At the end of each decode iteration, the per-slot termination check runs
(`src/main.cpp:1015-1037`). If argmax is `END_OF_TEXT_TOKEN_ID` (128001) or
`EOT_ID_TOKEN_ID` (128009), or if `current_prompt_len == MAX_SEQ_LEN-1`, the slot is freed
(`evidence/trace.md:169-171`). Releasing restores four pieces of state at once.

| State | On release | Evidence |
|---|---|---|
| `is_slot_free[slot]` | returns to `true` | `:1017` |
| `free_blocks` | pushes the slot's physical blocks | `:1025` |
| `block_table` | resets the freed slot's row to -1 | `:1026` |
| `block_table_gpu` | re-synchronized H2D | `:1030` |

The point where chapter 7 read "a slot is both a compute unit and a KV memory unit" is
connected here to the next batch iteration. A slot whose `is_slot_free` has returned to
`true` becomes a "free slot" in the next decode iteration.

## Active reconstruction: filling free slots immediately

When the next decode iteration starts, `active_slots`/`active_tokens` re-collects the slots
to process in this iteration (`src/main.cpp:722-737`). This reconstruction phase is the
part handed over from chapter 7 to chapter 8, namely the **immediate reuse of free
slots**. If there is a slot whose `is_slot_free` is true, the prompt is popped from the
queue and `prefill` is called on that slot (`:733`). Prefill runs after clearing the
existing `generated_tokens` (`:732-733`) (`evidence/trace.md:135`).

The key is the end of the reconstruction. All slots are added to active (`:735-736`),
including the slot that was just prefilled. That is, a new prompt joins the decode batch of
**this same iteration without waiting** (`evidence/trace.md:137`). From the moment the
prompt arrives, that slot performs `embeddingGatherDecode` (`:759`), the Q/K/V GEMM
(`:763-842`), KV scatter (`:851-873`), and `pagedAttention` (`:878`) in the same iteration.

This structure is why the batching is "continuous". The composition of the batch changes
between iterations depending on the state of the queue and the lifetime of the slots.

## Batch width is bounded by the number of slots and varies over time

Chapter 7 read that the batch width is bounded above by the slot count of 2
(`src/main.cpp:29`; `en-07.md:140-141`). This chapter views the same fact from the other
direction. The number of slots is fixed, but **the composition of active slots changes
every iteration**. When a slot reaches EOT and is freed (`:1015-1031`), the reconstruction
of the next iteration (`:722-737`) places the next prompt from the queue into that slot. As
long as prompts remain in the queue, the batch stays full across both slots, and prompts
remaining in the queue join the batch later, one slot at a time.

The story changes once the queue is empty. A freed slot is no longer refilled, so the batch
width shrinks, and when `num_active_slots==0` the loop-termination check triggers. If the
queue is empty it is a `break` (`:739-744`); if prompts remain it is a `continue` (`:745`)
(`evidence/trace.md:204-205`).

As a timeline, slot release → prefill of the free slot → joining active in the same
iteration repeats.

```
end of decode iteration n:  slot 1 reaches EOT/MAX_SEQ_LEN-1 → released (:1015-1031)
                   is_slot_free[1]=true (:1017) · free_blocks push (:1025)
                   block_table[1] -1 (:1026) · block_table_gpu resynchronized (:1030)
                        │
                        ▼
start of decode iteration n+1:  active reconstruction (:722-737)
                   is_slot_free[1]==true → pop prompt from queue → prefill (:733)
                     ├─ existing generated_tokens cleared (:732-733)
                     └─ on prefill end, full block_table_gpu sync (:552)
                        │
                        ▼
                   all slots added to active (:735-736)
                   → the just-prefilled slot is immediately included in this
                     iteration (trace.md:137)
                        │
                        ▼
                   embeddingGatherDecode (:759) → Q/K/V GEMM n=num_active_slots
                   (:763-842) → layer loop (:760-972)
```

## The "scheduler" is not an object but a rule of the decode loop

What the title's "scheduler" refers to must be made precise. There is no separate scheduler
class or function in the source. The elements that compose the batch are the ones already
seen in chapter 7: the hardcoded queue (`src/main.cpp:584-594`), the slot-occupancy flag
(`:597`), the prefill function (`:150-553`), and the termination/release logic
(`:1015-1031`). The rule deciding "which prompt goes into which slot and when" is embedded
in the reconstruction phase of the decode loop (`:722-737`).

One notable point here is that the prefill called inside the decode loop is the **same
function** (`src/main.cpp:150-553`) as the one used in the initial prefill loop
(`:695-708`). The only difference is how a slot becomes empty; "pull from the queue and
fill one slot" is the same code repeated. Policies such as priority, preemption, or timeout
do not exist. In this repository, "scheduling" is not a policy but a rule implemented as a
loop branch (`briefs.md:182`). How this rule differs from vLLM's production scheduler
behavior is outside the scope of this series (`guide.md:7-9`).

## Decode's KV scatter changes the block table

Inside the decode layer loop, the KV scatter (`src/main.cpp:851-873`) works the way
Claim 6 describes. The logical block index is `seq_len / BLOCK_SIZE` and the in-block token
position is `seq_len % BLOCK_SIZE` (`:856-857`); only when writing the first token of a
block is a new physical block popped from `free_blocks` and recorded in `block_table`
(`:859-865`). K/V are copied D2D to `kv_cache + block*BLOCK_BYTES (+ V_OFFSET) +
token*KV_DIM` (`:866-872`).

This scatter changes `block_table` only at a block boundary, i.e. at the moment of writing
the first token of a block. Otherwise it merely overwrites the existing physical block at
the given position, so the table does not change. But that moment when the table changes is
the starting point of Claim 10.

## Per-layer block_table resynchronization (Claim 10)

The `pagedAttention` kernel reads the block table on the GPU. Through the
`gpu_active_slots` mapping, the kernel looks up the physical blocks of the actual slots
(`src/kernels.cu:464-470`, `:480`). The problem is that KV scatter changes **the CPU-side
`block_table`**. If the scatter recorded a new physical block but the GPU-side table still
holds the old state, the kernel cannot read the just-allocated block.

tiny-vllm's solution is simple. Inside the layer loop, it repeats the order scatter
(`:851-873`) → `block_table` → full H2D copy of `block_table_gpu` (`:876`) →
`pagedAttention` (`:878`) in every layer. The copy size is
`MAX_SEQUENCES*N_LAYERS*MAX_BLOCKS_PER_SEQ*sizeof(int)`, i.e. 2×16×128×4 bytes (16KiB)
(`src/main.cpp:876`; constant definitions `:38, :15, :36`). Even if only a single layer's
row changed, the entire table is sent again.

```
layer L loop (:760-972)
  KV scatter (:851-873)
    └─ if first token of a block, pop a new physical block and record block_table
       (:859-865)
        │  block_table may change
        ▼
  full H2D copy of block_table → block_table_gpu (:876)      ← Claim 10
        │
        ▼
  pagedAttention (:878; src/kernels.cu:525-527)          ← the GPU reads the table
        │
        ▼
  o_proj (:880-900) → residualAdd (:902) → rmsNorm (:904) → MLP (:907-971)
```

The same full synchronization also happens at two other points: at the end of prefill
(`src/main.cpp:552`) and when a slot is released (`:1030`). `:552` is the extra sync point
at prefill end. Immediately before `pagedAttention` in the same iteration, the per-layer
`:876` copies the whole `block_table_gpu` again. The sync at slot release (`:1030`), by
contrast, informs the GPU of the row reset to -1 (`:1026`).

The source itself acknowledges this full copy with a TODO. The comment reads "do it more
clever and not copy full table unnecessarily" (`src/main.cpp:551`).

## Limitations

- **Loop persistence of Claim 9** — The decode loop exits only when the queue is empty and
  `num_active_slots==0` (`src/main.cpp:739-746`), so after the queue empties the loop
  persists until all slots reach their termination condition (`evidence/claims.md:100`).
  `MAX_NEW_TOKENS_GENERATED` (`:12`) is only declared and never used in the loop condition.
- **The full copy of Claim 10** — The entire table per layer (2×16×128×4 bytes) is copied.
  The source acknowledges this with a TODO (`src/main.cpp:551`).
- **The reality of the word "scheduler"** — There is no scheduler object, priority, or
  preemption in the source. What this chapter calls "scheduling" is only the slot-reuse
  rule of the decode loop (`briefs.md:182`).
- **Reachability of the defensive branch** — `num_active_slots==0 && !queue.empty()` →
  `continue` (`:745`) is a branch that exists in the source. However, if a slot is free and
  prompts remain in the queue, prefill runs first in the reconstruction phase
  (`:722-737`), so this path appears to be a defensive branch that is practically
  unreachable. The evidence document also merely lists the branches and does not claim this
  path executes (`evidence/trace.md:204-205`).
- **No performance claims** — Whether 2-slot reuse is "efficient" and how long total generation takes
  have no evidence base in Claims 1-10, so neither is claimed.

## Summary

This chapter showed how the batch that chapter 7 read as "two fixed slots" changes its
contents over time. When the `active_slots` reconstruction at the start of a decode
iteration finds a free slot (`src/main.cpp:726-737`), the next prompt from the queue is
prefilled into that slot (`:733`), and the slot immediately joins the batch of the same
iteration (`:735-736`). Remaining prompts join later, one slot at a time, until the queue is
empty; once the queue empties, the batch width shrinks as each slot finishes, and the loop
ends at `num_active_slots==0` (`:739-746`). The "scheduler" orchestrating this whole flow
is not an object but a rule implemented as a loop branch.

Behind this flow is memory synchronization. When decode's KV scatter changes `block_table`
at a block boundary (`:851-873`, `:859-865`), `pagedAttention` is called only after the
entire `block_table_gpu` is re-copied H2D in every layer (`:876` → `:878`). The same full
synchronization repeats at prefill end (`:552`) and slot release (`:1030`). The following
chapters read what kernel this synchronization ultimately exists for, namely the
`pagedAttention` kernel's online softmax (chapter 9) and block table traversal
(chapter 10).
