# tiny-vllm Chapter 1 · tiny-vllm's Execution Path and Build

This series reads the `jmaczan/tiny-vllm` repository at the pinned commit
`1896ff5c37a241050dbcd9527caf9dc1d3087a61` (`project.yaml:1-2`). The series
narrative begins with the runnable program and the weight format, establishes
the token→logit forward pass, proceeds through memory and scheduling for
multiple requests, and ends with paged attention (`guide.md:24-29`). Under the
evidence rules, every implementation claim is cited with the source path and
line range from the pinned commit; README descriptions are only supporting
evidence, and code and tests decide any conflict (`guide.md:11-16`).

Chapter 1 is the first step in that narrative. It surveys which sources the
executable is built from and in what order `main()` proceeds through weight
loading → prefill → decode → shutdown. The internals of weight loading
(Chapter 2), the tokenizer and embeddings (Chapter 3), the transformer block
(Chapter 4), attention and the KV cache (Chapter 5), batching (Chapters 7–8),
and paged attention (Chapter 10) are only touched at their entry points here
and handed off to their owning chapters.

## Files and Scope Covered by This Chapter

The target files of Chapter 1 are `CMakeLists.txt`, `src/main.cpp`, and
`test.sh`. The executable `tiny-vllm` is composed by `add_executable` from two
sources, `src/main.cpp` and `src/kernels.cu` (`CMakeLists.txt:49-52`). That is,
the entry point of the build artifact is `main.cpp`, and the kernel
implementation is `kernels.cu`.

This chapter does not make claims about the details of the build system. None
of the series' evidence claims (Claims 1–10) address CMake options, CUDA
architectures, linked libraries, or the internals of `test.sh`, so that content
is not described. The CUDA/HIP portability layer (`src/cuda_to_hip.h`) is also
not covered because there is no evidence claim for it. Training, distributed
serving, and performance claims external to the repository are outside the
series' scope (`guide.md:7-9`, `guide.md:11-16`).

Checking the repository size with the inventory, there are 31 items in total,

Chapter 5.

## main(): The Nine-Step Execution Path

The entry point is `main(int, char**)` (`src/main.cpp:555`). The top-level
order of `main` is the following nine steps.

```
main (:555)
 ├─ 1. Create cuBLAS handle (:557-563)
 ├─ 2. loadWeights(:566-569) ───────────────── Chapter 2
 ├─ 3. init_rope_frequencies (:572)
 ├─ 4. Initialize KV cache·block table (:574-581) ── Claim 5
 ├─ 5. Initialize prompt queue·batch state (:584-601) ─ Claim 9
 ├─ 6. Allocate CUDA buffers (:615-693)
 ├─ 7. Initial prefill loop (:695-708) ─────────── Claim 3·9
 ├─ 8. Infinite decode loop (:720-1039) ─────────── Claim 4
 └─ 9. Shutdown: "Ok bye!" (:1040-1044)
```

1. **Create cuBLAS handle** — creates the handle with `cublasCreate` and
   `return 1` on failure (`src/main.cpp:557-563`).
2. **Load weights** — if `loadWeights(weights)` fails, `return 1`
   (`src/main.cpp:566-569`). The function first checks the device count with
   `checkGPUStatus` (`:81-84`, returns 1 if there are zero devices, `:44-48`),
   opens `model.safetensors`, parses the header, and then uploads the entire
   tensor bytes to the GPU (`:79-147`). Its internals are covered in Chapter 2.
3. **Initialize RoPE frequencies** — `init_rope_frequencies(HEAD_DIM,
   MAX_SEQ_LEN, 500000, 32, 1, 4, 8192)` (`src/main.cpp:572`). It prepares
   sin/cos tables on the GPU with Llama3 NTK scaling applied
   (`src/kernels.cu:96-152`).
4. **Initialize KV cache and block table** — allocates `kv_cache` at 2GiB
   (`src/main.cpp:576`), fills `free_blocks` with 0..65535 (`:577-578`),
   initializes the CPU `block_table` entirely to -1, and allocates
   `block_table_gpu` (`:579-581`). This step creates the fixed block pool and
   the CPU/GPU block tables of Claim 5.
5. **Initialize prompt queue and batch state** — pushes four hardcoded token ID
   vectors onto the queue (`:584-594`, details in the next section) and
   initializes two `is_slot_free` slots and three kinds of generation state
   vectors (`:596-601`). The starting point of fixed `BATCH_SIZE=2` slot
   batching is Claim 9.
6. **Allocate CUDA buffers** — allocates all the device buffers used by
   prefill and decode, from `gpu_input_tokens` through
   `k_proj_batched_buffer` (`:615-693`). `prefill_attn_scores` is sized at
   `MAX_PROMPT_LEN * MAX_PROMPT_LEN * sizeof(bf16) * NUM_Q_HEADS` =
   512×512×2×32 bytes (`:648`). The prompt length limit of 512 and this
   allocation are the premise for the kernel guard section that follows.
7. **Initial prefill loop** — with `for (slot = 0; slot < 2 && !queue.empty();
   ++slot)`, calls `prefill` on free slots to fill slots 0 and 1 with the
   queue's first two prompts (`src/main.cpp:695-708`). The body of `prefill`
   runs pop prompt → `embeddingGather` → layer loop → final rmsNorm → logits
   GEMM → CPU argmax (`:150-553`; entry point cited at `:152-163`). Claim 3
   covers this entire path, and Claim 9 supports "fills only the first two of
   the queue."
8. **Infinite decode loop** — inside `while(true)` (`:720`), reconstructs the
   active slots (`:722-737`), and when a free slot appears, prefills the next
   prompt from the queue and immediately includes it in the same iteration's
   decode (entry point cited for Claim 4 at `:722-737`, Claim 9). If there are
   no active slots and the queue is empty, `break` (`:739-746`); if the queue
   still has entries, `continue` (`:745`). The details of the per-layer batched
   GEMM → KV scatter → `pagedAttention` → logits → CPU argmax are covered in
   Chapters 4–8.
9. **Shutdown** — prints `"Ok bye!"` and, after `cublasDestroy` and
   `cudaDeviceSynchronize`, `return 0` (`src/main.cpp:1040-1044`).

## The Prompt Queue: Hardcoded Starting Input

The four prompts are hardcoded not as strings but as token ID vectors
(`src/main.cpp:584-594`). Counting the elements gives 17, 14, 13, and 14
respectively.

- PROMPT 0 — length 17 (`src/main.cpp:585`)
- PROMPT 1 — length 14 (`src/main.cpp:588`)
- PROMPT 2 — length 13 (`src/main.cpp:591`)
- PROMPT 3 — length 14 (`src/main.cpp:594`)

For this reason, there is no string→token conversion step in the C++ execution
path. The includes of `src/main.cpp` are only `iostream`, `numeric`, `fstream`,
`cuda_to_hip.h`, `queue`, `json.hpp`, and `kernels.cuh` (`:1-8`), with no
socket or server layer, so this program is a single executable that consumes
prompts locally without network I/O. The fact that prompts are hardcoded token
ID vectors leads back to (part of) Claim 9 in Chapter 3.

The generation limit and termination conditions also come from fixed constants.
`MAX_NEW_TOKENS_GENERATED = 20` (`src/main.cpp:12`) is only declared and is not
used anywhere else. The actual termination condition is only that the argmax
result equals `END_OF_TEXT_TOKEN_ID` (128001) or `EOT_ID_TOKEN_ID` (128009), or
that `current_prompt_len == MAX_SEQ_LEN-1`, at which point the slot is released
(`src/main.cpp:26-27`, `:1015-1031`). Therefore the decode loop continues even
after the queue is empty until all slots reach a termination condition
(`:720`, `:739-746`).

## Kernel Launch Guards: The 1024-Thread Limit

Five of the kernel wrappers in `src/kernels.cu` have guards that skip execution
when the thread count exceeds 1024. However, the guard variable differs from
kernel to kernel, and under this fixed configuration none of them triggers.
Let us check the exact conditions one by one.

- **`rope` (prefill)** — skipped if `num_threads = proj_dim / 2` exceeds 1024
  (`src/kernels.cu:204-209`). The call arguments are
  `EMBEDDING_LENGTH=2048` (→1024) and `KV_DIM=512` (→256)
  (`src/main.cpp:244-245`). Since `proj_dim/2 ≤ 1024`, it does not trigger.
- **`ropeDecode`** — skipped by the same guard if `proj_dim / 2 > 1024`
  (`src/kernels.cu:390-395`). The call arguments are likewise 2048 and 512
  (`src/main.cpp:847-848`). It does not trigger.
- **`causalMask`/`softmax` (prefill)** — skipped if `num_tokens > 1024`
  (`src/kernels.cu:241-245`, `:295-299`). Here `num_tokens` is `prompt_len`
  (`src/main.cpp:329`, `:331`), and prompts are capped by
  `MAX_PROMPT_LEN=512` (`src/main.cpp:30`) with `prefill_attn_scores`
  allocated at that same limit (`:648`), so it does not exceed 1024. It does
  not trigger.
- **`softmaxDecode`** — skipped if `seq_len > 1024` (`src/kernels.cu:444-448`),
  but this function is only declared (`src/kernels.cuh:25`) and defined
  (`src/kernels.cu:442-458`) and is never called anywhere. The decode softmax
  is handled by the online softmax inside `pagedAttentionKernel`
  (`src/kernels.cu:508-519`).

The behavior when a guard triggers is not "the kernel quietly drops out" but
"**prints a message and does not run the kernel**." Each guard prints via
`std::cout`, for example, "Can't launch more than 1024 threads on RTX 5090,
RoPE kernel not launched", and then `return`s (`src/kernels.cu:207`, `:243`,
`:297`, `:393`, `:446`).

In other words, these guards are **latent paths** that are unreachable under
the current constant configuration. They could trigger if `prompt_len` left
`MAX_PROMPT_LEN` or if `proj_dim` grew, but on the pinned commit's execution
path execution is never skipped even once.

## Limitations

- This repository was not run, and the build and kernel behavior were not
  verified by execution (`evidence/recon.md:4`). The execution constants and
  the `main()` path are described on the basis of the sources and the
  inventory.
- The constants (`N_LAYERS`, `EMBEDDING_LENGTH`, etc.) are redundantly defined
  at `main.cpp:12-38` and `kernels.cu:8-19`, and the source acknowledges this
  duplication via a TODO (`src/kernels.cu:6`). The two locations' values were
  confirmed equal by comparing the sources, but this leaves a risk of
  divergence on future edits.
- The kernel launch guards (the "Kernel Launch Guards" section of this
  chapter) are only latent paths and do not trigger under the current constant
  configuration. The statement that "if the sequence exceeds 1024 the kernel
  drops out of the computation" is not supported by the source.
- `softmaxDecode` is a function that is only declared and defined and is never
  called. The decode softmax is inlined inside `pagedAttentionKernel`
  (`src/kernels.cu:461-523`).
- `MAX_NEW_TOKENS_GENERATED` is only declared and is not used in the loop
  condition. The decode loop continues until the queue is empty and all slots
  reach a termination condition (`src/main.cpp:720`, `:739-746`, `:1015`).
- The line counts and inventory size in this chapter were confirmed against
  the pinned-commit sources, but build artifacts were not confirmed by running
  the repository.

## Summary

Chapter 1 is the series' map. The executable `tiny-vllm` is built from
`src/main.cpp` and `src/kernels.cu` (`CMakeLists.txt:49-52`), and `main()`
executes in nine steps: cuBLAS creation → weight loading → RoPE initialization
→ KV cache and block table → prompt queue → buffer allocation → initial
prefill → decode loop → shutdown (`src/main.cpp:555-1044`). Prompts are
hardcoded as four token ID vectors (17·14·13·14) (`:585-594`), and the
generation-limit constant is only declared, while termination is decided by
EOT/EOT_ID or `MAX_SEQ_LEN-1` (`:1015`).

This chapter also checked the kernel wrappers' 1024-thread guards. The guards
exist, but `rope`/`ropeDecode` have `proj_dim/2 ≤ 1024`, `causalMask`/`softmax`
have `prompt_len ≤ MAX_PROMPT_LEN=512`, so they do not trigger, and
`softmaxDecode` is never called. Even when triggered, the behavior is to
"print a message and not run the kernel." From the next chapter onward, we
follow this path and fill it in one piece at a time, starting with weight
loading.
