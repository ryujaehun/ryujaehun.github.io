## safetensors: A Format Where the Header Describes Tensor Placement

Before reading the code, let us establish the file format. safetensors does not
serialize tensor data itself; it is closer to a container that writes "what is
where" into a header. The layout `loadWeights` assumes has three parts.

```
┌────────────────────┬──────────────────────────┬─────────────────────────────┐
│ 8-byte header len N │ JSON header (N bytes)    │ raw tensor bytes            │
└────────────────────┴──────────────────────────┴─────────────────────────────┘
                      │
                      └─ tensor name → { dtype, shape, data_offsets: [begin, end) }
                         special key __metadata__ → string metadata (not a tensor)
```

- **8-byte header length** — tells how many bytes the JSON header is. The source
  reads this value as `uint64_t` (`src/main.cpp:96-97`).
- **JSON header** — has tensor names as keys and each tensor's `dtype`, `shape`,
  and `data_offsets` as values. `data_offsets` is a half-open interval
  `[begin, end)` and a relative position with the start of the raw byte region
  as 0. This interpretation comes from the way the code uses the end value of
  `data_offsets` as the allocation size (below).
- **Raw tensor bytes** — the actual weight bytes following the header. The
  tensors are laid out contiguously within this region.

`__metadata__` is not a tensor but a string metadata key attached to the header.
`loadWeights` skips this key when building the map (`src/main.cpp:108-111`).

## loadWeights: From Preparation to the H2D Copy

The execution order of `loadWeights` is as follows. The second step of `main()`
that Chapter 1 identified unfolds here.

1. **GPU check** — calls `checkGPUStatus()` first (`src/main.cpp:81-84`). Its
   definition is at `:40-62`, and if the device count is 0 it returns `1` and
   stops loading.
2. **Open the file** — opens `model.safetensors` in binary (`:87-93`). On
   failure it returns `1`.
3. **Read the header length** — reads 8 bytes as a `uint64_t` to obtain the
   JSON header size (`:96-97`).
4. **Read and parse the JSON header** — reads the header bytes and parses them
   (`:99-101`).
5. **Name→offset map and `max_offset`** — collects each tensor's `data_offsets`
   into a map, and stores the maximum of the end values `data_offsets[1]` as
   `max_offset` (`:103-118`; maximum computation `:105-115`). `__metadata__` is
   excluded here (`:108-111`).
6. **GPU allocation** — allocates `model_weights` with `cudaMalloc` at size
   `max_offset` (`:120-121`).
7. **Raw bytes into a CPU buffer** — reads the raw weight bytes into a CPU
   vector (`:123-125`).
8. **H2D copy** — copies the CPU buffer to the GPU in one shot (`:127`).
9. **Assign tensor pointers** — sets each tensor pointer relative to its offset
   (`:132-145`).

In this order the meaning of `max_offset` is key. It is the largest of all
tensors' end offsets, so it is the size that holds the entire raw byte region.
Thus a single allocation at step 6 accommodates all tensors, and a single copy
at step 8 uploads them all to the GPU. This is the point Claim 1 summarizes as
"a single H2D copy of the entire raw bytes" (`evidence/claims.md:8`,
`src/main.cpp:120-127`).

## From Offsets to Tensor Pointers

By the end of step 8 the GPU has a single flat byte blob of size `max_offset`.
Step 9 is the stage that labels this blob. Computing pointers relative to each
tensor's start offset yields pointers of the form `model_weights + begin`
without any per-tensor copy. The tensor set assigned by `:132-145` is as
follows.

| Tensor | Role (from the next chapter onward) | Evidence |
|---|---|---|
| `embed_tokens` | token embedding gather, final logits GEMM | `src/main.cpp:132-145` |
| `norm` | final RMSNorm | `src/main.cpp:132-145` |
| `input_layernorm` (per layer) | RMSNorm before attention | `src/main.cpp:132-145` |
| `post_attention_layernorm` (per layer) | RMSNorm before MLP | `src/main.cpp:132-145` |
| `mlp_down_proj` / `mlp_gate_proj` / `mlp_up_proj` (per layer) | SwiGLU MLP | `src/main.cpp:132-145` |
| `w_k` / `w_o` / `w_q` / `w_v` (per layer) | attention Q/K/V/o projections | `src/main.cpp:132-145` |

Claim 1 summarizes the assignment list at `:132-145` as `embed_tokens`, `norm`,
and the per-layer `input_layernorm`/`mlp_*`/`w_k/w_o/w_q/w_v`
(`evidence/claims.md:13`). `post_attention_layernorm` is an item that
`trace.md`, which traced the same range in finer detail, additionally recorded
(`evidence/trace.md:44-46`).

The pointers at this point are not yet used. `loadWeights` only prepares
addresses, and the weights are read later in prefill's projections, MLP, and
final logits GEMM. For example, `embed_tokens` appears as the transpose operand
in the logits GEMM at the end of prefill (`src/main.cpp:509-527`). That
consumption point is the subject of Chapter 4 onward.

## Limitations

- This repository was not run, so the memory layout of `loadWeights` could not
  be verified against an actual file (`evidence/recon.md:4`). The procedural
  description in this chapter is based on the source and the trace notes.
- `json.hpp` is a 25830-line third-party header, and the detailed behavior of
  JSON parsing is outside the verification scope (`evidence/recon.md:15`,
  `evidence/claims.md:14`). This chapter cites only the call site
  (`src/main.cpp:99-101`).
- The statement that tensor pointers are computed relative to the start offset
  (`data_offsets[0]`) comes from Claim 1's phrasing "offset-based assignment"
  and from file-format convention. The exact per-tensor offset indexing at
  `:132-145` was not decomposed and cited line by line in this chapter.
- The fact that `__metadata__` is skipped is confirmed by the source
  (`src/main.cpp:108-111`), but the explanation of the reason — "because it is a
  metadata key, not a tensor" — is a format interpretation.
- Because there is no loader-specific test, the correctness of the offset-based
  assignment is not backed by tests. The only test is `tests/test_softmax.cu`
  (`evidence/recon.md:12`).
- Format conversion and quantization paths that are not in the repository are
  not described.

## Summary

Chapter 2 opened the "weight loading" box of `main()`. `loadWeights` reads the
8-byte header length of the safetensors file (`src/main.cpp:96-97`), parses the
JSON header (`:99-101`), and takes the maximum end value of each tensor's
`data_offsets` as `max_offset` (`:103-118`). It allocates GPU memory once at
that size (`:120-121`), reads the raw bytes into the CPU (`:123-125`), uploads
them in a single H2D copy (`:127`), and then assigns tensor pointers relative to
their offsets (`:132-145`). `__metadata__` is excluded because it is not a
tensor (`:108-111`).

The point of this design is "upload as one blob and only divide up the
addresses." The next chapter uses `embed_tokens` among these pointers to turn
the hardcoded prompt tokens into embeddings and begins the forward pass toward
the first token.
