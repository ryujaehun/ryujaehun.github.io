# 2. Weight Loading and GPU Buffer Design

Every path and line number in this article points to the tree at the fixed
revision `e25bf1994efa90bc98b721ba7c527402f86fbeaf`. The notation is

## The Question of This Chapter

How are safetensors weights read and loaded into GPU memory, and which buffers
are preallocated? The code scope is a single file, `src/main.cpp`. The minimum
evidence for this chapter is 3 code citations, 0 tests, and 0 runs. Since there
are no tests, all verification is done solely through source citations.

This chapter owns buffer size computation and aliasing design. Build boundaries
and the execution entry point belong to Part 1; prefill's kernel call order and
parallel reduction to Part 3; cuBLAS transpose and layout to Part 4; the
decode-family kernels and paged attention to Parts 5–6; and the lifetime of
slots and queues to Part 7. Because the environment has no GPU or CUDA
toolchain, no allocation or copy was executed. The weight file
`model.safetensors` belongs to the gated model
`meta-llama/Llama-3.2-1B-Instruct`, so obtaining it is also a constraint.

## This Chapter's Place in the Entry Sequence

`main` creates the cuBLAS handle (`src/main.cpp:557-563`) and immediately calls
`loadWeights` (`src/main.cpp:566-569`). It then initializes the RoPE frequency
table (`src/main.cpp:572`), sets up the paged KV cache allocator
(`src/main.cpp:574-581`), prepares the prompt queue (`src/main.cpp:583-594`)
and the slot/batch state (`src/main.cpp:597-610`), and finally allocates the
compute buffers (`src/main.cpp:617-693`). After that, the initial prefill loop
fills the empty slots (`src/main.cpp:695-708`).

The two blocks this chapter covers are `loadWeights` (`src/main.cpp:79-147`)
and the buffer allocation section (`src/main.cpp:617-693`). The paged KV cache
and slot state are the subjects of Parts 6 and 7, but from a memory-layout
perspective only the initialization points are confirmed here.

## Uploading a Single safetensors File All at Once

`loadWeights` is divided into four steps.

1. GPU check. It first calls `checkGPUStatus` (`src/main.cpp:40-62`)
   (`src/main.cpp:81-84`); if there are no devices at all, it prints an error
   and then `return 1` (`src/main.cpp:44-48`).
2. Open the file. It opens `model.safetensors` in the working directory in
   binary mode (`src/main.cpp:87`). On failure it is `return 1`
   (`src/main.cpp:88-93`).
3. Read the header. It reads the header length from the first 8 bytes
   (`src/main.cpp:96-97`), then reads the header string of that length
   (`src/main.cpp:99-101`).
4. Compute offsets. After parsing the header JSON (`src/main.cpp:104`), it
   iterates over each tensor, skips `__metadata__` (`src/main.cpp:106-111`),
   updates `max_offset` with the end value of `data_offsets`, and records the
   start value in a name→offset map (`src/main.cpp:112-117`).

This `max_offset` is the byte size of the entire set of weights. The code does a
single `cudaMalloc` of this size (`src/main.cpp:120-121`), creates a CPU vector
of the same size, reads the rest of the file into it (`src/main.cpp:123-125`),
and uploads it to the GPU with a single H2D copy (`src/main.cpp:127`). It is not
allocated per tensor but as a single allocation, and each individual tensor is
an address range within it.

Finally, it fills the pointers of the `Weights` struct using the tensor
name→offset map (`src/main.cpp:132-145`). The struct (`src/main.cpp:64-77`)
holds two single pointers, `embed_tokens` (`src/main.cpp:66`) and `norm`
(`src/main.cpp:76`), and nine per-layer arrays (`src/main.cpp:67-75`). The
per-layer arrays are `input_layernorm`, `mlp_gate_proj`, `mlp_up_proj`,
`mlp_down_proj`, `post_attn_layernorms`, `w_k`, `w_o`, `w_q`, and `w_v`, each
holding `N_LAYERS` (16) pointers (`src/main.cpp:15`, `src/main.cpp:67-75`).
There are thus 11 fields in total. The mapping loop iterates over 16 layers and
computes the addresses of the 9 kinds of tensors (`src/main.cpp:134-145`).

The struct comment states that the model structure is always assumed to be
Llama 3.2 1B-Instruct (`src/main.cpp:130-131`), and the path, too, is hardcoded
as a string rather than an argument (`src/main.cpp:87`).

## The 16 Preallocated Buffers

Buffer allocation is gathered at `src/main.cpp:617-693`. The size constants are
at `src/main.cpp:12-38`. `MAX_BUFFER_SIZE` is
`max(MAX_PROMPT_LEN, BATCH_SIZE)` (`src/main.cpp:31`), and since it is the
larger of 512 and 2, it is 512. A bf16 element is 2 bytes.

## Size Arithmetic

The bytes in the table are values computed directly from the constants.
`prefill_attn_scores` is `512 × 512 × 32 = 8,388,608` elements, and since it is
bf16, `16,777,216` bytes, i.e. 16 MiB (`src/main.cpp:30`, `src/main.cpp:20`,
`src/main.cpp:647-648`). `gate` and `up` are each `512 × 8192 = 4,194,304`
elements, i.e. 8 MiB (`src/main.cpp:17`, `src/main.cpp:662-663`,
`src/main.cpp:667-668`). `embed_proj` is `512 × 128,256 = 65,667,072` elements,
i.e. 125.25 MiB (`src/main.cpp:25`, `src/main.cpp:676-677`).

`embed_proj`'s element count is about 7.8 times that of `prefill_attn_scores`
(`65,667,072 ÷ 8,388,608 ≈ 7.83`). The logits buffer is the largest single
buffer in this chapter, and its host copy `embed_proj_cpu` is also allocated
with the same element count (`src/main.cpp:681-682`). `embed_proj` uses
`MAX_BUFFER_SIZE` (512), so the maximum prompt length, not the batch size of 2,
dominates its size (`src/main.cpp:31`).

The temp buffers are smaller. `k_proj_temp_buf`·`v_proj_temp_buf` are
`512 × 512 = 262,144` elements (512 KiB) (`src/main.cpp:635-639`), and the
decode `k_proj_batched_buffer`·`v_proj_batched_buffer` are `2 × 512 = 1024`
elements (2 KiB) (`src/main.cpp:689-693`). `gpu_input_tokens` is
`512 × 4 = 2048` bytes (`src/main.cpp:617-618`).

## Buffer Aliasing Design

Two buffers are shared by two different roles separated in time. The code
comments state this explicitly.

- `buf_2048_1` is shared by `q_proj` and `attn_scores_v`
  (`src/main.cpp:628`). It first receives the Q projection output as
  `q_proj = buf_2048_1` (`src/main.cpp:177`), and the per-head attention score
  computation reads this `q_proj` as Q input (`src/main.cpp:301-327`,
  especially `src/main.cpp:304`). Only after Q has been fully read does it write
  the same buffer again as `attn_scores_v = buf_2048_1` for the scores×V output
  (`src/main.cpp:343`).
- `buf_2048_2` is shared by `o_proj` and `down` (`src/main.cpp:656`). It
  receives the O projection output as `o_proj = buf_2048_2` (`src/main.cpp:377`),
  the residual kernel reads it and adds it to `hidden_state`
  (`src/main.cpp:399`), and then it receives the down projection output as
  `down = buf_2048_2` (`src/main.cpp:470`).

In both cases only one role is used at a time. Since the Q and scores×V outputs,
and the O and down outputs, do not need to be alive simultaneously, a single
buffer suffices. However, this safety is a static claim based on the consumption
order in the source, and there is no runtime verification.

In the decode path, the output of `pagedAttention` is written again to
`buf_2048_1` (`src/main.cpp:878`). Its in-place safety and paged attention's
inputs/outputs are owned by Part 6.

## Initial Layout of the paged KV cache and Slot State

Separately from the 16 buffers, `main` also preallocates memory for paged
attention. It `cudaMalloc`s `kv_cache` as 2GB (`src/main.cpp:575-576`, constant
`src/main.cpp:35`) and fills `free_blocks` from 0 to 65535
(`src/main.cpp:577-578`, constant `src/main.cpp:37`). It initializes all of
`block_table`'s `MAX_SEQUENCES × N_LAYERS × MAX_BLOCKS_PER_SEQ` entries to `-1`
(`src/main.cpp:579`) and `cudaMalloc`s a `block_table_gpu` of the same size
(`src/main.cpp:580-581`). At this point there is no upload to the GPU. The actual
H2D copy happens at the end of `prefill`, targeting the entire `block_table`
(`src/main.cpp:552`).

The slot/batch state is also allocated at this time. `is_slot_free` sets
`BATCH_SIZE` entries to `true` (`src/main.cpp:597`), and it creates
`generated_tokens`·`last_generated_tokens`·`current_prompt_len`
(`src/main.cpp:599-601`). `active_slots`·`active_tokens`, which are passed to
kernels as contiguous memory, are left as empty vectors
(`src/main.cpp:604-605`), and `gpu_active_slots`·`gpu_seq_lens` are each
`cudaMalloc`ed with size `BATCH_SIZE` (`src/main.cpp:607-610`). The lifetime of
these states is owned by Part 7.

## Limitations of This Chapter

- This series was written in an environment without an NVIDIA GPU or CUDA
  toolchain, so no allocation, copy, or kernel was executed. The claims about
  `loadWeights` and buffer sizes are all source citations.
- The minimum evidence for this chapter is 3 code citations, 0 tests, and 0
  runs. Kernel execution time, throughput, and memory usage are not measured,
  and this chapter contains no performance figures that could be read as
  measured values. The bytes in the table are estimates computed from
  compile-time constants, not measured values.
- The weight file is the `model.safetensors` of the gated model
  `meta-llama/Llama-3.2-1B-Instruct`, so obtaining it is a constraint, and the
  actual load was not verified.
- `loadWeights` assumes the model structure is always Llama 3.2 1B-Instruct
  (`src/main.cpp:130-131`) and the file path is also hardcoded
  (`src/main.cpp:87`). On other models the tensor name mapping breaks.
- The safety of buffer aliasing is a static claim about consumption order, and
  there is no runtime verification of concurrency or contention.
- `MAX_SEQ_LEN`, `BATCH_SIZE`, `MAX_PROMPT_LEN`, etc. are hardcoded constants
  with TODO comments (`src/main.cpp:28-31`). If these values change, the sizes
  in the table change with them.
