# tiny-vllm Chapter 6 · The different bottlenecks of prefill and decode

Up through Chapter 5, prefill and decode were read side by side as "two paths
that write values into the KV cache." This chapter changes that view and reads
the two paths as a unit of work each. prefill receives one prompt and processes
its **entire tokens** at once (`src/main.cpp:150-553`), while decode produces
**one token** per active slot on every iteration (`:720-1039`). It is the same
layer pipeline, but the number of tokens handled at once and the work and copy
counts that grow along with it diverge in opposite directions. Sorting that
structural difference into "bottlenecks" is this chapter's share.

This chapter's implementation claims are Claim 3 for the prefill path and
Claim 4 for decode's batching and argmax. The difference in KV scatter (Claim 6)
and the 2 GiB reservation (Claim 5) are drawn in as references. Following the
series' evidence rules, every claim cites source paths and line ranges from the
pinned commit (`guide.md:11-16`).

## prefill: processing the whole prompt at once

prefill pops one prompt from the queue (`src/main.cpp:152-154`), occupies a
slot (`:155`), and uploads its tokens to the GPU (`:157`). From here on, the
character of prefill is set. `embeddingGather` takes the block as the **token
count** and gathers the whole prompt into embeddings at once (`:158`;
`src/kernels.cu:42-53`, kernel `:32-40`). In other words, prefill's parallelism
width is matched to the prompt length from the very start.

Inside the layer loop (`src/main.cpp:164-493`), this "all tokens at once"
pattern repeats. The Q projection GEMM runs with `m=EMBEDDING_LENGTH,
n=prompt_len, k=EMBEDDING_LENGTH` (`:177-196`), and the K/V projection GEMMs
with `m=KV_DIM, n=prompt_len` (`:201-240`), transforming every token of the
prompt simultaneously. K/V pass through `rope` (`:244-245`) and are scattered
into the KV cache block by block (`:247-288`, Claim 6). attention is the part
that grows **quadratically** with the prompt length. The per-head score GEMM
(`:301-327`) → `causalMask` (`:329`; `src/kernels.cu:239-255`) → `softmax`
(`:331`; `src/kernels.cu:293-309`) → scores×V GEMM (`:343-371`) all handle a
`prompt_len × prompt_len` score matrix, and the `prefill_attn_scores` buffer
holding that matrix is reserved as `MAX_PROMPT_LEN² × NUM_Q_HEADS`
(`src/main.cpp:648`).

These prefill-only kernels bring a limitation with them. The `causalMask` and
`softmax` kernels cannot exceed the token count in thread count, so when
`prompt_len > 1024` they do not run and only print a message
(`src/kernels.cu:241-244`, `:295-298`). The prompts in this commit are at most
17 tokens, so it is never reached (`evidence/trace.md:228-231`), but it remains
a general limitation of the prefill path. Because of this guard, prefill's
attention work is only intact in the `prompt_len ≤ 1024` range.

Once the layer loop finishes, after the final `rmsNorm` (`:494`), the logits
GEMM is computed with `m=VOCAB_SIZE, n=prompt_len` for the **entire** prompt
(`:509-527`). The logits are copied to the CPU (`:529`), and the next token is
chosen by a CPU argmax on the last token row (`:533-543`). When the argmax
finishes, the generated-token state is updated (`:546-548`) and the whole
`block_table` is synchronized to the GPU (`:552`).

In short, prefill is a **large job** that takes tokens as its parallelism width
within a single call. The GEMMs grow in work with the prompt length, attention
with its square, and the logits' D2H copy and CPU argmax happen exactly once
per prompt.

## decode: producing one token per slot each iteration

The decode loop produces the next token of each active slot, one per slot, on
every iteration (`src/main.cpp:720-1039`). At the start of an iteration the
active slot list is rebuilt (`:722-737`); if there is a free slot, the next
prompt from the queue is prefilled and included in the same iteration
(`:726-737`). When all slots are finished and the queue is empty, the loop ends
(`:738-746`).

The contrast with prefill begins at the input. `embeddingGatherDecode` takes
the block as the **active slot count** (`:759`; `src/kernels.cu:358-369`, kernel
`:347-356`). Since it gathers only one token per slot into embeddings rather
than the whole prompt, its parallelism width is exactly the batch size. In the
layer loop that follows (`src/main.cpp:760-972`), the Q/K/V GEMMs run with
`n=num_active_slots` (`:763-783`, `:802-821`, `:824-842`). Where prefill
gathered tokens together with `n=prompt_len`, decode bundles "one token at a
time" with `n=the number of active slots`. After the per-slot `ropeDecode`
(`:844-849`), the KV scatter is token-by-token (`:851-873`, Claim 6). Once the
scatter finishes in each layer, `block_table_gpu` is re-synchronized (`:876`;
details in Chapter 8, Claim 10) and `pagedAttention` is called (`:878`; kernel
details in Chapter 10).

The big difference in decode's attention from prefill is that there is no
separate kernel for masking and softmax. prefill builds and consumes a
`prompt_len × prompt_len` matrix with the `causalMask` and `softmax` kernels,
while decode's `pagedAttention` kernel reads only the **cumulative K tokens** in
the KV cache, standing in for masking and folding online softmax inside
(`src/kernels.cu:461-523`). In other words, attention work grows linearly with
"the sequence length accumulated so far." The kernel's exact structure is
Chapter 10's share; this chapter only establishes the structural fact that
"unlike prefill, decode calls no separate softmax kernel for attention."

The second contrast appears in logits handling. After the final `rmsNorm`
(`:974`) and the logits GEMM (`:976-994`) following the layer loop, the logits
are copied to the CPU (`:996`) and a **per-slot** CPU argmax runs
(`:1000-1012`). The argmax casts bf16 to float before comparing
(`:1003-1010`). This D2H copy plus CPU argmax happens **on every iteration**.
The end-of-iteration determination (`:1015-1037`) carries over to the next
iteration, and returning to the start repeats the same flow.

## The two bottlenecks, seen structurally

Placing the two paths' differences side by side, step by step, makes the
direction of the bottlenecks clear.

| Step | prefill (`src/main.cpp:150-553`) | decode (`src/main.cpp:720-1039`) |
|---|---|---|
| Input gather | block = token count (`:158`, `kernels.cu:42-53`) | block = active slot count (`:759`, `kernels.cu:358-369`) |
| Q/K/V GEMM | `n=prompt_len` (`:177-240`) | `n=num_active_slots` (`:763-842`) |
| attention | score matrix `prompt_len²`, dedicated `causalMask`·`softmax` kernels (`:301-371`, `:329`, `:331`) | `pagedAttention`, reads only cumulative K (`:878`; Chapter 10) |
| KV scatter | block-wise D2D (`:247-288`) | token-wise D2D (`:851-873`) |
| Logits | `n=prompt_len` GEMM (`:509-527`), D2H·argmax once per prompt (`:529`, `:533-543`) | D2H every iteration (`:996`) + per-slot CPU argmax (`:1000-1012`) |
| Call structure | once per prompt | repeats for the number of generated tokens |

Putting the two paths' sequences side by side makes this structure visible.

```
prefill (once per prompt)                    decode (every iteration)
embeddingGather ─ entire tokens               embeddingGatherDecode ─ active slots
  (:158)                                       (:759)
layer loop ×16 (:164-493)                     layer loop ×16 (:760-972)
  Q/K/V GEMM  n=prompt_len                     Q/K/V GEMM  n=num_active_slots
  (:177-240)                                   (:763-842)
  attention score GEMM (:301-327)             KV scatter token-wise (:851-873)
  causalMask (:329) softmax (:331)             block_table sync (:876)
  scores×V GEMM (:343-371)                     pagedAttention (:878)
  KV scatter block-wise (:247-288)             o_proj→residual→rmsNorm→MLP
  o_proj→residual→rmsNorm→MLP                  (:880-971)
  (:377-492)
logits GEMM  n=prompt_len (:509-527)          logits GEMM  n=num_active_slots
                                                (:976-994)
D2H (:529) → CPU argmax (:533-543)            D2H (:996) → per-slot argmax
                                                (:1000-1012)
```

The structural bottleneck difference boils down to three axes.

1. **Tokens handled at once.** prefill's parallelism width is `prompt_len`, and
   its work grows linearly (GEMM) and quadratically (attention) with the prompt
   length. decode handles one token per slot, so its GEMM width is tied to
   `num_active_slots`.
2. **The shape of attention work.** prefill builds a `prompt_len²` matrix and
   runs it through masking and softmax kernels, while decode uses paged
   attention, which reads only the tokens accumulated in the cache. (Kernel
   details are in Chapter 10.)
3. **Number of calls and copies.** prefill ends with one call per prompt and a
   single D2H argmax. decode repeats as many times as there are generated
   tokens, with a logits D2H plus CPU argmax attached to every iteration
   (`:996`, `:1000-1012`).

Which side is "slower" is not this chapter's claim. The three axes above only
state the structural difference in work and copy count; execution time and
throughput have no basis and are not claimed.

## Limitations

- When `prompt_len > 1024`, the `causalMask`/`softmax` kernels do not run and
  only print a message (`src/kernels.cu:241-244`, `:295-298`). The prompts in
  this commit are at most 17 tokens, so it is never reached, but it remains a
  limitation of the prefill path (`evidence/trace.md:228-231`).
- Because argmax is on the CPU, decode needs a logits D2H copy on every
  iteration. The source marks this point with a TODO (`src/main.cpp:531-532`,
  `:686`). The CPU argmax casts bf16 to float before comparing (`:1003-1010`).
- `embed_proj_cpu` is allocated as `MAX_BUFFER_SIZE*VOCAB_SIZE`, but prefill
  only copies `prompt_len*VOCAB_SIZE`, so the remaining rows may be leftover
  data from a previous slot (`src/main.cpp:681-682`, `:529`;
  `evidence/trace.md:240-242`).
- The KV cache reserves the entire 2 GiB regardless of usage
  (`src/main.cpp:32-37`, `:576-581`; Claim 5, `evidence/claims.md:57`).
- This chapter makes no performance claims. "Bottleneck" only describes the
  structural difference in work and copy count; execution time and throughput
  have no basis and are not used.

## Summary

This chapter read prefill and decode side by side as two forms of work. prefill
is a large job that processes the whole prompt at once: its parallelism width
is `prompt_len`, its attention grows with the square of that
(`src/main.cpp:301-371`), its KV scatter is block-wise (`:247-288`), and its
logits argmax runs once per prompt (`:533-543`). decode is a repetition of
small jobs that produce one token per slot each iteration: its GEMM width is
tied to `num_active_slots` (`:763-842`), its attention is paged attention that
reads only the cumulative K in the cache (`:878`; Chapter 10), its KV scatter
is token-wise (`:851-873`), and a logits D2H plus CPU argmax tags along every
iteration (`:996`, `:1000-1012`). The contrast along these three axes is the
picture of Chapter 5's cache structure viewed again from a runtime perspective.

The key point is what the next two chapters will lay on top of this picture,
confirmed in advance. The act of prefill "entering an idle slot immediately"
already sits in the rebuild step of the decode iteration (`:726-737`); the
policy that sets the batch size is taken over by Chapter 7's `BATCH_SIZE=2`,
and the cost of slot release and table re-synchronization by Chapter 8. After
that, Chapter 10 expands how the paged attention kernel "reads only cumulative
K" into an actual thread structure.
