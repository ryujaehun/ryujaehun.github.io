# tiny-vllm 1장 · tiny-vllm의 실행 경로와 빌드

이 시리즈는 `jmaczan/tiny-vllm` 저장소의 고정 커밋
`1896ff5c37a241050dbcd9527caf9dc1d3087a61`를 읽는다(`project.yaml:1-2`).
시리즈의 서사는 실행 가능한 프로그램과 가중치 포맷에서 시작해 토큰→로짓
순전파를 확립하고, 다수 요청을 위한 메모리·스케줄링을 거쳐 paged attention에서
끝난다(`guide.md:24-29`). 증거 규칙상 모든 구현 주장은 고정 커밋의 소스 경로와
줄 범위로 인용하며, README 설명은 보조 근거일 뿐 코드와 테스트가 충돌을
결정한다(`guide.md:11-16`).

1장은 그 서사의 첫걸음이다. 실행 파일이 어떤 소스로 빌드되는지, `main()`이 어떤
순서로 가중치 로딩 → prefill → decode → 종료에 이르는지를 개괄한다. 가중치
로딩 내부(2장), 토크나이저와 임베딩(3장), transformer block(4장), attention과
KV 캐시(5장), 배칭(7·8장), paged attention(10장)은 이 장에서 입구만 확인하고
소유 챕터로 넘긴다.

## 이 장이 다루는 파일과 범위

1장의 대상 파일은 `CMakeLists.txt`, `src/main.cpp`, `test.sh`다. 실행 파일
`tiny-vllm`은 `add_executable`이 `src/main.cpp`와 `src/kernels.cu` 두 소스로
구성한다(`CMakeLists.txt:49-52`). 즉 빌드 산출물의 진입점은 `main.cpp`, 커널
구현은 `kernels.cu`다.

이 장은 빌드 시스템의 상세를 주장하지 않는다. 시리즈의 근거 주장(Claim 1~10) 중
어느 것도 CMake 옵션, CUDA 아키텍처, 링크 라이브러리, `test.sh` 내부를 다루지
않으므로 그 내용은 서술하지 않는다. CUDA/HIP 이식 계층(`src/cuda_to_hip.h`)도
근거 주장이 없어 다루지 않는다. 학습, 분산 서빙, 저장소 외부의 성능 주장은
시리즈 범위 밖이다(`guide.md:7-9`, `guide.md:11-16`).

저장소 규모를 인벤토리로 확인하면 총 31개 항목이며, 그중 `role: build`는
`CMakeLists.txt` 1개, `role: test`는 `tests/test_softmax.cu` 1개, `role: docs`는
`README.md` 1개, 나머지는 source다(`inventory/files.jsonl`). 실제 소스의 줄 수는
`src/main.cpp` 1044줄, `src/kernels.cu` 528줄, `README.md` 1304줄,
`include/json.hpp` 25830줄이며, 이 수치는 인벤토리
(`inventory/files.jsonl:9`, `:14`, `:27`, `:29`)와 고정 커밋 소스의 줄 수가
일치한다.

두 값은 상수에서 바로 유도된다. `V_OFFSET = BLOCK_SIZE * KV_DIM * sizeof(bf16)
= 16*512*2 = 16384`이고 `BLOCK_BYTES = V_OFFSET * 2 = 32768`(K와 V 두 벡터)이다
(`src/main.cpp:33-34`). `MAX_BLOCKS_PER_SEQ = MAX_SEQ_LEN / BLOCK_SIZE = 2048/16
= 128`(`src/main.cpp:36`), `NUM_BLOCKS = KV_CACHE_SIZE_BYTES / BLOCK_BYTES =
2GiB / 32768 = 65536`(`src/main.cpp:37`)이다. KV 캐시는 이 65536개 블록을
`free_blocks` 스택이 소유하는 2GiB 고정 블록 풀이다(`src/main.cpp:576-578`).
상수와 캐시 구조의 상세는 5장에서 다시 읽는다.

이 값들이 전부 "임시로 하드코딩"되어 있다는 것은 소스가 TODO로 인지한다. 단,
TODO 문구는 상수마다 다르다. 정확히 인용하면:

- `N_LAYERS`: "hardcoded for llama 3.2 1B, just like any other value for now"
  (`src/main.cpp:15`) — 이 문구는 `main.cpp`의 상수 중 이곳 한 곳에만 있다.
- `MAX_SEQ_LEN`: "make it tunable" (`src/main.cpp:28`).
- `BATCH_SIZE`: "not even close to being good, it's just here to have batching"
  (`src/main.cpp:29`).
- `MAX_PROMPT_LEN`: "arbitrary, tunable" (`src/main.cpp:30`).
- `BLOCK_SIZE`: "tunable as well, defined the size of a single page in pagedattn"
  (`src/main.cpp:32`).
- `KV_CACHE_SIZE_BYTES`: "2GB" (`src/main.cpp:35`).
- `MAX_NEW_TOKENS_GENERATED`: "parameterize it with program arguments"
  (`src/main.cpp:12`).

가중치를 담는 `Weights` 구조체는 `src/main.cpp:64-77`에 정의되어 있고,
`embed_tokens`·`norm`·레이어별 `input_layernorm`/`mlp_*`/`w_k/w_o/w_q/w_v`
포인터를 담는다. 실제로 값을 채우는 과정은 2장의 주제다.

## main(): 실행 경로 9단계

진입점은 `main(int, char**)`(`src/main.cpp:555`)이다. `main`의 최상위 순서는
다음 9단계다.

```
main (:555)
 ├─ 1. cuBLAS 핸들 생성 (:557-563)
 ├─ 2. loadWeights(:566-569) ───────────────── 2장
 ├─ 3. init_rope_frequencies (:572)
 ├─ 4. KV 캐시·블록 테이블 초기화 (:574-581) ── Claim 5
 ├─ 5. 프롬프트 큐·배치 상태 초기화 (:584-601) ─ Claim 9
 ├─ 6. CUDA 버퍼 할당 (:615-693)
 ├─ 7. 초기 prefill 루프 (:695-708) ─────────── Claim 3·9
 ├─ 8. 무한 decode 루프 (:720-1039) ─────────── Claim 4
 └─ 9. 종료: "Ok bye!" (:1040-1044)
```

1. **cuBLAS 핸들 생성** — `cublasCreate`로 핸들을 만들고 실패 시 `return 1`
   (`src/main.cpp:557-563`).
2. **가중치 로드** — `loadWeights(weights)`가 실패하면 `return 1`
   (`src/main.cpp:566-569`). 함수는 먼저 `checkGPUStatus`로 디바이스 수를
   확인하고(`:81-84`, 디바이스 0개면 1 반환, `:44-48`), `model.safetensors`를
   열어 헤더를 파싱한 뒤 텐서 바이트 전체를 GPU로 올린다(`:79-147`). 내부는
   2장에서 다룬다.
3. **RoPE 주파수 초기화** — `init_rope_frequencies(HEAD_DIM, MAX_SEQ_LEN,
   500000, 32, 1, 4, 8192)`(`src/main.cpp:572`). Llama3 NTK 스케일링을 적용한
   sin/cos 테이블을 GPU에 준비한다(`src/kernels.cu:96-152`).
4. **KV 캐시·블록 테이블 초기화** — `kv_cache`를 2GiB로 할당하고
   (`src/main.cpp:576`), `free_blocks`를 0..65535로 채운 뒤(`:577-578`),
   CPU `block_table`을 전부 -1로 초기화하고 `block_table_gpu`를 할당한다
   (`:579-581`). 이 단계가 Claim 5의 고정 블록 풀과 CPU/GPU 블록 테이블을 만든다.
5. **프롬프트 큐·배치 상태 초기화** — 하드코딩된 토큰 ID 벡터 4개를 큐에
   푸시하고(`:584-594`, 자세한 내용은 다음 절), `is_slot_free` 2칸, 생성 상태
   벡터 3종을 초기화한다(`:596-601`). `BATCH_SIZE=2` 고정 슬롯 배칭의 시작점이
   Claim 9다.
6. **CUDA 버퍼 할당** — `gpu_input_tokens`부터 `k_proj_batched_buffer`까지
   prefill·decode가 쓰는 모든 디바이스 버퍼를 할당한다(`:615-693`).
   `prefill_attn_scores`는 `MAX_PROMPT_LEN * MAX_PROMPT_LEN * sizeof(bf16) *
   NUM_Q_HEADS` = 512×512×2×32바이트로 잡힌다(`:648`). 프롬프트 길이 상한 512와
   이 할당이 이어지는 커널 가드 절의 전제가 된다.
7. **초기 prefill 루프** — `for (slot = 0; slot < 2 && !queue.empty(); ++slot)`
   로 여유 슬롯에 `prefill`을 호출해 큐의 프롬프트 2개를 슬롯 0·1에 채운다
   (`src/main.cpp:695-708`). `prefill` 본문은 프롬프트 pop → `embeddingGather`
   → 레이어 루프 → 최종 rmsNorm → 로짓 GEMM → CPU argmax로 이어진다
   (`:150-553`; 진입점 인용 `:152-163`). Claim 3이 이 경로 전체를, Claim 9가
   "큐의 앞 2개만 채운다"를 뒷받침한다.
8. **무한 decode 루프** — `while(true)`(`:720`) 안에서 활성 슬롯을 재구성하고
   (`:722-737`), 여유 슬롯이 생기면 큐에서 다음 프롬프트를 prefill해 같은 반복의
   decode에 즉시 포함시킨다(Claim 4의 진입점 인용 `:722-737`, Claim 9). 활성
   슬롯이 없고 큐가 비면 `break`(`:739-746`), 큐가 남았으면 `continue`
   (`:745`). 레이어별 배치 GEMM → KV 산포 → `pagedAttention` → 로짓 → CPU argmax
   의 상세는 4~8장에서 다룬다.
9. **종료** — `"Ok bye!"`를 출력하고 `cublasDestroy`·`cudaDeviceSynchronize`
   후 `return 0`(`src/main.cpp:1040-1044`).

## 프롬프트 큐: 하드코딩된 시작 입력

네 프롬프트는 문자열이 아니라 토큰 ID 벡터로 하드코딩되어 있다
(`src/main.cpp:584-594`). 원소 수를 세면 각각 17·14·13·14다.

- PROMPT 0 — 길이 17 (`src/main.cpp:585`)
- PROMPT 1 — 길이 14 (`src/main.cpp:588`)
- PROMPT 2 — 길이 13 (`src/main.cpp:591`)
- PROMPT 3 — 길이 14 (`src/main.cpp:594`)

이 때문에 C++ 실행 경로에는 문자열→토큰 변환 단계가 존재하지 않는다.
`src/main.cpp`의 include는 `iostream`, `numeric`, `fstream`, `cuda_to_hip.h`,
`queue`, `json.hpp`, `kernels.cuh`뿐이고(`:1-8`) 소켓·서버 계층이 없어, 이
프로그램은 네트워크 입출력 없이 로컬에서 프롬프트를 소모하는 단일 실행 파일이다.
프롬프트가 하드코딩된 토큰 ID 벡터라는 사실은 3장에서 Claim 9(일부)로 다시
이어진다.

생성 상한과 종료 조건도 고정 상수에서 온다. `MAX_NEW_TOKENS_GENERATED = 20`
(`src/main.cpp:12`)은 선언만 되고 다른 곳에서 사용되지 않는다. 실제 종료 조건은
argmax 결과가 `END_OF_TEXT_TOKEN_ID`(128001) 또는 `EOT_ID_TOKEN_ID`(128009)이거나
`current_prompt_len == MAX_SEQ_LEN-1`일 때 슬롯을 해제하는 것뿐이다
(`src/main.cpp:26-27`, `:1015-1031`). 따라서 decode 루프는 큐가 빈 뒤에도 모든
슬롯이 종료 조건에 도달할 때까지 이어진다(`:720`, `:739-746`).

## 커널 런치 가드: 1024 스레드 상한

`src/kernels.cu`의 커널 래퍼 다섯 개는 스레드 수가 1024를 넘으면 실행을 생략하는
가드를 갖고 있다. 다만 가드 변수는 커널마다 다르고, 이 고정 설정에서는 어느
것도 발동하지 않는다. 정확한 조건을 하나씩 확인하자.

- **`rope`(prefill)** — `num_threads = proj_dim / 2`가 1024를 넘으면 생략
  (`src/kernels.cu:204-209`). 호출 인자는 `EMBEDDING_LENGTH=2048`(→1024)과
  `KV_DIM=512`(→256)이다(`src/main.cpp:244-245`). `proj_dim/2 ≤ 1024`이므로
  발동하지 않는다.
- **`ropeDecode`** — 같은 가드로 `proj_dim / 2 > 1024`면 생략
  (`src/kernels.cu:390-395`). 호출 인자는 마찬가지로 2048과 512다
  (`src/main.cpp:847-848`). 발동하지 않는다.
- **`causalMask`/`softmax`(prefill)** — `num_tokens > 1024`면 생략
  (`src/kernels.cu:241-245`, `:295-299`). 여기서 `num_tokens`는 `prompt_len`이고
  (`src/main.cpp:329`, `:331`), 프롬프트는 `MAX_PROMPT_LEN=512`로 상한이 걸려
  있고(`src/main.cpp:30`) `prefill_attn_scores`도 그 상한으로 할당되므로
  (`:648`) 1024를 넘지 않는다. 발동하지 않는다.
- **`softmaxDecode`** — `seq_len > 1024`면 생략(`src/kernels.cu:444-448`)하지만,
  이 함수는 선언(`src/kernels.cuh:25`)·정의(`src/kernels.cu:442-458`)만 되고
  어디서도 호출되지 않는다. decode의 softmax는 `pagedAttentionKernel` 내부의
  온라인 softmax가 담당한다(`src/kernels.cu:508-519`).

가드가 발동하는 경우의 동작은 "커널이 조용히 빠지는 것"이 아니라 "**메시지를
출력하고 커널을 실행하지 않는 것**"이다. 각 가드는 `std::cout`으로 예를 들어
"Can't launch more than 1024 threads on RTX 5090, RoPE kernel not launched"를
출력한 뒤 `return`한다(`src/kernels.cu:207`, `:243`, `:297`, `:393`, `:446`).

즉, 이 가드들은 현재 상수 구성에서 도달하지 않는 **잠재적 경로**다. `prompt_len`
이 `MAX_PROMPT_LEN`을 벗어나거나 `proj_dim`이 커지면 발동할 수 있지만, 고정 커밋
의 실행 경로에서는 한 번도 실행이 생략되지 않는다.

- `MAX_NEW_TOKENS_GENERATED`는 선언만 되고 루프 조건에 쓰이지 않는다. decode
  루프는 큐가 비고 모든 슬롯이 종료 조건에 도달할 때까지 이어진다
  (`src/main.cpp:720`, `:739-746`, `:1015`).
- 이 장의 줄 수·인벤토리 규모는 고정 커밋 소스 기준으로 확인했지만, 저장소
  실행으로 빌드 산출물을 확인한 것은 아니다.

## 정리

1장은 시리즈의 지도다. 실행 파일 `tiny-vllm`은 `src/main.cpp`와 `src/kernels.cu`
로 빌드되고(`CMakeLists.txt:49-52`), `main()`은 cuBLAS 생성 → 가중치 로드 →
RoPE 초기화 → KV 캐시·블록 테이블 → 프롬프트 큐 → 버퍼 할당 → 초기 prefill →
decode 루프 → 종료의 9단계로 실행된다(`src/main.cpp:555-1044`). 프롬프트는
토큰 ID 벡터 4개(17·14·13·14)로 하드코딩되어 있고(`:585-594`), 생성 상한 상수는
선언만 될 뿐 종료는 EOT/EOT_ID 또는 `MAX_SEQ_LEN-1`이 결정한다(`:1015`).

커널 래퍼의 1024 스레드 가드도 이 장에서 확인했다. 가드는 존재하지만
`rope`/`ropeDecode`는 `proj_dim/2 ≤ 1024`, `causalMask`/`softmax`는
`prompt_len ≤ MAX_PROMPT_LEN=512`라 발동하지 않고, `softmaxDecode`는 호출되지
않는다. 발동 시에도 "메시지를 출력하고 커널을 실행하지 않는" 동작이다. 다음 장
부터는 이 경로를 따라 가중치 로딩부터 하나씩 채워 나간다.
