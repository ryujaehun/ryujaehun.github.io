# tiny-vllm: CUDA로 읽는 LLM 추론 엔진

## 1장. tiny-vllm의 실행 경로와 빌드

이 시리즈는 `jmaczan/tiny-vllm`의 고정 커밋 `1896ff5c37a241050dbcd9527caf9dc1d3087a61`을
읽는다. 1장은 실행 가능한 프로그램이 어떻게 만들어지고, `main`이 어떤 순서로
실행되는지부터 확인한다. 이후 모델 로딩, 토큰 생성, 배칭, paged attention으로
이어지는 길의 지도를 그리는 장이다.

## 시리즈 범위와 증거 규칙

시리즈의 범위는 `guide.md`가 규정한다. 모델 로딩에서 단일 토큰 생성, 배칭,
paged KV-cache attention까지의 실행 경로를 다루며, 학습·분산 서빙·저장소 외부
성능 주장은 범위 밖이다 (`guide.md:5-9`).

모든 구현 주장은 고정된 소스 경로와 줄 범위로 뒷받침해야 한다. README 설명은
보조 증거일 뿐이며, 충돌 시 코드와 테스트가 우선한다 (`guide.md:11-16`). 이
규칙은 시리즈 전반에 적용된다 (Claim 12, `evidence/claims.md:149-158`).

## 독자 계약

독자는 C++ 기초, CUDA 스레드/블록 용어, 행렬곱 직관을 갖춘 것으로 전제한다.
각 장은 필요한 transformer 연산을 먼저 설명한 뒤 그 구현을 따라간다
(`guide.md:18-22`).

## 시리즈 아크와 챕터 구성

`guide.md`는 시리즈를 네 단계로 나눈다 (`guide.md:24-29`): ① 실행 가능한
프로그램과 가중치 포맷, ② 토큰→로짓 forward 경로, ③ 다수 요청을 위한
메모리·스케줄링, ④ 데이터 구조와 커널 설계가 만나는 paged attention. 이를
`series.yaml:3-33`의 10개 챕터에 배치하면 다음 지도가 된다.

```
① 실행 프로그램·가중치 포맷 ── 1장 실행 경로와 빌드 · 2장 Safetensors와 Llama 가중치
② 토큰→로짓 forward ──────── 3장 토크나이저·임베딩·첫 토큰 · 4장 transformer block
                             5장 attention과 KV cache · 6장 prefill과 decode
③ 메모리·스케줄링(배칭) ──── 7장 static batching · 8장 continuous batching과 scheduler
④ paged attention ────────── 9장 online softmax kernel · 10장 paged KV cache와 attention
```

이 장의 범위는 `CMakeLists.txt`, `src/main.cpp`, `test.sh`다 (`series.yaml:6`).

## 실행 파일과 소스 구성

빌드 산출물은 `tiny-vllm` 실행 파일이며 `src/main.cpp`와 `src/kernels.cu`를
소스로 한다 (`CMakeLists.txt:49-52`, `evidence/trace.md:10-11`). 저장소는 이
소스들 외에도 빌드·문서·테스트 역할을 구분한 31개 파일을 담고 있다
(`inventory/files.jsonl`, `evidence/recon.md:6`).

빌드/실행/검증 스크립트는 `build.sh`, `run.sh`, `test.sh`다. `recon.md:10`과
`inventory/files.jsonl:11`(build.sh), `:25`(run.sh), `:30`(test.sh)이 각 파일의
존재를 확인해 준다. 이 시리즈는 스크립트 내용을 실행하지 않았으므로
`test.sh`는 존재와 소속만 다룬다 (Claim 12).

## 빌드: CMake와 CUDA/HIP 분기

`CMakeLists.txt`는 `USE_HIP` 옵션에 따라 CUDA/HIP 언어, 아키텍처, 라이브러리를
갈라서 빌드한다 (`CMakeLists.txt:3`, `:10-16`, `:21-25`, `:32-38`, `:42-47`,

## `main()`의 실행 순서

C++ 진입점은 `int main(int argc, char *argv[])`다 (`src/main.cpp:555`). 실행
순서를 요약하면 다음과 같다 (`evidence/trace.md:12-23`).

1. cuBLAS 핸들 생성 — `cublasCreate(&cublas_handle)`, 실패 시 `1` 반환
   (`src/main.cpp:557-563`).
2. 가중치 로딩 — `loadWeights(weights)` (`src/main.cpp:566-569`).
3. RoPE 주파수 초기화 — `init_rope_frequencies(...)` (`src/main.cpp:572`).
4. paged attention용 상태 준비 — `kv_cache`, `free_blocks`, `block_table`,
   `block_table_gpu` (`src/main.cpp:574-581`).
5. 하드코딩된 프롬프트 4개를 큐에 삽입 (`src/main.cpp:583-594`).
6. 배치 상태 벡터와 대형 작업 버퍼 할당 (`src/main.cpp:596-693`).
7. 초기 prefill 루프 — 빈 슬롯에 프롬프트를 prefill (`src/main.cpp:695-708`).
8. 무한 decode 루프 (`src/main.cpp:720-1039`).
9. 정상 종료 — `"Ok bye!"` 출력 후 `cublasDestroy`, `cudaDeviceSynchronize`,
   `return 0` (`src/main.cpp:1040-1044`).

여기서 "서버 루프"라는 표현은 주의가 필요하다. 이 루프에는 외부 요청/응답
경로가 없다. `while (true)` 루프는 큐가 비고 모든 슬롯이 해제될 때만
종료된다 (`src/main.cpp:738-746`, `evidence/trace.md:212-213`, Claim 11 한계,
`evidence/claims.md:146-147`).

## 모델 차원 상수

프로그램은 모델 차원을 `constexpr` 컴파일 상수로 고정한다
(`src/main.cpp:12-38`, Claim 2, `evidence/claims.md:20-30`). 표 1은 그 값이다.

| 상수 | 값 |
|---|---|
| `N_LAYERS` | 16 |
| `EMBEDDING_LENGTH` | 2048 |
| `HIDDEN_DIM` | 8192 |
| `KV_DIM` | 512 |
| `HEAD_DIM` | 64 |
| `NUM_Q_HEADS` | 32 |
| `NUM_K_HEADS` | 8 |
| `NUM_V_HEADS` | 8 |
| `VOCAB_SIZE` | 128256 |

표 1: 모델 차원 상수 (`src/main.cpp:12-38`, Claim 2)

`NUM_Q_HEADS=32`와 `NUM_K_HEADS=NUM_V_HEADS=8`의 조합은 query head 32개가 KV
head 8개를 공유하는 GQA(Grouped-Query Attention) 구성이다. 정확히는 **KV head
하나당 query head가 네 개씩 묶여** 하나의 KV head를 공유한다. 이후 장에서 보게
될 `q_head_id / GQA_Q_TO_K_RATIO`(`src/kernels.cu:468`, Claim 8,
`evidence/claims.md:108-110`)도 query head를 네 개씩 묶어 KV head 하나를
고르는 방향으로 구현되어 있어, 이 상수 조합이 GQA를 전제함을 뒷받침한다.

이 값들 대부분은 "hardcoded for llama 3.2 1B" TODO가 붙어 있다
(`src/main.cpp:15`, Claim 2 한계, `evidence/claims.md:29-30`). 마찬가지로
`MAX_SEQ_LEN=2048`(`src/main.cpp:28`), `BATCH_SIZE=2`(`src/main.cpp:29`),
`MAX_PROMPT_LEN=512`(`src/main.cpp:30`), `BLOCK_SIZE=16`(`src/main.cpp:32`)도
TODO로 표시된 하드코딩 값이다 (`evidence/trace.md:202-204`).

## 커널 런치 가드: 1024 스레드 상한

prefill과 decode의 일부 커널은 필요한 스레드 수가 1024를 넘으면 실행을
건너뛰고 메시지만 출력한다. Claim 10이 명시한 다섯 커널은 `rope`
(`src/kernels.cu:202-209`), `causalMask`(`:239-245`), `softmax`(`:293-299`),
`ropeDecode`(`:388-395`), `softmaxDecode`(`:442-448`)다
(`evidence/claims.md:125-135`). 조건은 "필요 스레드 수 > 1024"이며, 그 이상은
커널별 필요 스레드 수와 입력 크기의 관계를 단정하지 않는다. `MAX_SEQ_LEN=2048`
이므로 시퀀스가 길어져 필요 스레드 수가 1024를 넘는 구간에서는 해당 연산이
조용히 계산에서 빠질 수 있다. 다만 장문에서의 실제 동작은 첨부 파일만으로
확정할 수 없다 (Claim 10 한계, `evidence/claims.md:135`).

## 토크나이저가 없는 경로

C++ 실행 경로에는 토크나이저 호출이 없다. 프롬프트는 길이 17·14·13·14의
하드코딩된 토큰 ID 벡터 4개다 (`src/main.cpp:583-594`, Claim 11,
`evidence/claims.md:137-147`). `MAX_NEW_TOKENS_GENERATED`는 선언만 되고
사용되지 않는다 (`src/main.cpp:12`).

생성 종료는 argmax 결과가 `END_OF_TEXT_TOKEN_ID` 또는 `EOT_ID_TOKEN_ID`이거나
`current_prompt_len == MAX_SEQ_LEN - 1`일 때만 일어난다 (`src/main.cpp:1015-1037`).
즉 최대 생성 토큰 수는 실제로 강제되지 않는다 (Claim 11 한계,
`evidence/claims.md:146-147`).

## 미첨부 헤더

`src/main.cpp:8`과 `src/kernels.cu:2`가 `"kernels.cuh"`를 include하고,
`src/main.cpp:4`와 `src/kernels.cu:1`이 `"cuda_to_hip.h"`를 include하지만 두
파일 모두 첨부되지 않았다. 이 시리즈는 첨부되지 않은 파일의 내용을 추정하지
않는다 (`evidence/trace.md:180-183`, `evidence/trace.md:5-6`).

## 한계

- 모델 차원과 배치·시퀀스 관련 값이 llama 3.2 1B 전용 하드코딩이며
  (`src/main.cpp:15`), 다른 모델에는 그대로 적용되지 않는다 (Claim 2 한계).
- CUDA/HIP 빌드 분기(`USE_HIP`)의 실행 영향은 첨부 증거로 확정할 수 없어 범위
  밖으로 둔다 (Claim 12).
- 커널 런치 가드는 필요 스레드 수가 1024를 넘는 구간의 연산을 조용히
  건너뛴다. 장문에서의 실제 동작은 확정할 수 없다 (Claim 10 한계).
- `MAX_NEW_TOKENS_GENERATED`는 강제되지 않는다. 루프는 큐 소진과 슬롯 해제가
  겹칠 때만 종료된다 (Claim 11 한계).
- `kernels.cuh`와 `cuda_to_hip.h`는 미첨부라 함수 선언과 CUDA/HIP 매크로의
  정본을 확인할 수 없다 (`evidence/trace.md:180-183`).
