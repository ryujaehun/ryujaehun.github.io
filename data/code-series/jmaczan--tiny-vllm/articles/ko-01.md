# 1장 — tiny-vllm의 실행 경로와 빌드

## 고정 대상

이 시리즈는 `jmaczan/tiny-vllm` 저장소의 커밋
`1896ff5c37a241050dbcd9527caf9dc1d3087a61`을 고정해 읽는다
(`project.yaml:1-2`). 시리즈 제목은 `series.yaml:1`과 같다. 이후의 모든 인용은
이 커밋을 기준으로 하며, 저장소를 실행해 관찰한 결과가 아니라 첨부된 소스와
문서만으로 서술한다 (`evidence/trace.md:5-6`). 실행하지 않았다는 사실은
`evidence/trace.md:5-6`에 근거한다.

## 시리즈 범위와 증거 규칙

`guide.md`는 이 시리즈의 범위를 규정한다. 다루는 경로는 모델 로딩 → 단일 토큰
생성 → 배칭 → paged KV-cache attention이며, 학습·분산 서빙·저장소 외부 성능
주장은 범위 밖이다 (`guide.md:5-9`). 증거 규칙도 분명하다. 모든 구현 주장은
고정 소스 경로와 줄 범위로 뒷받침해야 하고, 설명이 충돌하면 README보다 코드와
테스트가 우선한다 (`guide.md:11-16`). 이 장을 포함한 모든 장은 이 규칙을 따른다
(Claim 12, `evidence/claims.md:149-158`).

## 독자 계약

독자에게 요구되는 배경은 C++ 기초, CUDA 스레드/블록 용어, 행렬곱 직관이다
(`guide.md:18-22`). 각 장은 구현을 따라가기 전에 필요한 transformer 연산을 먼저
설명한다 (`guide.md:20-22`). 이 장은 그중에서도 가장 앞단인 빌드 산출물과
프로그램 진입 순서를 다룬다.

## 시리즈 아크

`guide.md`는 전체 서술 순서를 네 단계로 제시한다 (`guide.md:24-29`).

```
[1단계] 실행 가능한 프로그램 + 가중치 포맷   → 1장, 2장
[2단계] 토큰 → 로짓 forward 경로             → 3장 ~ 6장
[3단계] 다수 요청을 위한 메모리·스케줄링      → 7장, 8장
[4단계] 데이터 구조와 커널 설계가 만나는 지점  → 9장, 10장 (paged attention)
```

이 장은 1단계의 입구다. 실행 파일이 어떻게 만들어지고, `main()`이 어떤 순서로
무엇을 준비하는지만 확정하고, 각 단계의 내부 구현은 뒤 장으로 넘긴다.

## 이 장의 범위

이 장에서 다루는 파일은 `CMakeLists.txt`, `src/main.cpp`, `test.sh`다
(`series.yaml:6`). 다만 실행 경로를 설명하기 위해 첨부된
`evidence/trace.md`, `evidence/claims.md`, `evidence/recon.md`,
`inventory/files.jsonl`의 관찰을 함께 인용한다.

## 저장소 구성

`evidence/recon.md:6`과 `inventory/files.jsonl`에 따르면 저장소에는 총 31개
파일이 있다. 이 총계에는 이 장의 중심 소스인 `src/main.cpp`(1045줄)와
`src/kernels.cu`(529줄)가 포함되며, 나머지 29개가 그 밖의 파일이다
(`evidence/recon.md:6-8`, `inventory/files.jsonl` 31줄).

빌드/실행/검증 스크립트로는 `build.sh`, `run.sh`, `test.sh`, `check.sh`,
`full_test.sh`가 있고, 프로파일링용 `ncu.sh`, `nsys.sh`가 별도로 존재한다
(`evidence/recon.md:10`, `:16`, `:27`, `:32`). 이 장의 범위가 `test.sh` 하나로
한정된 것은 `series.yaml:6`의 지정에 따른 것이며, 나머지 스크립트는 저장소에
실재하되 이 장에서 동작을 분석하지는 않는다.

역할 구분도 함께 본다. `CMakeLists.txt`는 role `build`이고
(`inventory/files.jsonl:7`), `src/main.cpp`와 `src/kernels.cu`는 1차 소스다
(`evidence/recon.md:7-8`). 문서는 `README.md`(1305줄)와 `reference.txt`가
담당하지만, 증거 규칙상 README는 보조 증거로만 쓴다 (`guide.md:14-16`,
`evidence/recon.md:37`). `include/json.hpp`는 25,831줄의 벤더 헤더로, 2장의
가중치 파싱에서 다룰 대상이다 (`inventory/files.jsonl:14`).

## 빌드와 실행 파일

빌드 산출물은 `tiny-vllm` 실행 파일이며, 소스는 `src/main.cpp`와
`src/kernels.cu`다 (`CMakeLists.txt:49-52`, `evidence/trace.md:10-11`).
C++ 진입점은 `int main(int argc, char *argv[])`이다
(`src/main.cpp:555`, `evidence/trace.md:12`).

빌드는 CUDA/HIP 두 갈래를 가진다. `USE_HIP` 옵션에 따라 언어, 아키텍처,
라이브러리가 달라진다 (`CMakeLists.txt:3`, `:10-16`, `:21-25`, `:32-38`,
`:42-47`, `:54-60`, `:65-75`; `evidence/trace.md:171-174`). 다만 이 분기가 실제
실행 경로에 미치는 영향은 첨부 파일만으로 확정할 수 없다
(`evidence/trace.md:182-183`).

## `main()`의 실행 순서

`main()`이 최상위에서 수행하는 동작은 다음 9단계다
(`evidence/trace.md:12-23`, `:27-108`).

1. **cuBLAS 핸들 생성** — `cublasCreate(&cublas_handle)`를 호출하고, 실패하면
   `1`을 반환한다 (`src/main.cpp:557-563`).
2. **가중치 로딩** — `loadWeights(weights)`를 호출하고, 0이 아니면 `1`을
   반환한다 (`src/main.cpp:566-569`).
3. **RoPE 주파수 초기화** — `init_rope_frequencies(...)`로 위치별 cos/sin
   테이블을 준비한다 (`src/main.cpp:572`).
4. **paged KV-cache 상태 준비** — `kv_cache`, `free_blocks`, `block_table`,
   `block_table_gpu`를 만든다 (`src/main.cpp:574-581`).
5. **프롬프트 큐 구성** — 길이 17·14·13·14의 하드코딩된 토큰 ID 벡터 4개를
   큐에 넣는다 (`src/main.cpp:583-594`).
6. **배치 상태와 작업 버퍼 할당** — `is_slot_free`와 생성 이력, 활성 슬롯/토큰
   배열, 각종 작업 버퍼를 할당한다 (`src/main.cpp:596-693`).
7. **초기 prefill 루프** — 빈 슬롯마다 `prefill(...)`을 호출한다
   (`src/main.cpp:695-708`).
8. **decode 루프** — `while (true)`로 도는 무한 루프에서 활성 슬롯을 모아
   1토큰 forward를 수행한다 (`src/main.cpp:720-1039`).
9. **정상 종료** — `"Ok bye!"` 출력 후 `cublasDestroy`,
   `cudaDeviceSynchronize`, `return 0`을 수행한다 (`src/main.cpp:1040-1044`).

이 순서에서 7~9단계의 내부 연산(prefill/decode forward, attention, KV 캐시)은
각각 3장 이후에서 상세히 다룬다.

## 모델 차원은 컴파일 상수다

이 프로그램은 모델 형상을 런타임에 읽지 않고 `constexpr` 상수로 고정한다
(Claim 2, `evidence/claims.md:20-30`, `src/main.cpp:12-38`).

| 상수 | 값 | 비고 |
| --- | --- | --- |
| `N_LAYERS` | 16 | transformer 블록 수 |
| `EMBEDDING_LENGTH` | 2048 | 임베딩 차원 |
| `HIDDEN_DIM` | 8192 | MLP 은닉 차원 |
| `KV_DIM` | 512 | K/V 투영 차원 |
| `HEAD_DIM` | 64 | attention head 차원 |
| `NUM_Q_HEADS` | 32 | query head 수 |
| `NUM_K_HEADS` / `NUM_V_HEADS` | 8 / 8 | K/V head 수 (GQA) |
| `VOCAB_SIZE` | 128256 | 어휘 크기 |

GQA 관점에서 `NUM_Q_HEADS=32`와 `NUM_K_HEADS=8`의 비율은 4이고, 커널은
`q_head_id / GQA_Q_TO_K_RATIO`로 K/V head를 고른다 (Claim 8,
`evidence/claims.md:108-110`, `src/kernels.cu:468`). 다만 이 매핑의 상세는
10장에서 다룬다.

## 실행 경로에서 미리 짚을 제약

이 장에서 확정한 실행 순서 위에는 몇 가지 제약이 얹혀 있다. 뒤 장에서 반복해
참조하므로 여기서 모아 둔다.

- **커널 런치 가드.** prefill의 `rope`·`causalMask`·`softmax`와 decode의
  `ropeDecode`·`softmaxDecode`는 필요한 스레드 수가 1024를 넘으면 메시지만
  출력하고 커널을 실행하지 않는다 (`src/kernels.cu:202-209`, `:239-245`,
  `:293-299`, `:388-395`, `:442-448`). `MAX_SEQ_LEN=2048`이므로 1024를 넘는
  구간은 조용히 계산에서 빠진다 (Claim 10, `evidence/claims.md:125-135`,
  `src/main.cpp:28`).
- **토크나이저 부재.** C++ 경로에는 토크나이저 호출이 없고, 프롬프트는 길이
  17·14·13·14의 하드코딩된 토큰 ID 벡터 4개다 (`src/main.cpp:583-594`).
  `MAX_NEW_TOKENS_GENERATED`는 선언만 되고 사용되지 않는다
  (`src/main.cpp:12`). 종료는 argmax 결과가 `END_OF_TEXT_TOKEN_ID` 또는
  `EOT_ID_TOKEN_ID`이거나 `current_prompt_len == MAX_SEQ_LEN - 1`일 때만
  일어난다 (`src/main.cpp:1015-1037`; Claim 11,
  `evidence/claims.md:137-147`).
- **서버 루프 종료.** `while(true)` 루프는 큐가 비고 모든 슬롯이 해제될 때만
  빠져나간다 (`src/main.cpp:738-746`, `evidence/trace.md:212-213`). 첨부된
  소스에는 외부 요청/응답 경로가 보이지 않으며, 이는 위의 토크나이저 부재와
  하드코딩 프롬프트에서 이끌어낸 추론이다 (`evidence/trace.md:184-189`).
- **하드코딩 표시.** 여러 값에 "hardcoded for llama 3.2 1B" TODO가 붙어 있어
  다른 모델에는 그대로 적용되지 않는다 (`src/main.cpp:15`). `MAX_SEQ_LEN=2048`,
  `BATCH_SIZE=2`, `MAX_PROMPT_LEN=512`, `BLOCK_SIZE=16` 등도 TODO로 표시된
  하드코딩 값이다 (`src/main.cpp:28-32`, `evidence/trace.md:202-204`).

## 한계와 불확실성

- **미첨부 헤더.** `src/main.cpp`와 `src/kernels.cu`가 `"kernels.cuh"`와
  `"cuda_to_hip.h"`를 include하지만 두 파일은 첨부되지 않아, 함수 선언과
  CUDA/HIP 매크로가 실행 경로에 미치는 영향을 확정할 수 없다
  (`evidence/trace.md:180-183`).
- **실행하지 않음.** 이 장의 서술은 저장소를 실행해 검증한 것이 아니라 첨부된
  소스와 문서의 인용에 근거한다 (`evidence/trace.md:5-6`).
- **성능 주장 없음.** 커널 성능·프로파일링 수치는 이 시리즈의 범위 밖이다
  (Claim 12, `guide.md:5-9`).

## 이 장의 정리

- 저장소는 고정 커밋에서 `tiny-vllm` 실행 파일을 만들고, `main()`은
  cuBLAS 생성 → 가중치 로딩 → RoPE 초기화 → KV 상태 → 프롬프트 큐 → 버퍼 할당 →
  초기 prefill → decode 루프 → 종료 순으로 진행한다.
- 모델 형상은 `constexpr` 상수로 고정되며, GQA 비율은 4다.
- 커널 런치 가드, 토크나이저 부재, 하드코딩 값, 서버 루프 종료 조건은 이후 장의
  서술에 계속 영향을 준다.

다음 장에서는 2단계로 넘어가 `model.safetensors`를 단일 GPU 할당으로 적재하는
경로를 본다.
