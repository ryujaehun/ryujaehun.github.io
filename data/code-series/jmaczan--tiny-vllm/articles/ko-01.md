# tiny-vllm: CUDA로 읽는 LLM 추론 엔진 — 1장. 실행 경로와 빌드

이 시리즈는 `jmaczan/tiny-vllm`이라는 작은 C++/CUDA 구현을 처음부터 끝까지
읽어나간다. 목표는 LLM 추론 엔진이 "실제로 어떻게 돌아가는지"를 소스 코드의
실행 순서대로 따라가는 것이다. 1장에서는 그 여정의 출발점, 즉 실행 가능한
프로그램을 빌드하고, `main` 함수가 어떤 순서로 무대를 차리는지 살펴본다.
이 시리즈를 관통하는 네 가지 물음도 이 장에서 미리 깔아둔다.

## 범위: 무엇을 읽고 무엇을 읽지 않는가

이 시리즈는 저장소의 커밋 `1896ff5c37a241050dbcd9527caf9dc1d3087a61`에
고정되어 있다. 이후 변경된 코드는 읽지 않는다. 다루는 경로는 모델 로딩에서
시작해 단일 토큰 생성, 배칭, 그리고 paged KV-cache attention까지다. 반대로
학습, 분산 서빙, 그리고 이 저장소 바깥에서 주장되는 성능 수치는 모두 범위
밖이다. 이 시리즈가 "이 커밋의 구현"을 설명하는 문서라는 사실이 이 범위의
근거다 (Claim 12, `guide.md:3-29`).

시리즈 아크는 그림 1처럼 네 단계로 나뉜다. 1장은 그 지도의 가장 위층에 해당한다.

```
모델 로딩 ──▶ 단일 토큰 생성 ──▶ 배칭 ──▶ paged KV-cache attention
   │               │              │               │
   2장             3-6장          7-8장           9-10장
 Safetensors와   토크나이저·    static/         online softmax,
 가중치 적재     임베딩·첫토큰  continuous      paged attention
                prefill·decode  batching
```

그림 1. 시리즈 아크. 이 시리즈는 실행 가능한 프로그램과 가중치 포맷에서
시작해 토큰→로짓 forward 경로를 확립한 뒤, 다수 요청을 위한 메모리·스케줄링이
그 경로를 어떻게 바꾸는지 다룬다. 마지막은 데이터 구조와 커널 설계가 만나는
paged attention에서 끝난다 (Claim 12, `guide.md:3-29`).

### 증거 규칙

이 시리즈의 모든 구현 주장은 소스 경로와 줄 범위를 함께 제시한다. README의
설명은 보조 증거일 뿐이며, 충돌이 생기면 코드와 테스트가 README보다 우선한다.
독자가 "이 동작이 어디서 나왔나"를 다시 확인할 수 있게 하는 것이 이 규칙의
목적이다 (Claim 12, `guide.md:11-16`).

## 실행 프로그램과 빌드: tiny-vllm

빌드 산출물은 `tiny-vllm`이라는 단일 실행 파일이다. `src/main.cpp`와
`src/kernels.cu`가 그 소스이며, 전자는 호스트 쪽 실행 경로와 forward 로직을,
후자는 GPU에서 도는 커널들을 담는다 (`trace.md`, `CMakeLists.txt:49-52`).
저장소에는 실행을 도와주는 스크립트들(`test.sh`, `build.sh`, `run.sh` 등)도
있지만, 이 장에서는 실행 프로그램 자체가 어떻게 구성되는지가 핵심이다.

`src/kernels.cu`는 `kernels.cuh`와 `cuda_to_hip.h`를 include하지만 이 파일들은
첨부되지 않아 정확한 선언과 CUDA/HIP 매크로의 영향은 확정할 수 없다. 이
불확실성은 이 시리즈가 "실행 경로를 첨부된 소스만으로 추적한다"는 한계의
출발점이다 (`trace.md:180-183`).

## main()의 실행 경로

C++ 진입점은 `int main(int argc, char *argv[])`다 (`src/main.cpp:555`).
`main`은 아래 순서로 무대를 차린다 (`trace.md:13-23`).

1. **cuBLAS 핸들 생성** — `cublasCreate(&cublas_handle)`을 호출한다. 실패하면
   `1`을 반환한다 (`src/main.cpp:557-563`).
2. **가중치 로딩** — `loadWeights(weights)`로 모델 가중치를 GPU로 올린다
   (`src/main.cpp:566`). 이 함수의 내부는 2장에서 상세히 읽는다.
3. **RoPE 주파수 초기화** — `init_rope_frequencies(...)`로 위치 인코딩용
   cos/sin 테이블을 만든다 (`src/main.cpp:572`).
4. **paged attention용 상태 준비** — `kv_cache`, `free_blocks`,
   `block_table`, `block_table_gpu`를 할당하고 초기화한다
   (`src/main.cpp:574-581`).
5. **프롬프트 큐 구성** — 하드코딩된 토큰 ID 벡터 4개를 큐에 넣는다
   (`src/main.cpp:583-594`). 토크나이저는 이 경로에 없다.
6. **배치 상태와 작업 버퍼 할당** — 슬롯 상태 벡터와 대형 작업 버퍼들을
   순서대로 할당한다 (`src/main.cpp:596-693`).
7. **prefill 루프** — 빈 슬롯에 큐에서 꺼낸 프롬프트를 prefill한다
   (`src/main.cpp:695-708`).
8. **decode 루프** — `while (true)` 무한 루프에서 배치를 계속 돌린다
   (`src/main.cpp:720-1039`).
9. **정상 종료** — 큐가 소진되고 모든 슬롯이 해제되면 루프를 빠져나와
   `"Ok bye!"`를 출력하고 핸들을 정리한 뒤 `return 0`으로 끝낸다
   (`src/main.cpp:1040-1044`).

이 목록을 보면 이 실행 프로그램이 "요청을 받아 토큰을 생성하고 응답하는 서버"
의 모양을 하고 있음을 알 수 있다. 3장부터는 이 경로의 정면인 forward가 어떻게
토큰을 로짓으로 바꾸는지, 7·8장은 여러 요청을 어떻게 한 번에 처리하는지를
다룬다.

## 컴파일 상수로 고정된 모델 차원

이 프로그램의 모델 형상은 실행 중에 읽어오지 않는다. 표 1과 같이 전부
`constexpr`로 컴파일 타임에 고정되어 있다 (Claim 2, `src/main.cpp:12-38`).

| 상수 | 값 | 의미 |
|---|---|---|
| `N_LAYERS` | 16 | transformer 레이어 수 |
| `EMBEDDING_LENGTH` | 2048 | 토큰 임베딩 차원 |
| `HIDDEN_DIM` | 8192 | MLP hidden 차원 |
| `KV_DIM` | 512 | K/V 프로젝션 출력 차원 |
| `HEAD_DIM` | 64 | attention 헤드당 차원 |
| `NUM_Q_HEADS` | 32 | Q 헤드 수 |
| `NUM_K_HEADS` / `NUM_V_HEADS` | 8 / 8 | K·V 헤드 수 |
| `VOCAB_SIZE` | 128256 | 어휘 크기(로짓 차원) |

표 1. 실행 프로그램의 모델 차원. `src/main.cpp:12-38`에서 컴파일 상수로
하드코딩된다 (Claim 2).

`NUM_Q_HEADS`(32)와 `NUM_K_HEADS`(8)의 4:1 비율에서 GQA(Grouped Query
Attention) 구조를 미리 짐작할 수 있다. 이 값들이 실제로 attention과
paged attention 커널에서 어떻게 쓰이는지는 5장과 10장에서 확인한다. 여기서
중요한 점은 "이 실행 파일은 이 형상에서만 동작하도록 만들어진 것"이라는
사실이다. 여러 값에 "hardcoded for llama 3.2 1B" TODO가 붙어 있어 다른 모델에는
그대로 적용되지 않는다 (Claim 2 한계, `src/main.cpp:15`).

## 프롬프트는 하드코딩된 토큰 벡터다

이 C++ 실행 경로에는 토크나이저가 없다. 문자열을 입력받아 토큰 ID로 바꾸는
단계가 존재하지 않으며, 프롬프트는 길이 17·14·13·14의 토큰 ID 벡터 4개가
직접 코드에 박혀 있다 (Claim 11, `src/main.cpp:583-594`). 즉 "사용자 문장 →
토큰" 변환은 전혀 일어나지 않고, 이미 토큰화가 끝난 벡터를 큐에 넣는 것에서
시작한다.

또 하나 주목할 점은 `MAX_NEW_TOKENS_GENERATED`라는 상수가 선언만 되고 실제로
사용되지 않는다는 것이다. 생성할 새 토큰 수의 상한을 강제하지 않는 셈이다
(Claim 11, `src/main.cpp:12`). 실제 종료 조건은 argmax 결과가
`END_OF_TEXT_TOKEN_ID` 또는 `EOT_ID_TOKEN_ID`이거나, 시퀀스 길이가
`MAX_SEQ_LEN - 1`에 도달했을 때뿐이다 (Claim 11, `src/main.cpp:1015-1037`).

그리고 서버 루프는 개별 프롬프트가 끝나는 것과 별개로, 큐가 비고 모든 슬롯이
해제되어야만 종료된다 (Claim 11, `src/main.cpp:738-746`). 즉 이 프로그램은
하드코딩된 네 프롬프트가 모두 끝나기 전에는 계속 돌아간다.

## 커널 런치 가드: 1024 스레드 한계

GPU 커널들을 부르는 쪽에는 공통된 가드가 있다. 필요한 스레드 수가 1024를
넘으면 커널을 실행하지 않고 메시지만 출력하고 지나간다 (Claim 10,
`src/kernels.cu:202-209`). 그런데 `MAX_SEQ_LEN`은 2048로 하드코딩되어 있다
(`src/main.cpp:28`). 이 두 사실을 합치면 장문에서는 1024를 넘어가는 구간이
"조용히" 계산에서 빠진다 (Claim 10). 에러로 멈추는 것이 아니라, 그냥
실행되지 않는다.

이 가드가 걸리는 커널은 prefill의 `rope`, `causalMask`, `softmax`와 decode의
`ropeDecode`, `softmaxDecode`다 (Claim 10, `src/kernels.cu:239-245`,
`src/kernels.cu:293-299`, `src/kernels.cu:388-395`, `src/kernels.cu:442-448`).
각 커널이 어떤 역할을 하는지는 4·5·9장에서 구체적으로 읽을 것이다. 1장에서
기억할 것은 "이 프로그램은 길이 제한을 넘는 입력을 오류로 처리하지 않는다"는
성격이다.

## 한계와 열린 질문

이 장에서 확인한 실행 경로는 아래의 한계를 안고 있다.

- **1024 스레드 가드의 조용한 생략**: 1024를 넘는 구간은 커널이 실행되지
  않는다. `MAX_SEQ_LEN`이 2048이므로 장문에서 실제로 어떻게 동작하는지는
  첨부된 소스만으로는 확정할 수 없다 (Claim 10, `src/kernels.cu:202-209`,
  `src/main.cpp:28`).
- **최대 생성 토큰 수가 강제되지 않음**: `MAX_NEW_TOKENS_GENERATED`는 선언만
  되고 미사용이다. 종료는 EOT 토큰 또는 `MAX_SEQ_LEN`에만 달려 있다
  (Claim 11, `src/main.cpp:12`, `src/main.cpp:1015-1037`).
- **토크나이저 부재**: 입력은 하드코딩된 토큰 ID 벡터 4개뿐이다
  (Claim 11, `src/main.cpp:583-594`).
- **첨부되지 않은 헤더**: `kernels.cuh`와 `cuda_to_hip.h`가 include되지만
  첨부되지 않아 함수 선언과 CUDA/HIP 매크로의 정본을 확인할 수 없다
  (`trace.md:180-183`).
- **빌드 상세 일부는 미검증**: CUDA/HIP 빌드 분기 등은 이 시리즈의 증거
  문서에 인용되지 않은 부분으로, 존재만 언급하고 동작을 주장하지 않는다.
- **가중치 로딩·forward 내부는 이후 장으로**: `loadWeights`의 내부는 2장,
  각 커널의 내부는 4장 이후에서 상세화한다.
