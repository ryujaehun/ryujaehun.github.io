# 1장 — tiny-vllm의 실행 경로와 빌드

이 시리즈는 `jmaczan/tiny-vllm`의 고정 커밋
`1896ff5c37a241050dbcd9527caf9dc1d3087a61`을 읽는다 (`project.yaml:1-2`,
`guide.md:5`). 이 장은 실행 가능한 프로그램이 어떻게 빌드되고, `main`이 어떤
순서로 추론 경로에 진입하는지를 따라간다. 구체적인 가중치 포맷과 forward 커널은
뒤 장에서 다루고, 여기서는 "무엇이 어떤 상수로 고정되어 있고, 어디서 시작해
어디서 끝나는가"를 확정한다.

## 이 장의 범위와 근거 규칙

1장의 대상 파일은 `CMakeLists.txt`, `src/main.cpp`, `test.sh` 세 개다
(`series.yaml:6`). 시리즈 전체의 범위와 증거 규칙은 `guide.md`가 규정한다
(`guide.md:3-29`). 구현 주장은 소스 경로와 줄 범위로 뒷받침하고, README 설명과
코드가 충돌하면 코드와 테스트를 우선한다 (`guide.md:11-16`).

이 장의 근거 계층은 다음과 같다. 핵심 구현 주장은 `evidence/claims.md`의 주장
번호(Claim 2, Claim 10, Claim 11, Claim 12)에 직접 연결한다. `evidence/trace.md`,
`evidence/recon.md`, `inventory/files.jsonl`은 저장소 구조·파일 수·스크립트 구성
같은 보강 사실에, `evidence/trace.md`는 진입점과 실행 순서 요약에 보조 근거로
사용한다. 이는 `briefs.md:4-5`가 요구하는 "claims.md 중심" 근거 규칙을 지키기
위한 것이다.

시리즈의 서술 범위 자체가 하나의 주장이다. **Claim 12**에 따르면 시리즈는 고정
커밋의 모델 로딩 → 단일 토큰 생성 → 배칭 → paged KV-cache attention 경로를
다루며, 학습·분산 서빙·저장소 외부 성능 주장은 범위 밖이다 (Confidence: High,
`guide.md:3-29`). 아래 4단계 아크가 이 범위를 챕터에 배치한 지도다.

```
[1] 실행 경로와 빌드            → 1장
        │
        ▼
[2] 가중치 로딩 → 토큰 생성      → 2·3장 (safetensors, 임베딩, 첫 토큰)
        │
        ▼
[3] transformer block·attention → 4·5장 (RMSNorm, RoPE, GEMM, KV cache)
        │
        ▼
[4] 배칭과 paged attention      → 6~10장 (prefill/decode, 배칭, paged KV cache)
```

## 저장소와 빌드 산출물

인벤토리는 총 31개 파일을 나열하며, 그중 `src/main.cpp`(1045줄)와
`src/kernels.cu`(529줄)가 실행 경로의 1차 소스다 (`recon.md:6-8`,
`inventory/files.jsonl`). 나머지 29개에는 문서·스크립트·Python 참조
구현·테스트가 섞여 있다. `README.md`는 1305줄의 문서이고
(`inventory/files.jsonl:9`), `include/json.hpp`는 25,831줄의 벤더 헤더다
(`inventory/files.jsonl:14`). 둘 다 실행 경로를 읽는 1차 대상은 아니다.

빌드는 `CMakeLists.txt`가 담당하며 역할은 `build`다 (`inventory/files.jsonl:7`).
빌드 산출물은 `tiny-vllm` 실행 파일이고, 그 소스는 `src/main.cpp`와
`src/kernels.cu`다 (`CMakeLists.txt:49-52`, `evidence/trace.md:10-11`).
저장소에는 빌드·실행·검증을 감싸는 스크립트도 있다: `build.sh`, `run.sh`,
`test.sh`, `check.sh`, `full_test.sh`와 프로파일링용 `ncu.sh`, `nsys.sh`다
(`inventory/files.jsonl:11-13`, `inventory/files.jsonl:15-16`,
`inventory/files.jsonl:25`, `inventory/files.jsonl:30`, `recon.md:10`,
`recon.md:16`, `recon.md:27`, `recon.md:32`). 다만 이 장은 `test.sh`를
1장 범위로만 언급하고, 각 스크립트의 내부 동작은 다루지 않는다.

## 모델 차원은 컴파일 상수다

**Claim 2**는 실행 프로그램의 모델 차원이 `constexpr`로 컴파일 시점에
고정된다고 말한다 (Confidence: High, `src/main.cpp:12-38`). 값은
`src/main.cpp:12-38`에서 그대로 읽는다.

| 상수 | 값 | 의미 |
| --- | --- | --- |
| `N_LAYERS` | 16 | transformer 레이어 수 |
| `EMBEDDING_LENGTH` | 2048 | 임베딩/은닉 차원 |
| `HIDDEN_DIM` | 8192 | MLP 중간 차원 |
| `KV_DIM` | 512 | K/V head 전체 차원 |
| `HEAD_DIM` | 64 | head당 차원 |
| `NUM_Q_HEADS` | 32 | Q head 수 |
| `NUM_K_HEADS` | 8 | K head 수 (GQA) |
| `NUM_V_HEADS` | 8 | V head 수 (GQA) |
| `VOCAB_SIZE` | 128256 | 어휘 크기 |

여기에 더해 `MAX_SEQ_LEN=2048`, `BATCH_SIZE=2`, `MAX_PROMPT_LEN=512`,
`BLOCK_SIZE=16` 같은 실행 상수도 하드코딩되어 있다 (`src/main.cpp:28-32`,
`src/main.cpp:29`). `Weights` 구조체는 임베딩·최종 norm과 레이어별
input/post-attn layernorm, q/k/v/o, gate/up/down 포인터 배열을 가진다
(`src/main.cpp:64-77`). 여러 값에는 "hardcoded for llama 3.2 1B" TODO가 붙어
있어 다른 모델에는 그대로 적용되지 않는다 (`src/main.cpp:15`). 즉 이 장의
상수 표는 특정 모델 형상에 맞춘 컴파일 상수이지, 범용 설정이 아니다.

## 실행 경로: main()의 9단계

C++ 진입점은 `int main(int argc, char *argv[])`이며 (`src/main.cpp:555`,
`evidence/trace.md:12`), 아래 9단계는 `evidence/trace.md`의 10단계 Ordered
steps를 바탕으로 decode 진입·forward·종료 판정을 묶고 정상 종료를 더해 요약한
것이다 (`evidence/trace.md:22-23`, `:27-108`).

1. **cuBLAS 초기화와 가중치 로딩.** `cublasCreate(&cublas_handle)` 성공을
   확인하고 (`src/main.cpp:557-563`), `loadWeights(weights)`를 호출한다
   (`src/main.cpp:566`).
2. **RoPE 주파수 사전 계산.** `init_rope_frequencies(...)`가 llama3 방식
   스케일링을 적용한 cos/sin 테이블을 만든다 (`src/main.cpp:572`).
3. **paged KV-cache 할당자 준비.** `kv_cache`를 할당하고 `free_blocks`를
   0..`NUM_BLOCKS-1`로 채우며 `block_table`을 전부 `-1`로 초기화한다
   (`src/main.cpp:574-581`).
4. **프롬프트 큐 구성.** 길이 17·14·13·14의 토큰 ID 벡터 4개를 큐에 넣는다
   (`src/main.cpp:583-594`).
5. **배치 상태와 작업 버퍼 할당.** 슬롯 상태와 토큰·임베딩·hidden·Q/K/V·
   attention·MLP·logit 버퍼를 순서대로 할당한다 (`src/main.cpp:596-693`).
6. **초기 prefill 루프.** 빈 슬롯마다 큐의 프롬프트를 `prefill`한다
   (`src/main.cpp:695-708`).
7. **prefill forward.** 토큰→로짓 전체 forward를 CPU argmax까지 수행한다
   (`src/main.cpp:149-553`).
8. **decode 루프.** `while (true)` 안에서 활성 슬롯을 모아 슬롯별 1토큰
   forward를 수행한다 (`src/main.cpp:720-1039`).
9. **정상 종료.** 큐가 비고 모든 슬롯이 해제되면 루프를 빠져나와
   `"Ok bye!"`를 출력하고 `cublasDestroy`, `cudaDeviceSynchronize` 후
   `return 0`을 수행한다 (`src/main.cpp:738-746`, `src/main.cpp:1040-1044`).

이 순서에서 6~8단계는 모두 큐에서 시작해 토큰을 만들어 내는 경로이고,
1~5단계는 그 경로를 실행하기 위한 준비다. 이 장은 준비 단계의 뼈대까지만
확정하고, prefill/decode 내부 연산은 각각 3~6장에서 상세히 다룬다.

## 토크나이저가 없고 생성 한도가 강제되지 않는다

**Claim 11**은 C++ 경로에 토크나이저 호출이 없으며 프롬프트가 하드코딩된 토큰
ID 벡터 4개라고 말한다 (Confidence: High, `src/main.cpp:583-594`,
`src/main.cpp:738-746`). 문자열을 토큰으로 바꾸는 단계가 코드에 없으므로,
4단계에서 넣는 길이 17·14·13·14의 벡터가 곧 모델 입력이다
(`src/main.cpp:583-594`).

`MAX_NEW_TOKENS_GENERATED`는 선언만 되고 사용되지 않는다 (`src/main.cpp:12`).
실제 종료는 argmax 결과가 `END_OF_TEXT_TOKEN_ID` 또는 `EOT_ID_TOKEN_ID`이거나
`current_prompt_len == MAX_SEQ_LEN - 1`일 때만 일어난다
(`src/main.cpp:1015-1037`). 서버 루프는 큐가 비고 모든 슬롯이 해제될 때만
종료된다 (`src/main.cpp:738-746`). 따라서 "토큰 N개를 생성하면 멈춘다"는
상한은 코드에 존재하지 않는다.

## 커널 런치 가드: 1024 스레드 초과 시 조용히 건너뛴다

**Claim 10**은 prefill의 `rope`·`causalMask`·`softmax`와 decode의
`ropeDecode`·`softmaxDecode`가 필요한 스레드 수가 1024를 넘으면 메시지만
출력하고 커널을 실행하지 않는다고 말한다 (Confidence: High,
`src/kernels.cu:202-209`, `src/kernels.cu:239-245`, `src/kernels.cu:293-299`,
`src/kernels.cu:388-395`, `src/kernels.cu:442-448`). `MAX_SEQ_LEN=2048`이므로
시퀀스가 1024를 넘는 구간은 해당 커널이 조용히 계산에서 빠진다
(`src/main.cpp:28`). 이 가드는 이 장에서 실행 경로의 일부로만 언급하고,
장문에서 실제로 어떤 값이 나오는지는 첨부 파일만으로 확정하지 않는다
(Claim 10 Limitation).

## 이 장이 다루지 않는 것

- 학습, 분산 서빙, 저장소 외부 성능 주장은 시리즈 범위 밖이다
  (Claim 12, `guide.md:3-9`).
- 가중치 로딩·포맷 내부는 2장, forward 커널 상세는 4장 이후에서 다룬다.
- CUDA/HIP 빌드 분기는 브리프가 배제한 "claims.md에 인용되지 않은 빌드
  상세"에 해당하므로 이 장에서 서술하지 않는다 (`briefs.md:36`).

## 한계와 불확실성

- `src/main.cpp`와 `src/kernels.cu`는 `"kernels.cuh"`와 `"cuda_to_hip.h"`를
  include한다 (`evidence/trace.md:180-183`). 두 헤더는 저장소에 실재하지만
  (`inventory/files.jsonl:26`, `inventory/files.jsonl:28`), 이 시리즈 작성에는
  첨부(제공)되지 않아 함수 선언과 CUDA/HIP 매크로의 정본을 확인할 수 없다.
  "저장소에 없다"가 아니라 "작성 근거로 제공되지 않았다"는 뜻이다.
- 이 문서는 저장소를 실행하지 않았고, 첨부되지 않은 파일의 내용은 추정하지
  않는다 (`evidence/trace.md:5-6`). 따라서 성능 수치나 실제 출력 토큰은
  주장하지 않는다.
- 첨부된 소스에는 외부 요청을 받는 서버·네트워크 경로가 보이지 않는다.
  실행은 하드코딩된 프롬프트 큐로 시작하고 (`src/main.cpp:583-594`), 루프는
  큐가 비고 모든 슬롯이 해제될 때 종료된다 (`src/main.cpp:738-746`,
  `evidence/trace.md:160-161`, `evidence/trace.md:212-213`).
- `MAX_NEW_TOKENS_GENERATED`가 강제되지 않으므로 종료는 EOT 토큰 또는
  `MAX_SEQ_LEN`에만 달려 있다 (`src/main.cpp:12`, `src/main.cpp:1015`).
- prefill의 `softmax`·`causalMask`·`rope`는 1024 스레드 초과 시 조용히
  건너뛴다 (`src/kernels.cu:202-209`, `src/kernels.cu:239-245`,
  `src/kernels.cu:293-299`). `MAX_SEQ_LEN=2048`이므로 장문에서의 동작은 첨부
  파일만으로 확정할 수 없다.
- `prefill_attn_scores`는 `MAX_PROMPT_LEN * MAX_PROMPT_LEN * NUM_Q_HEADS`로
  할당되어 프롬프트 길이가 `MAX_PROMPT_LEN`(512)을 넘는 경우를 다루지 않는다
  (`src/main.cpp:30`, `src/main.cpp:647-648`).
- 모델 경로가 `"model.safetensors"`로 하드코딩되어 있어 (`src/main.cpp:87`)
  실행 환경에 따라 로딩이 실패할 수 있다.
- 블록 할당자는 `NUM_BLOCKS`(=65536)를 전제로 하지만 실제 수요 대비 고갈
  검사가 첨부 코드에는 없다 (`src/main.cpp:37`, `src/main.cpp:577`).
- paged attention, batching, softmax 커널에 대한 검증 경로는 첨부 파일에
  없다. 커널 단위 테스트는 `tests/test_softmax.cu` 하나뿐이며
  (`inventory/files.jsonl:31`), 이 장은 그 동작을 주장하지 않는다.

## 정리

- 실행 파일은 `tiny-vllm`이고 소스는 `src/main.cpp`·`src/kernels.cu`다
  (`CMakeLists.txt:49-52`).
- 모델 차원과 실행 상수는 컴파일 상수로 고정된다 (Claim 2,
  `src/main.cpp:12-38`).
- `main`은 cuBLAS 생성 → 가중치 로딩 → RoPE 초기화 → KV 상태 → 프롬프트 큐 →
  버퍼 할당 → 초기 prefill → decode 루프 → 종료 순으로 진행한다
  (`src/main.cpp:555-1044`).
- 토크나이저가 없고, 생성 토큰 상한이 강제되지 않는다 (Claim 11,
  `src/main.cpp:583-594`, `src/main.cpp:1015-1037`).
- 여러 커널은 1024 스레드를 넘으면 조용히 실행되지 않는다 (Claim 10,
  `src/kernels.cu:202-209` 등).
