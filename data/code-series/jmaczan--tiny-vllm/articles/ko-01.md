# 1장 — tiny-vllm의 실행 경로와 빌드

이 시리즈는 `jmaczan/tiny-vllm`의 커밋
`1896ff5c37a241050dbcd9527caf9dc1d3087a61`을 고정해 읽는다. 1장의 목표는
코드 한 줄 한 줄을 뜯기 전에, 이 저장소가 어떤 프로그램이고 어떤 순서로
실행되는지 지도를 그리는 것이다. 모델 로딩에서 시작해 단일 토큰 생성, 배칭,
paged KV-cache attention으로 이어지는 나머지 장들의 좌표를 여기서 정한다.

## 이 장과 시리즈의 범위

시리즈의 범위는 고정 커밋의 **모델 로딩 → 단일 토큰 생성 → 배칭 → paged
KV-cache attention** 경로다. 학습, 분산 서빙, 저장소 밖의 성능 주장은 범위
밖으로 둔다. 모든 구현 서술은 소스 경로와 줄 범위를 함께 인용해야 하고,
설명이 충돌하면 README보다 코드와 테스트를 우선한다 (`guide.md:3-16`,
Claim 12).

독자 계약도 분명하다. C++ 기초, CUDA 스레드/블록 용어, 행렬곱 직관을
전제로 하고, 각 장은 구현을 따라가기 전에 필요한 transformer 연산을 먼저
설명한다 (`guide.md:18-22`). 이 장은 그중에서도 실행 순서와 빌드 골격에
집중한다.

## 시리즈 아크 지도

`guide.md:24-29`의 아크는 네 단계다. 각 단계는 이 시리즈의 챕터 묶음과
다음처럼 대응한다 (`series.yaml:3-33`, `briefs.md`).

| 단계 | 다루는 내용 | 챕터 |
| --- | --- | --- |
| 1 | 실행 프로그램과 가중치 포맷 | 1장, 2장 |
| 2 | 토큰 → 로짓 forward 경로 | 3장–6장 |
| 3 | 다수 요청을 위한 메모리·스케줄링 | 7장–8장 |
| 4 | 데이터 구조와 커널 설계가 만나는 paged attention | 9장–10장 |

1장은 이 지도의 입구다. 프로그램이 어떻게 빌드되고 `main()`이 어떤 순서로
움직이는지만 확정하고, 가중치 포맷 내부는 2장으로, forward 커널 상세는
4장 이후로 넘긴다.

## 빌드 산출물과 실행 스크립트

빌드 타깃은 `tiny-vllm` 실행 파일이고, 소스는 `src/main.cpp`와
`src/kernels.cu`다 (`CMakeLists.txt:49-52`, `trace.md:10-11`). 저장소에는
빌드와 실행을 감싸는 스크립트가 함께 있다. `build.sh`, `run.sh`,
`test.sh`의 존재는 `recon.md:10`과 `inventory/files.jsonl`에서 확인된다
(각각 `inventory/files.jsonl:11`, `:25`, `:30`). 이 장은 `test.sh`까지를
범위로 두지만, 스크립트 내부 동작은 이 문서들이 인용하지 않으므로 존재
이상은 주장하지 않는다 (`series.yaml:6`).

빌드 분기 하나는 짚고 넘어갈 만하다. `CMakeLists.txt`는 `USE_HIP` 옵션에
따라 CUDA/HIP 언어, 아키텍처, 라이브러리를 가른다. 이 분기는
`trace.md:171-174`가 `CMakeLists.txt:3`, `10-16`, `21-25`, `32-38`,
`42-47`, `54-60`, `65-75`로 명시 인용한다. 다만 `claims.md`에는 별도
주장으로 등록되지 않았으므로, 이 장에서도 분기의 존재와 인용 위치만
확인하고 실행 경로에 미치는 영향은 다루지 않는다.

## `main()`의 실행 순서

진입점은 `int main(int argc, char *argv[])`다 (`src/main.cpp:555`).
`trace.md:12-23`이 정리한 순서를 그대로 따라가면 다음과 같다.

1. **cuBLAS 초기화** — `cublasCreate(&cublas_handle)`을 호출하고, 반환이
   `CUBLAS_STATUS_SUCCESS`가 아니면 `1`을 반환한다
   (`src/main.cpp:557-563`).
2. **가중치 로딩** — `loadWeights(weights)`를 호출하고, 결과가 0이 아니면
   `1`을 반환한다 (`src/main.cpp:566-569`). 로딩 내부는 2장에서 다룬다.
3. **RoPE 주파수 초기화** — `init_rope_frequencies(...)`로 위치별 cos/sin
   테이블을 준비한다 (`src/main.cpp:572`). prefill/decode 두 경로가 서로
   다른 RoPE를 쓰는 문제는 4장에서 자세히 본다.
4. **paged KV-cache 준비** — `kv_cache`, `free_blocks`, `block_table`,
   `block_table_gpu`를 할당·초기화한다 (`src/main.cpp:574-581`).
5. **프롬프트 큐 구성** — 하드코딩된 토큰 ID 벡터 4개를 `queue`에 넣는다
   (`src/main.cpp:583-594`).
6. **배치 상태와 작업 버퍼 할당** — `is_slot_free`, `generated_tokens`,
   `last_generated_tokens`, `current_prompt_len`과 GPU 인덱스/시퀀스 길이
   버퍼, 각종 작업 버퍼를 준비한다 (`src/main.cpp:596-693`).
7. **초기 prefill 루프** — 각 슬롯이 비어 있으면 `prefill(...)`을 호출해
   최대 `BATCH_SIZE`개의 프롬프트를 소비한다 (`src/main.cpp:695-708`).
8. **decode 루프** — `while (true)` 루프가 활성 슬롯을 모아 슬롯별 forward를
   수행한다 (`src/main.cpp:720-1039`).
9. **정상 종료** — `"Ok bye!"`를 출력하고 `cublasDestroy`,
   `cudaDeviceSynchronize` 후 `return 0`한다 (`src/main.cpp:1040-1044`).

여기서 주의할 점 하나. 8번 루프를 이 문서는 "서버 루프"라고 부르지만
(`trace.md:212-213`), 코드에는 외부 요청을 수신하고 응답을 돌려주는 경로가
없다. 이 루프는 내부 큐에 들어 있는 하드코딩된 프롬프트를 소비하는 **배치
실행 루프**이며, 큐가 비고 모든 슬롯이 해제될 때만 종료된다
(`src/main.cpp:738-746`). 요청/응답 서버라는 서술은 첨부 증거로 뒷받침되지
않는다.

## 컴파일 상수로 고정된 모델 차원

이 프로그램은 모델 차원을 런타임 인자가 아니라 `constexpr` 상수로 박아
넣는다 (`src/main.cpp:12-38`, Claim 2). 표 1이 그 값이다.

**표 1. `src/main.cpp:12-38`의 모델 차원 상수**

| 상수 | 값 | 비고 |
| --- | --- | --- |
| `N_LAYERS` | 16 | transformer 레이어 수 |
| `EMBEDDING_LENGTH` | 2048 | 임베딩/hidden 차원 |
| `HIDDEN_DIM` | 8192 | MLP 중간 차원 |
| `KV_DIM` | 512 | KV head 전체 차원 |
| `HEAD_DIM` | 64 | attention head 차원 |
| `NUM_Q_HEADS` | 32 | query head 수 |
| `NUM_K_HEADS` / `NUM_V_HEADS` | 8 / 8 | KV head 수 |
| `VOCAB_SIZE` | 128256 | 어휘 크기 |

`NUM_Q_HEADS`와 `NUM_K_HEADS`가 32 대 8이므로 query head 하나당 KV head가
네 개씩 묶이는 GQA(Grouped-Query Attention) 구성으로 **짐작**할 수 있다.
이 비율과 GQA 매핑 자체는 4장·10장에서 `pagedAttentionKernel`의
`q_head_id / GQA_Q_TO_K_RATIO` 선택(`src/kernels.cu:468`, Claim 8)을 보며
확인한다.

값 자체는 Llama 3.2 1B에 맞춰져 있다. `src/main.cpp:15`에 "hardcoded for
llama 3.2 1B" TODO가 붙어 있어 다른 모델에는 그대로 적용되지 않는다
(`src/main.cpp:15`, Claim 2 한계). `BATCH_SIZE=2`, `MAX_SEQ_LEN`,
`BLOCK_SIZE`, `MAX_PROMPT_LEN` 같은 값도 TODO가 달린 하드코딩 상수다
(`src/main.cpp:28-32`).

## 커널 런치 가드: 1024 스레드 상한

이 구현에는 커널을 실행하기 전에 필요한 스레드 수를 확인하고, 1024를
넘으면 메시지만 출력한 뒤 커널 실행을 건너뛰는 가드가 있다
(`src/kernels.cu:202-209` 등, Claim 10). 가드가 걸린 커널은 다섯 개다.

| 커널 | 위치 |
| --- | --- |
| prefill `rope` | `src/kernels.cu:202-209` |
| prefill `causalMask` | `src/kernels.cu:239-245` |
| prefill `softmax` | `src/kernels.cu:293-299` |
| decode `ropeDecode` | `src/kernels.cu:388-395` |
| decode `softmaxDecode` | `src/kernels.cu:442-448` |

문제는 `MAX_SEQ_LEN=2048`이라는 점이다 (`src/main.cpp:28`). 스레드 수가
시퀀스 길이에 비례하는 커널에서 1024를 넘는 구간은 오류 없이 계산에서
빠진다. 즉 장문 입력에서 이 가드가 조용히 발동할 수 있다. 장문에서 실제로
어떤 결과가 나오는지는 첨부 파일만으로 확정할 수 없으므로, 이 시리즈는
"해당 구간이 계산에서 빠진다"는 사실까지만 주장한다 (Claim 10 한계).

## 토크나이저 부재와 하드코딩 프롬프트

C++ 실행 경로에는 토크나이저 호출이 없다. `main()`이 큐에 넣는 것은 길이
17, 14, 13, 14의 토큰 ID 벡터 4개다 (`src/main.cpp:583-594`, Claim 11).
사용자 입력이나 문자열을 토큰으로 바꾸는 단계는 이 경로에 존재하지 않는다.
`python/tokenizer.py`는 참조 구현으로 저장소에 있지만, `claims.md`에 동작
인용이 없으므로 이 시리즈는 그 동작을 주장하지 않는다.

또 하나의 한계는 생성 길이다. `MAX_NEW_TOKENS_GENERATED`는
`src/main.cpp:12`에 선언만 되고 사용되지 않는다 (Claim 11). 생성이 끝나는
조건은 argmax 결과가 `END_OF_TEXT_TOKEN_ID` 또는 `EOT_ID_TOKEN_ID`이거나
`current_prompt_len == MAX_SEQ_LEN - 1`일 때뿐이다 (`src/main.cpp:1015-1037`).
그래서 "최대 N토큰"이라는 상한은 실제로는 강제되지 않는다.

## 미첨부 헤더라는 빈칸

`src/main.cpp:8`과 `src/kernels.cu:2`는 `"kernels.cuh"`를, `src/main.cpp:4`와
`src/kernels.cu:1`은 `"cuda_to_hip.h"`를 include한다. 두 헤더는 첨부되지
않았으므로 함수 선언·시그니처의 정본과 CUDA/HIP 매크로가 실행 경로에
미치는 영향을 확정할 수 없다 (`trace.md:180-183`). 이 시리즈가 커널
호출을 설명할 때는 호출 지점의 인자와 주변 버퍼 상태를 근거로 삼고,
헤더에 숨은 매크로 동작은 추정하지 않는다.

## 이 장의 한계

- **가중치 로딩 내부는 다루지 않는다.** `loadWeights`의 호출 위치
  (`src/main.cpp:566`)와 성공/실패 분기(`src/main.cpp:566-569`)만 확인했고,
  safetensors 파싱과 단일 할당 매핑은 2장에서 다룬다.
- **forward 커널 상세는 다루지 않는다.** RMSNorm, RoPE, GEMM, attention은
  4장 이후의 주제다.
- **빌드 스크립트 내부 동작은 주장하지 않는다.** `test.sh`, `build.sh`,
  `run.sh`의 존재만 `recon.md:10`, `inventory/files.jsonl`로 확인했다.
- **`USE_HIP` 분기의 실행 영향은 확정하지 않는다.** `trace.md:171-174`가
  인용 위치를 제시하지만, 이 장은 존재와 인용 범위만 기록한다.
- **장문에서 커널 런치 가드의 실제 결과는 확정하지 않는다.** 1024 스레드
  초과 구간이 계산에서 빠진다는 사실까지만 말할 수 있다 (Claim 10 한계).
