# tiny-vllm 9장 · online softmax CUDA kernel

8장은 decode의 레이어 루프가 KV 산포(`src/main.cpp:851-873`) → `block_table_gpu`
전체 재동기화(`:876`) → `pagedAttention`(`:878`) 순서로 돌고, 그 재동기화가 결국
어느 커널을 위해 존재하는지를 읽었다. 이 장은 그 커널이 attention 스코어에
적용하는 정규화를 본다. tiny-vllm의 decode는 별도 softmax 커널을 쓰지 않는다.
`softmaxDecode`(`src/kernels.cu:442-458`)는 정의되어 있지만 main.cpp에서
호출되지 않고(`evidence/trace.md:216-219`), decode의 softmax는
`pagedAttentionKernel` 내부의 온라인 갱신(`:508-519`)이 담당한다. 그래서 이 장의
제목이 가리키는 "online softmax CUDA kernel"은 사실 paged attention 커널 안에
내장된 상태 갱신 규칙이다.

이 장의 주 소유 주장은 Claim 8이다. FlashAttention식 온라인 softmax가
`current_max`/`d`/`acc`를 갱신하고 `acc/d`를 출력하며(`src/kernels.cu:509-519`,
`:522`), 각 스레드가 Q의 1차원을 담당해 warp 내 트리 합으로 dot product를
구한다(`:469`, `:489-493`, `:494-507`). 시리즈의 증거 규칙대로 모든 주장은 고정
커밋의 소스 경로와 줄 범위로 인용한다(`guide.md:11-16`).

## 이 장이 다루는 파일과 범위

`series.yaml` 9장의 대상 파일은 `src/kernels.cu`와 `tests/test_softmax.cu`다
(`series.yaml:29-30`). 사용할 주장과 근거는 다음과 같다.

- **Claim 8 (주 소유)** — FlashAttention식 온라인 softmax가 `current_max`/`d`/
  `acc`를 갱신하고 `acc/d`를 출력한다. 근거: `src/kernels.cu:509-519`, `:522`
  (`evidence/claims.md:82-88`).
- **Claim 8 (참조)** — 각 스레드가 Q의 1차원을 담당하고, `__shfl_down_sync`
  트리 합으로 dot product를 구한다. 근거: `src/kernels.cu:489-493`,
  `:494-507`.
- **Claim 2 Limitation (참조)** — 커널 단위 테스트는 `tests/test_softmax.cu`
  하나뿐이다. 근거: `evidence/claims.md:24`, `evidence/recon.md:12`.

범위 경계를 명확히 둔다. 이 장은 온라인 softmax의 갱신 규칙과 dot product를
구하는 warp 트리 결합에 집중한다. 이 갱신이 실행되는 커널의 그리드 배치·블록
테이블 순회·K/V 읽기는 온라인 softmax가 "어디서" 도는지의 맥락으로 필요한
만큼만 짚고, 그 **전체 구조와 상세는 10장**으로 넘긴다. `tests/test_softmax.cu`
의 구체 내용·수치는 Claim 1~10에 근거가 없으므로 서술하지 않는다
(`briefs.md:203`). prefill의 별도 `softmax` 커널은 4·5장 문맥에서 대조로만
언급한다.

## decode의 softmax는 paged attention 커널 안에 있다

decode가 온라인 softmax를 쓰는 지점을 먼저 확정한다. decode의 레이어 루프는
8장에서 본 순서 그대로다: KV 산포(`src/main.cpp:851-873`)가 `block_table`을
바꾸면 `block_table_gpu` 전체를 H2D로 재복사하고(`:876`) `pagedAttention`을
호출한다(`:878`; `src/kernels.cu:525-527`).

이 호출이 이 장의 대상 커널을 실행한다. 래퍼는 그리드 `(num_active_slots,
NUM_Q_HEADS)`, 블록 `HEAD_DIM=64`로 커널을 띄운다(`src/kernels.cu:527`). 즉
블록 하나가 (활성 슬롯 하나, Q 헤드 하나) 쌍을 맡고, 그 안의 64개 스레드가 각각
해당 Q의 한 차원을 담당한다(`:469`). 이 실행 구조 전체의 상세 — `gpu_active_slots`
매핑, 블록 테이블을 따른 물리 블록 순회, K·V 주소 계산 — 는 10장의 몫이다.
여기서는 커널이 스코어를 내는 데 쓰는 두 메커니즘, 곧 온라인 갱신과 warp 트리
합만 떼어 읽는다.

## 온라인 softmax: running max와 재스케일 (Claim 8)

커널은 스코어 한 점마다 세 개의 실행 상태를 갱신한다. 초기값은 소스에
`current_max = -INFINITY`, `acc = 0`, `d = 0`으로 박혀 있다(`src/kernels.cu:474-476`).
`d`가 denominator, `acc`가 가중합이라는 주석도 같은 줄에 있다(`:476`). 소스
주석은 이 갱신이 FlashAttention 강의 노트를 따른다고 남겨 두었다(`:473`).

각 토큰의 dot product `p`에 대해 커널은 다음 규칙을 적용한다
(`src/kernels.cu:508-519`, `:522`).

```
상태: current_max, d, acc          dot product: p  (이 장 아래의 warp 트리 합으로 산출)

  new_max   = max(current_max, p)                (:510-514)
  cf        = expf(current_max - new_max)        (:515)
  current_max = new_max                          (:516)
  exp_score = expf(p - current_max)              (:517)
  d   = d * cf + exp_score                       (:518)
  acc = acc * cf + exp_score * v                 (:519)

출력: output = acc / d                           (:522)
```

이 규칙이 "온라인"인 이유가 `cf`(correction factor)에 담겨 있다. 누적된 `d`와
`acc`는 항상 "지금까지 본 최댓값"을 기준으로 환산된 값이다. 그런데 새 토큰의
스코어 `p`가 최댓값을 넘어서면(`:511`) 기준점이 옛 최댓값 `current_max`에서 새
최댓값 `new_max`로 바뀐다. 이때 옛 기준으로 계산된 누적분은
`expf(current_max - new_max)`를 곱해 새 기준으로 다시 맞춰야 한다(`:515`). 같은
재스케일이 `d`(`:518`)와 `acc`(`:519`) 양쪽에 곱해지므로, 두 누적값은 항상 같은
기준점을 공유하고 마지막에 `acc / d`로 나누는 것만 남는다(`:522`). 이
재스케일링은 중간에 행 전체를 들고 있지 않으므로 가능하다 — 커널 소스에는 스코어 행을
저장하는 배열이 없고 세 스칼라 상태 변수만 갱신한다(`:474-476`).

이 갱신이 각 토큰에 대해 일어나는 흐름을 그리면 다음과 같다.

```
running max·denominator·가중합        토큰을 하나씩 읽으며
────────────────────────────────     ┌──────────────────────────────┐
current_max  d        acc            │ p = q·k / sqrt(64)           │
   -∞         0        0             │   ─ warp 트리 합 (:489-507)  │
   │  토큰 0: p0                     │ p가 current_max를 넘으면     │
   │  new_max=max(·,p0)              │   옛 누적분에 cf=exp(old-new) │
   │  d, acc ← ×cf 후 p0 반영        │   를 곱해 새 기준으로 환산    │
   ▼                                 │   (:515, :518-519)           │
current_max  d        acc            └──────────────────────────────┘
   p0       1+…      p0·v0 + …
   │  토큰 1: p1
   ▼
   …  토큰이 늘어날 때마다 같은 한 줄 갱신

출력: acc / d                        (:522)
```

스코어 행 전체를 저장한 뒤 두 번 도는 방식(prefill의 `softmax` 커널)과 달리,
이 갱신은 토큰을 한 번만 읽고 그 자리에서 가중합을 만든다. 단, "온라인"이 decode
반복 사이의 점진적 계산을 뜻하는 것은 아니다. 이 커널은 매 호출마다 지금까지
누적된 K/V 토큰 전체를 다시 순회한다(`:478-482`). 온라인인 것은 "스코어 행을
메모리에 두지 않고 스칼라 상태로 스트리밍한다"는 점이다.

## warp 트리 합: Q·K dot product가 한 스레드로 모이는 경로 (Claim 8)

온라인 갱신의 입력인 `p`는 커널 안에서 한 스레드에 모인다. 각 스레드는 Q의 한
차원을 담당하므로(`src/kernels.cu:469`) 토큰의 K에서 같은 차원을 읽어(`:484`)
한 요소 곱 `qk = q * k`를 만든다(`:486`). 이 64개(블록 크기) 요소 곱을 전부 합쳐
dot product를 만들어야 하는데, 커널은 이것을 warp 내 셔플로 해결한다.

블록은 `HEAD_DIM=64`개 스레드, 곧 warp 두 개로 이루어진다. warp 안에서는
`__shfl_down_sync`가 오프셋 16/8/4/2/1 다섯 단계로 트리 합을 수행해, 각 warp의
lane 0에 그 warp의 32요소 합이 모인다(`:489-493`). 두 warp 절반의 합을 잇는
것은 shared 배열 `dot_products[2]`다(`:463`). thread 0가 warp 0의 합을, thread
32가 warp 1의 합을 각각 써넣고(`:494-501`), thread 0가 두 값을 더한 뒤
`SQRT_HEAD_DIM`(= 8, `sqrt(64)`)로 나눠 스케일을 적용한다(`:503-506`). 모든
스레드는 이 값을 shared에서 다시 읽어(`:508`) 다음 온라인 갱신의 `p`로 쓴다.
`1/sqrt(64)` 스케일은 5장이 prefill에서 `attn_alpha = 1/8`로 본 상수
(`src/main.cpp:649`)와 같은 계수다(`src/kernels.cu:12`, `:505`).

```
블록: HEAD_DIM=64 스레드 = warp 2개        각 스레드 = Q의 1차원 (:469)
                                              q = q_proj[…+q_head_id*64+thread_id]
warp 0 (threads 0..31)                      warp 1 (threads 32..63)
  qk = q·k  (토큰마다, :486)                  qk = q·k  (:486)
  │  __shfl_down_sync 16/8/4/2/1 (:489-493)  │  __shfl_down_sync 16/8/4/2/1
  ▼ lane 0 = 32요소 합                        ▼ lane 0 = 32요소 합
thread 0 → dot_products[0] (:496)           thread 32 → dot_products[1] (:500)
        │                                       │
        └──────────────┬────────────────────────┘
                       ▼
   thread 0: (dot_products[0] + dot_products[1]) / 8   (:503-506)
                       ▼
   모든 스레드가 dot_products[0]을 읽어 p로 사용    (:508)
```

이 결합이 Claim 8의 dot product 절반이다(`evidence/claims.md:82-88`). 스레드가
"Q 차원 하나"를 담당한다는 것(`:469`)과 다섯 단계 셔플 트리(`:489-493`), shared
배열로 두 warp을 잇는 것(`:494-507`)이 한 흐름을 이룬다.

## prefill의 softmax와 decode의 온라인 갱신

같은 시리즈에서 4·5장이 본 prefill 쪽은 방식이 다르다. prefill은
`causalMask`(`src/kernels.cu:224-237`) 후 별도 `softmax` 커널(`:257-290`)을
돌린다. 이 커널은 스코어 행을 한 번에 읽고 트리 결합으로 최댓값과 합을 함께
계산한 뒤(`:270-287`) `exp(x - m) / d`를 저장한다(`:289`). 행이 메모리에 이미
있으므로(reduce한 뒤 그 자리에 결과를 덮어씀) 온라인 재스케일이 필요 없다
(`evidence/trace.md:112-113`).

decode는 이 경로를 쓰지 않는다. 별도 마스크 커널도, 별도 softmax 커널도 없다.
마스킹은 "이미 캐시에 쓴 K/V 토큰만 순회한다"는 방식으로 대신되고(`:478-482`),
softmax는 이 장에서 읽은 온라인 갱신이 담당한다. 이 마스킹·순회 구조의 상세는
10장에서 다룬다.

인벤토리상 유일한 커널 테스트는 `tests/test_softmax.cu` 하나뿐이다
(`evidence/recon.md:12`). 구체 내용·수치는 근거 범위 밖이다(`briefs.md:203`). 저장소는

온라인 softmax 수치 정확성을 이 글은 주장하지 않는다.

## 한계

- **Claim 8의 warp 결합 가정** — 현재 `HEAD_DIM=64` launch는 정확히 두 개의 완전한
  warp를 만든다(`src/kernels.cu:525-527`). `dot_products[2]`와 `WARP_FULL_MASK`
  구조가 이 구성에 고정 의존하므로(`:463`, `:489-507`), `HEAD_DIM` 변경 시 환원
  구조를 함께 재검토하고 재컴파일해야 한다.
- **softmaxDecode 미사용** — `softmaxDecode`(`src/kernels.cu:442-458`)는
  정의만 있고 호출처가 없다. decode의 softmax는 전적으로 paged attention 커널
  내부 온라인 갱신이 담당한다(`evidence/trace.md:216-219`).
- **수치 검증 부재** — `pagedAttentionKernel`의 수치는 이 시리즈 근거로 검증되지
  않았다.
- **성능 주장 없음** — 온라인 갱신이 "빠르다"거나 메모리 사용이 얼마나
  줄어드는지는 Claim 1~10에 근거가 없어 쓰지 않는다. 이 장이 서술하는 것은 상태
  갱신 규칙과 그 규칙이 스코어 행을 저장하지 않는 구조적 사실뿐이다.

## 정리

이 장은 paged attention 커널이 스코어를 정규화하는 두 메커니즘을 읽었다. 첫째,
온라인 softmax다. 커널은 토큰을 하나씩 읽으며 `current_max`/`d`/`acc`를
갱신하고(`src/kernels.cu:508-519`), 새 최댓값이 나타날 때마다
`expf(current_max - new_max)`로 기존 누적분을 새 기준에 맞춘 뒤(`:515`)
마지막에 `acc / d`를 출력한다(`:522`). 스코어 행 전체를 저장할 필요가 없다는
것이 이 규칙의 핵심이다. 둘째, warp 트리 합이다. 각 스레드가 Q의 1차원을
담당하고(`:469`), `__shfl_down_sync` 다섯 단계(`:489-493`)와 크기 2의 shared
배열(`:494-507`)이 64개 요소의 dot product를 한 스레드에 모은다.

이 두 메커니즘은 prefill의 `softmax` 커널과 달리 스코어 행을 만들지 않는다.
그래서 decode는 KV 캐시에서 블록 테이블을 따라 토큰을 읽는 그 자리에서 바로
정규화된 attention 출력을 얻을 수 있다. 그 "토큰을 읽는 경로" — 물리 블록
순회, `gpu_active_slots` 매핑, 누적 K만 읽어 마스킹을 대신하는 구조 — 가 다음
장의 주제다.
