# 5. 토큰 하나만 만드는 decode 경로

이 글의 모든 경로와 줄 번호는 고정 revision
`e25bf1994efa90bc98b721ba7c527402f86fbeaf` 의 트리를 가리킨다. 표기는
`파일:시작-끝` 형식이며, 실행 결과가 아니라 소스 인용이다. 이 시리즈는 NVIDIA
GPU 와 CUDA 툴체인이 없는 환경에서 작성되어 어떤 커널도 실행하지 않았다. 따라서
아래의 모든 주장은 소스 인용이며, 커널 실행 시간·처리량·메모리 사용량은
측정하지 않는다.

## 이 장의 질문

decode 는 왜 prefill 과 다른 커널 변형을 쓰는가. 코드 범위는
`src/kernels.cu`, `src/main.cpp`, `python/decode_test.py` 세 파일이다. 이 장의
최소 근거는 코드 인용 4건, 테스트 1건, 실행 0건이다.

이 장은 3편 `prefill-path` 에 의존한다. decode 는 prefill 과의 대비로만 성립하기
때문이다. 이 장은 decode 스텝이라는 용어와 "prefill 대비 무엇이 다른가"를
소유한다. KV 저장 구조와 block table 인덱싱은 6편, cuBLAS 의 전치 플래그와
열 우선 레이아웃은 4편, 슬롯·큐 수명주기와 종료 조건은 7편, 가중치 적재와 버퍼
크기·별칭은 2편, 빌드 경계와 진입점은 1편이 맡는다. 여기서는 decode 가 어떤
커널을 왜 다르게 부르는지, 그리고 새 토큰의 K/V 를 어떻게 캐시에 붙이는지에
집중한다.

`python/decode_test.py` 는 이 장의 코드 범위에 포함된 테스트 자산이지만, 이
장의 근거에는 그 동작을 다루는 주장이 없다. 이 장은 그 파일을 실행하지 않으며,
decode 계열 검증도 정적 인용으로만 구성한다.

## decode 는 prefill 다음에 어디서 도는가

prefill 은 `prefill` 함수(`src/main.cpp:150-553`)에서 큐의 프롬프트
`prompt_len` 개 토큰을 한 번에 처리한다. 반면 decode 는 `main` 의
`while (true)` 루프(`src/main.cpp:720-1039`) 안에서 매 반복 활성 슬롯마다 토큰
하나씩만 계산한다. 이 루프가 이 장이 따라가는 실행 경로다.

매 반복의 앞머리는 슬롯 상태를 재구성한다. `active_slots` 와 `active_tokens` 를
비우고(`src/main.cpp:722-723`), 슬롯을 돌며 비어 있는 슬롯을 큐의 다음
프롬프트로 채운다(`src/main.cpp:724-737`). 이 재채움은 `prefill` 을 다시
호출하는 지점이며(`src/main.cpp:726-734`), 슬롯·큐 수명주기는 7편이 소유한다.
그다음 활성 슬롯 목록과 각 슬롯의 마지막 토큰, 그리고
`current_prompt_len[slot] + 1` 로 계산한 시퀀스 길이를 디바이스로 올린다
(`src/main.cpp:749-757`). `+1` 은 방금 생성한 토큰의 KV 가 이미 캐시에
기록되었기 때문에 길이에 포함된다는 뜻이다.

이 장의 초점은 이 루프가 prefill 과 **다른 커널**을 부른다는 사실이다. decode
전용으로 정의된 커널은 `src/kernels.cu` 에 따로 있다.

## decode 계열 커널과 prefill 대비

`src/kernels.cu` 의 decode 구간(`src/kernels.cu:346-523`)에는 prefill
구간(`src/kernels.cu:26-344`)과 별개로 네 함수가 있다.

- `embeddingGatherKernelDecode`(`src/kernels.cu:347-356`)와 래퍼
  `embeddingGatherDecode`(`src/kernels.cu:358-369`)
- `ropeKernelDecode`(`src/kernels.cu:371-384`)와 래퍼
  `ropeDecode`(`src/kernels.cu:388-405`)
- `softmaxKernelDecode`(`src/kernels.cu:408-439`)와 래퍼
  `softmaxDecode`(`src/kernels.cu:442-458`)
- `pagedAttentionKernel`(`src/kernels.cu:461-523`)과 래퍼
  `pagedAttention`(`src/kernels.cu:525-527`)

이 중 앞 세 개가 prefill 대응 커널을 대체하는 변형이고, `pagedAttentionKernel`
은 prefill 에 대응 커널이 없는 decode 전용 어텐션이다. 네 함수 모두
`src/kernels.cuh:23-28` 에 선언되어 있다.

다음 표는 두 계열이 무엇에서 갈리는지 정리한다.

답한다.

- decode 계열 커널은 시퀀스 길이 1(슬롯당 토큰 1개)을 전제로 인덱싱을
  단순화한다. `embeddingGatherKernelDecode` 는 `blockIdx.x` 를 슬롯으로 삼고
  (`src/kernels.cu:349`), `softmaxKernelDecode` 는 `MAX_SEQ_LEN` 스트라이드
  레이아웃을 가정한다(`src/kernels.cu:413`).
- `ropeKernelDecode` 는 전체 위치가 아니라 현재 위치 하나만 회전시킨다

아래에서 각 변형을 순서대로 본다.

## 임베딩: `blockIdx.x` 가 토큰이 아니라 슬롯

prefill 의 `embeddingGatherKernel` 은 블록 하나가 토큰 하나를 맡는다. 블록
인덱스로 입력 토큰 ID 를 고르고, `workIndex = blockIdx.x * 2048 + threadIdx.x` 로
출력 행을 정한다(`src/kernels.cu:32-40`). 런치는
`embeddingGatherKernel<<<num_input_tokens, 1024>>>` 이므로
`blockIdx.x` 가 곧 토큰 위치다(`src/kernels.cu:45`).

decode 의 `embeddingGatherKernelDecode` 도 모양은 같지만 의미가 다르다. 입력이
토큰 ID 배열이 아니라 슬롯별 마지막 토큰 배열 `gpu_last_tokens` 이고,
`blockIdx.x` 가 슬롯을 가리킨다(`src/kernels.cu:347-349`). 출력도 슬롯 순서로
쌓이므로 `workIndex = blockIdx.x * 2048 + threadIdx.x` 의 `blockIdx.x` 는 토큰
위치가 아니라 활성 슬롯 인덱스다(`src/kernels.cu:350`). 호출부는
`embeddingGatherDecode(gpu_last_tokens, num_active_slots, hidden_state, ...)`
이며(`src/main.cpp:759`), 여기서 `num_active_slots` 가 블록 수가 된다
(`src/kernels.cu:361`). 즉 decode 는 "토큰 하나당 블록 하나"라는 구조를 유지한
채 토큰 축을 슬롯 축으로 바꾼 것이다.

## RoPE: 현재 위치 하나만, 호출마다 다시 계산

decode 의 RoPE 는 prefill 과 두 지점에서 갈린다. 첫째, 한 번에 위치 하나만
회전한다. `ropeKernelDecode` 는 단일 블록으로 런치되고(`src/kernels.cu:397`),
각 스레드가 `2 * threadIdx.x` 와 `2 * threadIdx.x + 1` 두 원소를 회전한다
(`src/kernels.cu:379-382`). 회전 각도는 인자로 받은 `position_in_sequence` 하나에
대해서만 계산된다(`src/kernels.cu:378`). 호출부는 활성 슬롯마다
`ropeDecode(&q_proj[slot * EMBEDDING_LENGTH], current_prompt_len[active_slot], ...)`
와 `ropeDecode(k_proj_batched_buffer + slot * KV_DIM, current_prompt_len[active_slot], ...)`
를 부른다(`src/main.cpp:847-848`). 위치 인자가 그 슬롯이 이번에 생성할 토큰의
인덱스, 곧 `current_prompt_len` 이다.

둘째, decode 는 각도를 매번 다시 계산한다. `ropeKernelDecode` 안에는 다음
계산이 있다.

```cpp
int double_i = 2 * (threadIdx.x % 32);
float theta = 1.0 / (pow(500000.0, ((float)double_i / HEAD_DIM)));
float angle = position_in_sequence * theta;
```

인용: [`src/kernels.cu:376-378`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/kernels.cu#L376-L378)

여기서 `500000.0` 과 `32` 는 리터럴로 박혀 있다(`src/kernels.cu:376-377`). 바로
위 주석은 이 값을 미리 계산해 재사용하는 일이 TODO 로 남아 있음을 밝힌다
(`src/kernels.cu:375`). 반면 prefill 의 `ropeKernel_llama3` 는
`d_cos_table`/`d_sin_table` 을 인자로 받아 `cos_table[token_idx * head_dim + pair_idx * 2]`
를 읽기만 한다(`src/kernels.cu:173-200`). 이 테이블은 `main` 이 시작할 때
`init_rope_frequencies(HEAD_DIM, MAX_SEQ_LEN, 500000.0f, 32.0f, 1.0f, 4.0f, 8192)`
로 한 번 만들어 GPU 에 올린 것이다(`src/main.cpp:572`,
`src/kernels.cu:96-152`, 할당·H2D 는 `src/kernels.cu:146-151`). prefill 은
테이블을 참조하고, decode 는 같은 상수를 코드 안에서 다시 계산한다는 차이다.

## K/V 를 배치 버퍼에 모아 블록에 흩뿌린다

decode 의 K/V 투영은 슬롯을 행으로 묶어 cuBLAS 한 번으로 처리한다. K 투영은
`n = num_active_slots` 로 호출되어 출력을 `k_proj_batched_buffer` 에 쓰고
(`src/main.cpp:802-821`), V 투영은 같은 방식으로 `v_proj_batched_buffer` 에 쓴다
(`src/main.cpp:824-842`). 두 버퍼는 decode 전용으로 `BATCH_SIZE × KV_DIM`
크기만큼 잡혀 있다(`src/main.cpp:684-693`). RoPE 를 슬롯별로 적용한 뒤
(`src/main.cpp:844-849`), 새 토큰의 K/V 를 paged KV cache 의 해당 블록으로
복사한다(`src/main.cpp:851-873`).

이 복사가 prefill 과 다른 지점은 한 번에 한 토큰만 다룬다는 것이다. 슬롯마다
새 토큰의 시퀀스 내 위치를 `current_prompt_len` 으로 잡고, 논리 블록과 블록 내
오프셋으로 나눈다(`src/main.cpp:855-857`). 블록이 아직 없으면 `free_blocks` 의
뒤에서 하나 꺼내 `block_table` 에 적고, 아니면 기존 블록을 그대로 쓴다
(`src/main.cpp:858-865`).

```cpp
int logical_block_idx = seq_len / BLOCK_SIZE;
int token_in_block_idx = seq_len % BLOCK_SIZE;
int block = block_table[active_slot * N_LAYERS * MAX_BLOCKS_PER_SEQ + layer * MAX_BLOCKS_PER_SEQ + logical_block_idx];
if (token_in_block_idx == 0)
{
    int physical_block_idx = free_blocks.back();
    free_blocks.pop_back();
    block = physical_block_idx;
    block_table[active_slot * N_LAYERS * MAX_BLOCKS_PER_SEQ + layer * MAX_BLOCKS_PER_SEQ + logical_block_idx] = block;
}
```

인용: [`src/main.cpp:856-865`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/main.cpp#L856-L865)

블록 내 오프셋이 0 일 때만, 즉 새 블록의 첫 토큰일 때만 할당이 일어난다
(`src/main.cpp:859-865`). K 는 블록 시작에서
`token_in_block_idx * KV_DIM * sizeof(__nv_bfloat16)` 만큼 뒤에, V 는 거기서
`V_OFFSET` 만큼 더 뒤에 `cudaMemcpy` D2D 로 기록된다(`src/main.cpp:866-872`).
`V_OFFSET` 은 `BLOCK_SIZE * KV_DIM * sizeof(__nv_bfloat16)` 이고
(`src/main.cpp:33`), 블록 하나는 K 와 V 를 합쳐 `BLOCK_BYTES` 를 차지한다
(`src/main.cpp:34`). 이 블록 레이아웃과 `block_table` 논리 인덱스 산술의 의미는
6편이 소유한다.

prefill 은 같은 일을 `BLOCK_SIZE` 토큰 청크 단위로 한다. 토큰 구간마다 블록을
할당하고 청크 전체를 한 번에 복사한다(`src/main.cpp:251-288`). decode 는 그
청크를 토큰 하나로 줄인 셈이다. 기록을 마치면 `block_table` 전체를
`block_table_gpu` 로 H2D 동기화한다(`src/main.cpp:876`). 이 전체 복사에는
"더 영리하게, 불필요하게 전체를 복사하지 않도록" 하라는 TODO 주석이 붙어 있다
(`src/main.cpp:551`).

## 어텐션은 `pagedAttentionKernel` 이 대신한다

prefill 은 점수 행렬을 만든 뒤 `causalMask` 로 미래를 가리고
(`src/main.cpp:329`) `softmax` 를 호출한다(`src/main.cpp:331`). decode 에는 이
두 호출이 없다. decode 의 어텐션은 `pagedAttention` 한 번으로 끝난다
(`src/main.cpp:878`). 이 커널이 `kv_cache`, `block_table_gpu`, `gpu_seq_lens`,
`gpu_active_slots` 를 함께 받아(`src/kernels.cu:461`) 블록을 순회하며 점수를
계산하고(`src/kernels.cu:478-485`), 워프 리덕션과 온라인 소프트맥스로 가중
평균을 누적해(`src/kernels.cu:486-519`) 결과를 출력한다(`src/kernels.cu:522`).
미래 위치를 가리는 일은 별도 마스크 없이 시퀀스 길이까지만 순회하는 것으로
대신한다. 이 커널의 내부와 입출력은 6편이 소유한다.

여기서 한 가지 사실을 짚어 둘 필요가 있다. decode 계열로 선언된
`softmaxDecode`/`softmaxKernelDecode`(`src/kernels.cuh:25`,
`src/kernels.cu:408-458`)는 `src/main.cpp` 의 decode 경로 어디에서도 호출되지
않는다. decode 의 확률 정규화는 `pagedAttentionKernel` 내부의 온라인
소프트맥스가 맡는다. 이 커널의 `MAX_SEQ_LEN` 스트라이드 가정
(`src/kernels.cu:413`)은 prefill softmax 의 `num_tokens` 스트라이드
(`src/kernels.cu:262`)와 다른 레이아웃을 전제하지만, 현재 호출 그래프에서는
사용되지 않는다.

## 나머지 레이어와 로짓

어텐션 뒤의 계산은 prefill 과 같은 커널을 쓴다. 출력은 입력 q 프로젝션과 같은
버퍼 `buf_2048_1` 에 쓰이고(`src/main.cpp:878`), 그 버퍼가 곧바로 O 투영의
입력이 된다(`src/main.cpp:892`). O 투영 뒤 `residualAdd`(`src/main.cpp:902`),
post-attention RMSNorm(`src/main.cpp:904`), SwiGLU 의 gate·up·`silu`·down
(`src/main.cpp:907-969`), 다시 `residualAdd`(`src/main.cpp:971`) 순으로 레이어
하나가 끝난다. prefill 과 다른 점은 이 호출들이 `prompt_len` 대신
`num_active_slots` 를 토큰 수로 받는다는 것뿐이다.

16개 레이어를 지나면 최종 RMSNorm(`src/main.cpp:974`)과 `embed_tokens` 로짓
(`src/main.cpp:976-994`)이 오고, D2H 복사(`src/main.cpp:996`) 뒤 CPU 에서 활성
슬롯마다 argmax 를 찾아 출력한다(`src/main.cpp:1000-1014`). 생성 토큰이
`<|end_of_text|>`(128001)나 `<|eot_id|>`(128009)이거나
`current_prompt_len == MAX_SEQ_LEN - 1` 이면 슬롯을 비우고 블록을 반납하며
(`src/main.cpp:1015-1031`), 아니면 토큰을 누적하고 길이를 1 늘린다
(`src/main.cpp:1032-1037`). 이 종료·슬롯 처리는 7편이 소유한다.

## 이 장이 다루지 않는 것

- prefill 의 커널 호출 순서와 병렬 리덕션: 3편. 이 장은 prefill 을 대비
  대상으로만 인용한다.
- cuBLAS 의 전치 플래그와 열 우선 레이아웃: 4편. 이 장은 decode 호출의 `n`
  인자와 출력 버퍼만 짚는다.
- `pagedAttentionKernel` 의 block table 인덱싱, 온라인 소프트맥스, in-place
  쓰기, KV 블록 레이아웃: 6편. 이 장은 decode 가 이 커널을 부른다는 사실과
  호출 위치까지만 다룬다.
- 슬롯·큐의 수명주기와 종료 조건, 블록 반납: 7편.
- 버퍼 크기 산정과 별칭 설계: 2편. `k_proj_batched_buffer` 등의 크기 근거는
  여기서 재정의하지 않는다.
- `python/decode_test.py` 는 코드 범위에 포함되지만, 이 장의 근거에 그 동작을
  다루는 주장이 없어 실행 없이 범위로만 둔다.

## 이 장의 한계

- 이 시리즈는 NVIDIA GPU 와 CUDA 툴체인이 없는 환경에서 작성되어 커널을 하나도
  실행하지 않았다. decode 커널의 인덱싱·리덕션·복사에 대한 모든 주장은 소스
  인용이며 실행 검증이 없다.
- 이 장의 최소 근거는 코드 인용 4건, 테스트 1건, 실행 0건이다. 커널 실행
  시간·처리량·메모리 사용량은 측정하지 않으며, 이 장에는 측정값으로 읽힐 수
  있는 성능 수치가 없다.
- `softmaxDecode`/`softmaxKernelDecode` 는 선언·정의되어 있지만
  `src/main.cpp` 의 decode 경로에서 호출되지 않는다. 이 장은 그 사실을 소스
  호출 그래프에 근거해 서술하며, 실행으로 확인하지 않았다.
- `softmaxKernelDecode` 의 `MAX_SEQ_LEN` 스트라이드 가정(`src/kernels.cu:413`)
  은 prefill softmax 의 `num_tokens` 스트라이드(`src/kernels.cu:262`)와 다르다.
  두 레이아웃 가정의 정합성은 실행 검증되지 않았다.
- `ropeKernelDecode` 의 각도 재계산은 TODO 로 남아 있다(`src/kernels.cu:375`).
  decode 와 prefill 두 RoPE 경로의 수치 일치는 실행 검증되지 않았다.
- decode 는 매 레이어마다 `block_table` 전체를 H2D 로 복사한다
  (`src/main.cpp:876`, TODO `src/main.cpp:551`). 이 비용은 측정하지 않는다.
- decode 의 K/V 복사와 블록 할당(`src/main.cpp:851-873`)은 활성 슬롯 수와
  슬롯별 길이에 의존한다. 동시성·경합의 실행 검증은 없다.
- 이 장이 설명하는 순서는 `BATCH_SIZE = 2`(`src/main.cpp:29`)와
  `MAX_SEQ_LEN = 2048`(`src/main.cpp:28`), `BLOCK_SIZE = 16`
  (`src/main.cpp:32`)이라는 컴파일 타임 상수 위에 있다. 이 값이 바뀌면 인덱싱과
  버퍼 크기가 함께 바뀐다.
- 가중치 파일은 gated 모델 `meta-llama/Llama-3.2-1B-Instruct` 의
  `model.safetensors` 라서, decode 를 실제로 돌려보는 검증은 후속 과제로
  남는다.
