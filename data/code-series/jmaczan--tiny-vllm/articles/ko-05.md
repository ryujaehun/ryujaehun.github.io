# tiny-vllm 5장 · attention과 KV cache

4장은 레이어 루프 한 바퀴를 순서대로 읽으면서 attention을 "순서의 한 단계"로만
넘겼다. 그때 짧게만 확인한 것은 헤드 구조와 스코어 스케일 상수뿐이었다. 이 장은
attention 단계가 실제로 읽고 쓰는 메모리, 곧 KV 캐시를 중심으로 그 단계를 다시
본다. prefill이 프롬프트의 K/V를 어떻게 캐시에 흩뿌리고(`src/main.cpp:251-288`),
decode가 토큰 하나씩을 어떻게 덮어쓰는지(`:851-873`), 그리고 attention이 그
K/V를 어떤 헤드 배치로 소비하는지(`:301-371`)가 이 장의 몫이다.

이 장의 구현 주장은 세 갈래다. 캐시의 물리 구조가 Claim 5, prefill/decode의
산포 경로가 Claim 6, 헤드 재사용 규칙이 Claim 7이다. 시리즈의 증거 규칙대로 모든
주장은 고정 커밋의 소스 경로와 줄 범위로 인용한다(`guide.md:11-16`).

## 이 장이 다루는 파일과 범위

`series.yaml` 5장의 대상 파일은 `src/main.cpp`와 `src/kernels.cu`다
(`series.yaml:16-18`). 서술은 KV 캐시의 초기화(`src/main.cpp:574-581`), prefill의
KV 산포(`:251-288`), decode의 KV 산포(`:851-873`), 그리고 prefill의 attention
단계(`:301-371`)에 집중한다. `src/kernels.cu`는 캐시 상수의 중복 정의(`:16-19`)와
decode의 paged attention 커널이 쓰는 GQA 매핑(`:468`)으로 등장한다.

이 장이 넘기는 것은 두 가지다. paged attention 커널 자체는 10장에서, 배칭·슬롯
스케줄러 정책은 7·8장에서 다룬다. decode의 `block_table_gpu` 재동기화(`:876`)도
주제상 8장(Claim 10)의 몫이므로 이 장에서는 존재만 언급한다.

## KV 캐시: 2GiB 고정 블록 풀

KV 캐시는 실행 초기에 한 번에 2GiB로 할당된다. 그 크기와 블록 단위를 정하는
상수들이 `src/main.cpp:32-37`에 있다(`evidence/claims.md:54`).

```
BLOCK_SIZE        = 16              // 페이지(블록) 하나가 담는 토큰 수
KV_DIM            = 512             // K/V 한 헤드 그룹의 차원
V_OFFSET          = BLOCK_SIZE * KV_DIM * sizeof(bf16)   // = 16384
BLOCK_BYTES       = V_OFFSET * 2                         // = 32768, K와 V 두 판
KV_CACHE_SIZE_BYTES = 2 * 1024^3                         // = 2GiB
MAX_BLOCKS_PER_SEQ  = MAX_SEQ_LEN / BLOCK_SIZE           // = 2048 / 16 = 128
NUM_BLOCKS          = KV_CACHE_SIZE_BYTES / BLOCK_BYTES  // = 65536
```

블록의 기하를 정리하면 이렇다. 한 블록은 `BLOCK_SIZE=16` 토큰 × `KV_DIM=512`
차원 × bf16(2바이트)를 담는 K 판을 오프셋 `+0`에 두고, V 판을 `+V_OFFSET`에
둔다. `V_OFFSET`은 정확히 K 판의 바이트 크기이므로(`src/main.cpp:33`), 블록
전체는 두 판을 합쳐 `BLOCK_BYTES = V_OFFSET * 2 = 32768`바이트다(`:34`). 이
32768바이트가 2GiB에 정확히 65536번 들어가므로(`:37`) 총 `NUM_BLOCKS=65536`
블록이 캐시에 들어 있다. K와 V를 한 블록에 함께 담는다는 배치가 이 장 뒤에서
K(`+0`)와 V(`+V_OFFSET`)라는 두 오프셋으로 그대로 이어진다.

할당과 소유 구조는 `src/main.cpp:574-581`에서 만들어진다.

- `kv_cache`는 `cudaMalloc`으로 2GiB 통째로 할당된다(`:576`).
- `free_blocks`는 `0..NUM_BLOCKS-1`(65536개)을 `std::iota`로 채워 물리 블록
  인덱스의 스택으로 삼는다(`:577-578`).
- `block_table`은 `MAX_SEQUENCES * N_LAYERS * MAX_BLOCKS_PER_SEQ` 크기의 CPU
  벡터로 전부 `-1`로 초기화된다(`:579`).
- `block_table_gpu`는 같은 크기로 할당된다(`:580-581`).

이 구조가 Claim 5다: 캐시는 사용량과 무관하게 2GiB 전체를 예약하고, 물리 블록의
소유권은 `free_blocks`가, 시퀀스·레이어별 논리 블록→물리 블록 매핑은 CPU
`block_table`이 담당한다(`evidence/claims.md:51`). 주의할 점은 이 캐시가 "페이지
예약" 방식이라 실제로 쓴 양과 무관하게 2GiB가 할당되어 있다는 것이다
(`evidence/claims.md:57`).

```
kv_cache (2GiB, 물리 블록 풀)
┌─────────┬─────────┬─────────┬─────────┬───┐
│ block 0 │ block 1 │ block 2 │ block 3 │ … │
└─────────┴─────────┴─────────┴─────────┴───┘
  block 0 안: K 판(+0) · V 판(+V_OFFSET)   (각 16384B)

free_blocks (물리 블록 인덱스 스택)        block_table (CPU, 전부 -1 초기화)
┌─────────────────────────┐               ┌──────────────────────────────┐
│ … 65534 65535 │ ← pop    │               │ slot×N_LAYERS×128 + layer×128 │
└─────────────────────────┘               │  + logical_block_idx          │
  pop: main.cpp:268-269, :861-862          │  = physical block (또는 -1)    │
  push: main.cpp:1025                      └──────────────────────────────┘
```

## 논리 블록 → 물리 블록: block_table이 하는 일

`block_table`의 인덱스는 `slot * N_LAYERS * MAX_BLOCKS_PER_SEQ + layer *
MAX_BLOCKS_PER_SEQ + block_idx`로 계산된다(`src/main.cpp:265`, `:271`, `:858`,
`:864`). 즉 시퀀스(슬롯)와 레이어별로 각각의 논리 블록이 어떤 물리 블록에
대응하는지가 이 테이블 한 장에 담긴다. 초기값 `-1`은 "아직 할당되지 않음"을
의미한다. KV 산포가 이 테이블에서 물리 블록 번호를 읽고(`:265`, `:858`),
`-1`이면 `free_blocks`에서 pop해 새 물리 블록을 배정한 뒤 그 번호를 기록한다
(`:268-271`, `:861-864`). 물리 블록 번호가 정해지면 캐시 주소는
`kv_cache + block * BLOCK_BYTES`로 단순 곱셈으로 나온다(`:280`, `:285`, `:866`,
`:870`).

슬롯이 해제될 때는 그 슬롯이 쓰던 물리 블록들이 `free_blocks`로 돌아간다
(`src/main.cpp:1025`, `evidence/trace.md:181`). 이 반환 경로는 7·8장에서 슬롯
수명과 함께 다루고, 이 장에서는 "물리 블록은 free_blocks 스택이 유일한 소유자"
라는 점만 남긴다.

## prefill의 KV 산포: 블록 단위로 채우기

prefill은 프롬프트의 K/V를 레이어마다 블록 단위로 캐시에 흩뿌린다. 루프가
`token_idx = 0`부터 `BLOCK_SIZE` 간격으로 `prompt_len`까지 돈다
(`src/main.cpp:251-288`, `evidence/claims.md:64`).

루프 안의 순서는 세 단계다.

1. **복사할 토큰 수 결정** — 남은 토큰 수를 `BLOCK_SIZE`로 제한한다
   (`:253-257`). 마지막 블록이 16보다 짧을 수 있기 때문이다.
2. **물리 블록 확보** — `block_idx = token_idx / BLOCK_SIZE`로(`:264`) 논리 블록
   번호를 정하고, `block_table`에서 물리 블록을 읽는다. `-1`이면 `free_blocks`
   에서 pop해 그 값을 기록하고(`:266-272`), 이미 할당되어 있으면
   `assert(false)`를 던진다(`:273-277`). 소스 주석은 prefill 중에는 블록이 항상
   비어 있어야 한다고 본다("block must be -1 during prefill", `:275`).
3. **D2D 복사** — K는 `kv_cache + block*BLOCK_BYTES`(즉 `+0`)에, V는
   `+V_OFFSET`에 각각 `num_tokens_to_copy * KV_DIM * sizeof(bf16)`만큼
   `cudaMemcpy(...DeviceToDevice)`로 복사한다(`:280-287`).

Claim 6이 정리하는 prefill 쪽 절반은 곧 이 경로다: prefill은 `BLOCK_SIZE` 단위로
물리 블록을 pop해 K(`+0`)/V(`+V_OFFSET`)를 D2D 복사한다
(`evidence/claims.md:61`). 복사 단위가 토큰이 아니라 "블록 한 판"이라는 점이
이어지는 decode와의 핵심 차이다.

## decode의 KV 산포: 토큰 단위로 채우기

decode는 활성 슬롯마다, 레이어마다 **한 토큰**의 K/V만 캐시에 덮어쓴다
(`src/main.cpp:851-873`, `evidence/claims.md:65`). 슬롯별 루프 안의 순서는
다음과 같다.

1. **위치 계산** — `seq_len = current_prompt_len[active_slot]`(`:855`)에서 논리
   블록과 블록 내 토큰 위치를 잡는다.
   ```
   logical_block_idx = seq_len / BLOCK_SIZE     (:856)
   token_in_block_idx = seq_len % BLOCK_SIZE    (:857)
   ```
2. **블록 경계에서만 새 블록** — `token_in_block_idx == 0`일 때만
   `free_blocks`에서 pop해 `block_table`에 기록한다(`:859-865`). 그 외에는
   `block_table`에 이미 적힌 물리 블록을 그대로 쓴다. 즉 블록 하나의 수명은 그
   블록이 받는 16개 토큰 전부를 채울 때까지 이어지고, 할당은 16토큰마다 한 번
   일어난다.
3. **토큰 위치에 덮어쓰기** — K/V를 각각
   ```
   kv_cache + block*BLOCK_BYTES (+ V_OFFSET) + token_in_block_idx*KV_DIM*bf16
   ```
   주소로 D2D 복사한다(`:866`, `:870`). 한 토큰이므로 복사량은 `KV_DIM *
   sizeof(bf16)`뿐이다(`:868`, `:872`).

Claim 6의 decode 절반은 곧 이 경로다: `seq_len % BLOCK_SIZE == 0`일 때만 새
블록을 pop하고, 그 외에는 기존 블록의 해당 토큰 위치에 덮어쓴다
(`evidence/claims.md:61`). 복사량과 할당 빈도가 prefill과 정반대 방향으로
줄어든다 — prefill은 "블록 한 판"을, decode는 "토큰 하나"를 쓴다.

이 두 산포 경로를 나란히 두면 채움 방식의 차이가 선명해진다.

```
prefill (한 레이어, 프롬프트 전체)        decode (한 레이어, 활성 슬롯 1개)
token_idx: 0..prompt_len, 16씩            seq_len = current_prompt_len[slot]
┌─────────────────────────────┐           ┌───────────────────────────────┐
│ block 0  K/V 16토큰 D2D      │           │ logical_block = seq_len/16    │
│ block 1  K/V 16토큰 D2D      │           │ token_in_block = seq_len%16   │
│ …                             │           │ 토큰 0일 때만 pop·기록        │
└─────────────────────────────┘           │ K/V 1토큰(512×bf16) D2D        │
  주소: block*BLOCK_BYTES(+V_OFFSET)       └───────────────────────────────┘
  (:251-288)                                주소: …+token_in_block*KV_DIM
                                            (:851-873)
```

산포가 끝나면 `block_table`이 `block_table_gpu`로 재복사되고(`:876`) 그 다음
`pagedAttention`이 호출된다(`:878`). decode의 attention이 이 캐시를 어떤
구조로 읽는지는 10장이 다루고, 이 장에서는 산포가 만든 캐시가 곧 attention의
입력이라는 연결고리만 짚는다. 산포 경로가 CPU의 실제 슬롯 인덱스(`active_slot`)
를 기준으로 도는 반면 paged attention 커널은 활성 위치를 `gpu_active_slots`
매핑으로 실제 슬롯에 대응시킨다는 인덱싱 혼재는 추적 메모가 지적한다
(`evidence/trace.md:235-239`).

## attention: GQA로 헤드를 재사용하다

캐시에 K/V를 쌓는 이유는 attention이 그 값을 소비하기 때문이다. 이 장이
attention에서 확인할 것은 헤드 재사용 규칙, 곧 Claim 7이다
(`evidence/claims.md:71`).

헤드 상수는 `src/main.cpp:20-24`에 있다. Q는 `NUM_Q_HEADS=32`, K/V는 각각
`NUM_K_HEADS=NUM_V_HEADS=8`이고, 비율 상수가
`GQA_Q_TO_K_RATIO=4`, `GQA_ATTN_SCORES_TO_V_RATIO=4`로 정의된다. 즉 4개의 연속
Q 헤드가 1개의 K 헤드와 1개의 V 헤드를 공유한다.

prefill의 attention 단계는 스코어 GEMM(`src/main.cpp:301-327`) → `causalMask`
(`:329`; `src/kernels.cu:239-255`, 커널 `:224-237`) → `softmax`(`:331`;
`src/kernels.cu:293-309`, 커널 `:257-290`) → scores×V GEMM(`:343-371`) 순서로
진행된다(4장의 레이어 파이프라인 참조). 스코어 GEMM은 Q 헤드마다 `k_head_idx =
i / GQA_Q_TO_K_RATIO`로 공유할 K 헤드를 정한다(`:303`). 스코어 계산의 형태는
소스 주석이 `attn_score_head = Q_head * K_head^T / sqrt(64)`로 남겨 두었다
(`:298`). 스케일 상수 `attn_alpha = 1.0f / 8.0f`가 이 `sqrt(64)=8`에
대응한다(`:649`). 이 루프가 주목할 점은 K 피연산자로
`k_proj_temp_buf + k_head_idx * HEAD_DIM`을 읽는다는 것이다(`:305`) — prefill의
스코어 GEMM은 방금 산포한 캐시가 아니라 임시 버퍼의 K/V를 그대로 쓴다. 캐시
산포는 이후 단계, 특히 decode가 캐시에서 읽기 위해 미리 저장하는 역할이다.

scores×V GEMM은 같은 매핑을 V에 적용한다. `v_head_idx = i /
GQA_ATTN_SCORES_TO_V_RATIO`(`:346`)로 V 헤드를 고르고, V도
`v_proj_temp_buf + v_head_idx * HEAD_DIM`에서 읽는다(`:349`). 출력은 헤드당
`(num_tok, 64)`이므로 32개를 합치면 `(num_tok, 2048)`이 된다(`:342` 주석).

decode 쪽 attention은 캐시를 읽는 쪽이므로 매핑이 커널 안에 들어 있다.
`pagedAttentionKernel`은 `kv_head_idx = q_head_id / GQA_Q_TO_K_RATIO`로
동일한 비율을 쓴다(`src/kernels.cu:468`). 이 커널은 블록 테이블을 따라 물리
블록을 순회하며 K·V를 읽는데(`:480-485`), 커널 전체는 10장의 몫이다. 여기서는
prefill과 decode가 **같은 비율 상수(4)**를 공유한다는 것만 Claim 7로 확정한다
(`evidence/claims.md:71`).

```
Q 헤드 32개 ────────────── K/V 헤드 8개
 0 ─┐                      0
 1 ─┤  / GQA_Q_TO_K_RATIO    │
 2 ─┤  (=4)                  │
 3 ─┘                       ┘
 4 ─┐                       1
 … ─┤                        …
28 ─┐                       7
29 ─┤
30 ─┤
31 ─┘
  k_head_idx = i/4  (:303)   v_head_idx = i/4  (:346)
  paged attention: kv_head_idx = q_head_id/4  (kernels.cu:468)
```

## 검증 경로

이 장이 서술한 캐시 구조와 산포 경로에 대응하는 단위 테스트는 없다. 인벤토리상
유일한 커널 테스트는 `tests/test_softmax.cu` 하나뿐이다
(`evidence/recon.md:12`). KV 산포는 커널이 아니라 D2D `cudaMemcpy` 호출이므로
커널 테스트 범위 밖이고(`evidence/claims.md:67`), attention 스코어·scores×V
GEMM의 정확성도 테스트로 뒷받침되지 않는다. 저장소를 실행하지 않았으므로 이
장은 "캐시가 어떤 구조로 산포되고 attention이 어떤 매핑으로 읽는지"를 서술할
뿐, 그 수치 결과가 올바르다는 것을 주장하지 않는다(`evidence/recon.md:4`).

- decode 산포는 CPU의 실제 슬롯 인덱스로, paged attention 커널은 활성 위치
  매핑으로 블록 테이블을 읽는다 — 두 인덱싱 체계가 섞여 있어 추적 시 주의가
  필요하다(`evidence/trace.md:235-239`).
- `attn_alpha = 1/8`이 `HEAD_DIM=64`의 역제곱근이라는 것은 소스 주석
  (`src/main.cpp:298`)과 상수(`:649`)가 일치하는 관찰이지, 수치 검증 결과가
  아니다.
- 이 장은 성능을 주장하지 않는다. 산포의 "블록 단위/토큰 단위"는 작업량과
  복사 횟수의 구조적 차이를 말할 뿐 실행 시간·처리량은 근거가 없어 쓰지
  않는다.

## 정리

이 장은 attention이 소비하는 KV 캐시를 세 갈래로 읽었다. 첫째, 캐시의 물리
구조다. `BLOCK_SIZE=16`×`KV_DIM=512`×bf16 블록이 K 판(`+0`)과 V 판
(`+V_OFFSET`)으로 나뉘어 `BLOCK_BYTES=32768`바이트를 이루고, 2GiB 전체가
`NUM_BLOCKS=65536`개의 물리 블록으로 예약된다(`src/main.cpp:32-37`, `:574-581`;
Claim 5). 둘째, 산포 경로다. prefill은 블록 단위로 pop·D2D 복사하고
(`:251-288`), decode는 `seq_len % BLOCK_SIZE`가 0일 때만 새 블록을 pop해 토큰
위치에 덮어쓴다(`:851-873`; Claim 6). 셋째, 헤드 재사용 규칙이다. Q 32개가
K/V 8개를 비율 4로 공유하며, prefill 스코어 GEMM(`:303`), scores×V(`:346`),
paged attention 커널(`src/kernels.cu:468`)이 같은 매핑을 쓴다(Claim 7).

핵심은 paged attention의 데이터 구조가 이 장에서, 커널이 10장에서 준비된다는
점이다. 논리 블록을 물리 블록으로 바꾸는 `block_table`과 물리 블록을 소유하는
`free_blocks`가 그 데이터 구조의 두 축이고, 다음 장은 이 구조를 실행 시간 관점
에서 다시 보는 prefill과 decode의 병목 비교로 이어진다.
