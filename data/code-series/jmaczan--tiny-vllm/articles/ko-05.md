# 5. 토큰 하나만 만드는 decode 경로

이 글의 모든 경로와 줄 번호는 고정 revision
`e25bf1994efa90bc98b721ba7c527402f86fbeaf` 의 트리를 가리킨다(`guide.md:6`). 표기는
`파일:시작-끝` 형식이며, 실행 결과가 아니라 소스 인용이다.

## 이 장의 질문

3편에서 prefill 경로가 프롬프트의 모든 토큰을 한 번에 흘려 다음 토큰 하나를 고르는
것을 봤다. 그 뒤의 매 스텝은 방금 고른 토큰 하나를 입력으로 삼아 토큰 하나를 더
만든다. 이 장의 질문은 **decode 는 왜 prefill 과 다른 커널 변형을 쓰는가**다
(`series.yaml:95`). prefill 과 decode 의 구분, attention 수식, KV cache 의 존재
이유, continuous batching 의 목적은 이 시리즈의 전제이며 여기서 다시 설명하지
않는다(`guide.md:14-16`).

이 장은 decode 스텝의 소유 편이며 prefill 과의 대비로만 성립하므로 3편에 의존한다
(`guide.md:146`). decode 스텝의 소유권과 KV 저장 구조의 경계는 `guide.md:198-199`
가 규정한다. 슬롯·큐와 종료 조건은 7편이 맡는다(`guide.md:200`). 코드 범위는
`src/kernels.cu`, `src/main.cpp`, `python/decode_test.py` 다(`series.yaml:97-99`).
`required_evidence` 는 code 4 / tests 1 / runtime 0 이며(`series.yaml:102-105`),
runtime 은 0 이므로 아래 모든 주장은 실행 없이 소스 인용으로만 뒷받침된다
(결정 003, `guide.md:75-87`).

## decode 는 슬롯마다 토큰 하나씩 이어 붙인다

decode 는 `main` 안의 `while(true)` 루프 하나로 산다(`src/main.cpp:720-1039`). 매
반복은 같은 순서를 밟는다(`trace.md:118-158`).

1. `active_slots`·`active_tokens` 를 비운다(`src/main.cpp:722-723`).
2. 슬롯을 순회하며 빈 슬롯은 큐의 다음 프롬프트를 `prefill` 로 채우고, 점유 슬롯
   전부를 `active_slots`·`active_tokens` 에 모은다(`src/main.cpp:724-737`).
3. 활성 슬롯이 0 이면 큐가 빈 경우 break, 아니면 continue 한다
   (`src/main.cpp:738-746`).
4. `gpu_last_tokens`·`gpu_active_slots`·`gpu_seq_lens` 를 H2D 로 올린다. `seq_lens`
   는 슬롯별 현재 길이에 1을 더한 값이다(`src/main.cpp:749-757`).
5. `embeddingGatherDecode` 로 슬롯별 마지막 토큰 하나를 임베딩한다
   (`src/main.cpp:759`).
6. 16개 레이어를 순회한다(`src/main.cpp:760-972`). RMSNorm → Q/K/V 투영 → RoPE →
   K/V 블록 분산 → `pagedAttention` → O 투영 → 잔차 → post-attn RMSNorm → SwiGLU →
   잔차 순이다.
7. 최종 RMSNorm(`src/main.cpp:974`)과 로짓 cuBLAS(`src/main.cpp:976-994`)를 거친다.
8. `embed_proj` 를 D2H 로 내리고 활성 슬롯별 CPU argmax 로 다음 토큰을 고른다
   (`src/main.cpp:996`, `src/main.cpp:1000-1014`).
9. 종료를 검사한다(`src/main.cpp:1015-1037`). EOS/EOT 토큰 또는 길이 한도 처리와
   블록 반납은 7편이 소유한다(`guide.md:200`).

prefill 과의 핵심 차이는 입력이다. prefill 은 프롬프트 전체를 한 번에 처리하지만
(3편), decode 는 `gpu_last_tokens` 에 담긴 슬롯별 마지막 토큰 하나만 임베딩한다.
이전 스텝까지의 문맥은 KV 캐시 블록에 남아 있고, 매 반복이 그 위에 토큰 하나를 이어
붙인다. 캐시가 어떤 모양으로 놓이는지는 6편이 다룬다(`guide.md:199`).

decode 는 이 때문에 전용 버퍼를 따로 가진다. `gpu_last_tokens`
(`src/main.cpp:684-685`)와 `k_proj_batched_buffer`·`v_proj_batched_buffer`
(`src/main.cpp:688-693`)가 decode 전용으로 할당된다(Claim 4, `claims.md:70-87`).
뒤에서 보듯 K/V 는 이 배치 버퍼에 모은 뒤 블록으로 흩는다.

## prefill 과 decode 를 가르는 n 인자

두 경로의 차이는 cuBLAS 호출의 `n` 인자에서 바로 드러난다. prefill 은 프롬프트
토큰 수를, decode 는 활성 슬롯 수를 넣는다.

| 호출 | prefill | decode |
| --- | --- | --- |
| Q 투영 | `n = prompt_len` (`src/main.cpp:182`) | `n = num_active_slots` (`src/main.cpp:769`) |
| K 투영 | `n = prompt_len` (`src/main.cpp:205`) | `n = num_active_slots` (`src/main.cpp:806`) |
| V 투영 | `n = prompt_len` (`src/main.cpp:226`) | `n = num_active_slots` (`src/main.cpp:828`) |
| O 투영 | `n = prompt_len` (`src/main.cpp:382`) | `n = num_active_slots` (`src/main.cpp:886`) |
| 로짓 | `n = prompt_len` (`src/main.cpp:513`) | `n = num_active_slots` (`src/main.cpp:980`) |

같은 cuBLAS 호출이 prefill 에서는 "토큰 N개를 한 번에", decode 에서는 "슬롯 N개를
한 번에"로 읽힌다. 행렬의 모양이 아니라 **축의 의미**가 바뀐 것이다. prefill 의 한
호출이 한 프롬프트의 토큰 여러 개를 처리하는 반면, decode 의 한 호출은 서로 다른
슬롯의 토큰 하나씩을 묶어 처리한다. `num_active_slots` 는 decode 루프가 슬롯을 훑은
뒤의 개수이며(`src/main.cpp:738`), `BATCH_SIZE=2`(`src/main.cpp:29`)보다 클 수 없다.

이 축 변화가 커널 변형의 이유다. prefill 커널은 프롬프트의 토큰 위치를 인덱싱
축으로 삼지만, decode 시점의 슬롯당 시퀀스는 길이 1이므로 커널이 "토큰 위치" 대신
"슬롯"을 축으로 삼아 인덱싱을 단순화한다(Claim 10, `claims.md:187-207`).

## decode 계열 커널은 슬롯을 축으로 삼는다

prefill 계열 커널 일곱 개는 `src/kernels.cu:32-344` 에 있고, decode 계열 네 개는 그
뒤 `src/kernels.cu:347-523` 에 있다(`guide.md:107-110`, `trace.md:251-255`). 다음
표는 대응하는 커널의 인덱싱 가정을 맞세운다.

<!-- visual: prefill-decode-contrast supports: [prefill-decode-contrast] -->
| 항목 | prefill 계열 | decode 계열 |
| --- | --- | --- |
| 임베딩 | `embeddingGatherKernel` — 프롬프트 토큰들을 담당(`src/kernels.cu:32-53`) | `embeddingGatherKernelDecode` — `blockIdx.x` 가 슬롯(`src/kernels.cu:347-369`, 슬롯 인덱싱 `349`) |
| RoPE | `ropeKernel_llama3` — 토큰마다 한 블록(`src/kernels.cu:173-222`) | `ropeKernelDecode` — 단일 블록, 현재 위치 하나만 회전(`src/kernels.cu:371-405`, 런치 `397`) |
| softmax | `softmaxKernel` — `num_tokens` 스트라이드(`src/kernels.cu:257-309`, `262`) | `softmaxKernelDecode` — `MAX_SEQ_LEN` 스트라이드(`src/kernels.cu:408-458`, `413`) |
| 어텐션 | cuBLAS `Q·K^T` + `causalMask` + `softmax`(3편) | `pagedAttentionKernel`(`src/kernels.cu:461-523`) |

`embeddingGatherKernelDecode` 는 `gpu_last_tokens[blockIdx.x]` 로 슬롯의 토큰을 읽고
`blockIdx.x * 2048` 을 행 시작으로 삼는다(`src/kernels.cu:349-350`). 블록 하나가
슬롯 하나를 담당한다. prefill 계열 `embeddingGatherKernel` 이 `blockIdx.x` 를
프롬프트의 토큰 위치로 쓰는 것과 대비된다(`src/kernels.cu:34-38`).

`ropeKernelDecode` 는 단일 블록 런치 `<<<1, num_threads>>>` 로 현재 위치 하나만
회전한다(`src/kernels.cu:397`). prefill 계열 `rope` 가
`<<<num_tokens, num_threads>>>` 로 프롬프트 전체 위치를 한 번에 처리하는 것과 다르다
(`src/kernels.cu:211`). 회전시킬 위치 값은 호출부에서 슬롯마다 넘긴다
(`src/main.cpp:844-849`, `847-848`).

`softmaxKernelDecode` 는 행 시작을 `blockIdx.x * MAX_SEQ_LEN` 으로 잡는다
(`src/kernels.cu:413`). prefill `softmaxKernel` 의 `blockIdx.x * num_tokens`
(`src/kernels.cu:262`)와 다른 레이아웃 가정이다. decode 버퍼가 슬롯 수×`MAX_SEQ_LEN`
크기로 잡혀 있다는 전제가 깔려 있다(`trace.md:228-230`).

decode 의 어텐션만 cuBLAS 가 아니라 `pagedAttentionKernel` 인 이유는 읽는 대상이
다르기 때문이다. prefill 은 방금 만든 `k_proj_temp_buf`·`v_proj_temp_buf` 를 그대로
소비하지만(3편), decode 는 여러 스텝에 걸쳐 블록으로 흩어 둔 KV 캐시를 다시 읽어야
한다. 그 읽기 경로와 온라인 소프트맥스는 6편이 소유한다(`guide.md:199`).

## decode 경로에서 실제로 호출되는 커널

decode 계열로 분류되는 함수는 `embeddingGatherDecode`, `ropeDecode`,
`softmaxDecode`, `pagedAttention` 넷이다(`src/kernels.cu:347-523`). 그런데 decode
경로에서 실제로 호출되는 것은 셋뿐이다.

- `embeddingGatherDecode` — decode 반복마다 한 번, 레이어 루프
  (`src/main.cpp:760-972`) **밖**에서 호출된다(`src/main.cpp:759`).
- `ropeDecode` — 레이어 루프 **안**에서 슬롯마다 호출된다
  (`src/main.cpp:847-848`).
- `pagedAttention` — 레이어 루프 **안**에서 호출된다(`src/main.cpp:878`).

`softmaxDecode` 는 `src/kernels.cu:442-458` 에 구현돼 있지만 `main.cpp` 어디에서도
호출되지 않는다. decode 의 attention 은 `pagedAttentionKernel` 이 온라인
소프트맥스를 내부에서 처리하므로 별도 softmax 커널이 필요 없다. 이 온라인
소프트맥스의 구현은 6편이 소유한다(`guide.md:199`). `softmaxDecode` 의 런치 가드
(`src/kernels.cu:444-448`)와 `MAX_SEQ_LEN` 스트라이드(`src/kernels.cu:413`)는
호출되지 않는 코드에 남은 레이아웃 가정이다.

함수 선언이 모여 있는 `src/kernels.cuh` 에도 `softmaxDecode` 선언이 있으나, 그
헤더의 본문은 이 시리즈의 첨부에 포함되지 않았다(`trace.md:219-221`). 위 관찰은
호출부가 없다는 정적 관찰이며 실행 검증은 아니다.

## RoPE: 사전 계산 테이블과 호출마다 재계산

prefill 과 decode 는 RoPE 주파수를 얻는 방식에서도 갈린다(Claim 11,
`claims.md:209-226`).

prefill 계열은 사전 계산 테이블을 쓴다. `init_rope_frequencies` 가 `main` 초기에
호출되고(`src/main.cpp:572`), `d_inv_freq`·`d_cos_table`·`d_sin_table` 세 디바이스
배열을 할당·채운다(`src/kernels.cu:96-152`). 주파수는 Llama-3 방식으로
스케일링되고(`src/kernels.cu:109-124`), 테이블은 H2D 로 올라간다
(`src/kernels.cu:126-127`, `146-151`). `ropeKernel_llama3` 는 테이블을 참조만 한다
(`src/kernels.cu:173-200`, 참조 위치 `194-196`).

반면 `ropeKernelDecode` 는 호출마다 `theta = 1/pow(500000, 2i/64)` 를 다시
계산한다(`src/kernels.cu:371-384`). 주파수 상수 `500000.0` 과 헤드 절반 `32` 를
하드코딩한다(`src/kernels.cu:377-378`). 사전 계산 테이블을 쓰지 않는다는 점이
prefill 과의 차이다.

이 재계산은 TODO 로 남아 있고(`trace.md:231-233`), 두 경로가 수치적으로 같은
회전을 만드는지는 실행 검증되지 않았다(`claims.md:224-226`).

## K/V 기록: 배치 투영과 블록 분산

decode 는 슬롯들의 K/V 를 배치 하나로 투영한다. K/V 투영 cuBLAS 는
`k_proj_batched_buffer`·`v_proj_batched_buffer` 에 결과를 쓴다
(`src/main.cpp:802-842`). 이 버퍼는 `BATCH_SIZE × KV_DIM` 크기로 decode 전용
할당이다(`src/main.cpp:688-693`). prefill 의 임시 버퍼 `k_proj_temp_buf`·
`v_proj_temp_buf` 가 `MAX_PROMPT_LEN × KV_DIM` 인 것과 크기 산정이 다르다
(`src/main.cpp:635-639`). 버퍼 크기 산정의 근거는 2편이 소유한다(`guide.md:194`).

투영한 K/V 를 블록에 흩는 규칙은 `src/main.cpp:851-873` 에 있다(Claim 12,
`claims.md:227-245`). 핵심 분기는 다음과 같다.

```cpp
int logical_block_idx = seq_len / BLOCK_SIZE;
int token_in_block_idx = seq_len % BLOCK_SIZE;
int block = block_table[active_slot * N_LAYERS * MAX_BLOCKS_PER_SEQ + layer * MAX_BLOCKS_PER_SEQ + logical_block_idx];
if (token_in_block_idx == 0)
{
    int physical_block_idx = free_blocks.back();
    free_blocks.pop_back();
    block = physical_block_idx;
    block_table[active_slot * N_LAYERS * MAX_BLOCKS_PER_SEQ + layer * MAX_BLOCKS_PER_SEQ + logical_block_idx] = block;
}
```

인용: `src/main.cpp:855-864`.

`token_in_block_idx == 0` 일 때만 `free_blocks` 에서 새 물리 블록을 꺼내고
(`src/main.cpp:859-865`), 그 외에는 기존 블록의 위치에 `cudaMemcpy`(D2D)로
기록한다(`src/main.cpp:866-872`). 즉 블록 하나가 채워질 때만 할당하고, 그 다음
토큰들은 이미 잡힌 블록의 `token_in_block_idx` 위치에 덮어쓴다. prefill 이 논리
블록마다 `block_table` 값이 `-1` 이어야 한다고 단정하는 것
(`src/main.cpp:266-277`)과 달리, decode 는 블록 경계에서만 새 블록을 요구한다.

산포가 끝나면 `block_table` 전체를 `block_table_gpu` 로 H2D 동기화한 뒤
(`src/main.cpp:876`) `pagedAttention` 을 호출한다(`src/main.cpp:878`). 이 동기화는
prefill 쪽에도 같은 TODO 주석과 함께 있다(`src/main.cpp:550-552`). 매 레이어마다
테이블 전체를 복사하는 이 비용은 측정되지 않았다(`claims.md:242-244`,
`trace.md:234-235`).

KV cache 의 블록 레이아웃과 `pagedAttentionKernel` 이 블록을 읽는 경로는 6편이
소유한다(`guide.md:199`). 여기서는 decode 스텝이 K/V 를 어떻게 쓰는지만 다룬다.

## tests: 1 — python/decode_test.py

이 장의 `required_evidence.tests` 는 1 이다(`series.yaml:104`). 이 장의 code_scope 인
`python/decode_test.py` 는 `meta-llama/Llama-3.2-1B-Instruct` 토크나이저를 불러와
(`python/decode_test.py:1-2`) 프롬프트 4개의 토큰 ID 열을(`python/decode_test.py:4-9`)
`t.decode(tokens)` 로 다시 텍스트로 되돌려(`python/decode_test.py:12`) 토큰 ID 와
텍스트의 매핑을 확인하는 12줄 스크립트다(`recon.md:37-38`). 이 파일은 저장소에
커밋돼 있으나 이 시리즈의 첨부에는 포함되지 않았고 실행하지도 않았다. `claims.md` 에
이 테스트를 직접 다루는 claim 은 없다(`briefs.md:150-151`). decode 계열 검증은 실행
없이 정적 인용으로만 이뤄진다.

## 이 장이 확정한 것

- decode 계열 커널은 시퀀스 길이 1(슬롯당 토큰 1개)을 전제로 인덱싱 축을 슬롯으로
  바꾼다. `embeddingGatherKernelDecode` 는 `blockIdx.x` 를 슬롯으로 삼고,
  `ropeKernelDecode` 는 단일 블록으로 현재 위치 하나만 회전하며,
  `softmaxKernelDecode` 는 `MAX_SEQ_LEN` 스트라이드를 가정한다(Claim 10,
  `claims.md:187-207`).
- 같은 cuBLAS 호출의 `n` 인자가 prefill 에서는 `prompt_len`, decode 에서는
  `num_active_slots` 로 바뀐다(`src/main.cpp:182`·`769` 등).
- prefill 의 RoPE 는 사전 계산 테이블을 참조하지만, `ropeKernelDecode` 는 호출마다
  `theta` 를 재계산하고 상수 `500000.0`·`32` 를 하드코딩한다(Claim 11,
  `claims.md:209-226`).
- decode 는 슬롯별 K/V 를 배치 버퍼에 모은 뒤, `token_in_block_idx == 0` 일 때만
  `free_blocks` 에서 새 블록을 할당하고 그 외에는 기존 블록에 D2D 로 기록한다
  (Claim 12, `claims.md:227-245`).
- decode 경로에서 호출되는 decode 계열 함수는 `embeddingGatherDecode`(레이어 루프
  밖), `ropeDecode`·`pagedAttention`(레이어 루프 안) 셋이며 `softmaxDecode` 는
  호출되지 않는다.

## 이 장이 다루지 않는 것

- KV 블록 레이아웃, block table 인덱싱, `pagedAttentionKernel` 의 읽기·온라인
  소프트맥스: 6편(`guide.md:199`).
- 슬롯·큐, EOS/EOT 종료, 블록 반납: 7편(`guide.md:200`).
- prefill 커널 순서와 블록 내 병렬 리덕션: 3편(`guide.md:195-196`).
- cuBLAS 전치 플래그와 열-행 우선 레이아웃: 4편(`guide.md:197`).
- 버퍼 크기 산정과 별칭 설계: 2편(`guide.md:194`).

## 이 장의 한계

- 이 시리즈는 NVIDIA GPU 와 CUDA 툴체인이 없는 환경에서 작성되어 커널을 실행하지
  않는다. 이 장의 모든 주장은 소스 인용이며 실행 검증이 없다(`guide.md:75-87`;
  Claim 10·11·12 한계).
- `softmaxKernelDecode` 의 `MAX_SEQ_LEN` 스트라이드(`src/kernels.cu:413`)는 prefill
  `softmaxKernel` 의 `num_tokens` 스트라이드(`src/kernels.cu:262`)와 다른 레이아웃
  가정이며 실행으로 확인되지 않았다(`claims.md:204-207`, `trace.md:228-230`).
- `ropeKernelDecode` 의 주파수 재계산은 TODO 로 남아 있고(`trace.md:231-233`),
  prefill 테이블 경로와 수치가 일치하는지 검증되지 않았다(`claims.md:224-226`).
- decode 는 매 레이어마다 `block_table` 전체를 `block_table_gpu` 로 H2D 복사한다
  (`src/main.cpp:876`). 이 비용은 이 시리즈의 측정 원칙에 따라 측정하지 않았다
  (`claims.md:242-244`, `trace.md:234-235`).
- `softmaxDecode` 가 호출되지 않는다는 관찰은 소스 정적 관찰이며, 실행 중 다른
  경로로 호출되지 않는다는 보장은 아니다.
- `src/kernels.cuh` 와 `src/cuda_to_hip.h` 본문은 첨부에 없어 함수 시그니처 수준의
  대조만 가능했다(`trace.md:219-221`).
- `python/decode_test.py` 는 code_scope 이고 `tests` 최소값 1 을 채우지만
  (`series.yaml:99`, `104`), 이 테스트를 직접 다루는 claim 이 없어
  (`briefs.md:150-151`) 실행 없이 정적 인용으로만 다룬다.
- 슬롯 해제와 블록 반납, 생성 종료 조건(`src/main.cpp:1015-1037`)은 이 장에서 순서만
  인용했고 7편이 소유한다(`guide.md:200`).
