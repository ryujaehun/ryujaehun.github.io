# tiny-vLLM 코드 읽기 5편 — 토큰 하나만 만드는 decode 경로

3편 `prefill-path` 는 프롬프트의 모든 토큰을 한 번에 흘려 다음 토큰 하나를
골랐다. 이후의 매 스텝은 그 토큰을 입력으로 삼아 토큰 하나를 새로 만든다.
5편의 질문은 시리즈의 중간 지점이다. **decode 는 왜 prefill 과 다른 커널
변형을 쓰는가.** 답은 인덱싱 축에 있다. prefill 은 프롬프트의 토큰 위치 N개를
축으로 삼지만, decode 시점의 시퀀스는 슬롯당 길이 1이므로 커널이 "토큰 위치"
대신 "슬롯"을 축으로 삼아 인덱싱을 단순화한다.

이 편은 prefill 과의 대비로만 성립하므로 3편에 의존한다(guide.md:146). decode
스텝의 소유권은 이 편에 있고, KV cache 의 블록 구조와 읽기 경로는 6편이
소유한다(guide.md:198). 여기서는 커널 변형과 K/V 기록 경로에 집중하고, 블록
레이아웃은 넘겨 받는 쪽이 푼다.

## 고정 revision

- Repository: https://github.com/jmaczan/tiny-vllm
- Commit: `e25bf1994efa90bc98b721ba7c527402f86fbeaf`

이 편의 모든 인용은 위 커밋의 트리를 가리키는 permalink 다. 기본 브랜치를 다시
해석하거나 이후 revision 으로 대체하지 않는다.

   슬롯 해제·블록 반납 절차는 7편이 소유한다.

prefill 과의 핵심 차이는 입력이다. prefill 은 프롬프트 전체를 한 번에 처리해
다음 토큰 하나를 고르지만(3편), decode 는 `gpu_last_tokens` 에 담긴 슬롯별
**마지막 토큰 하나**만 임베딩한다. 이전 스텝까지의 문맥은 KV 캐시 블록에 남아
있고, 매 반복이 그 위에 토큰 하나를 이어 붙인다. 캐시가 메모리에 어떤 모양으로
놓이는지는 6편이 다룬다.

decode 는 이 때문에 전용 버퍼를 따로 가진다. `gpu_last_tokens`·
`k_proj_batched_buffer`·`v_proj_batched_buffer` 가 decode 전용으로 할당된다
([`src/main.cpp:683-693`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/main.cpp#L683-L693),
claims.md:74-87). 뒤에서 보듯 K/V 는 이 배치 버퍼에 모은 뒤 블록으로 흩는다.

## 시퀀스 길이 1: 슬롯을 축으로 삼는 커널 변형

prefill 커널은 프롬프트의 토큰 위치 N개를 축으로 삼는다
([`src/kernels.cu:32-344`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/kernels.cu#L32-L344),
3편). decode 커널은 슬롯당 토큰이 정확히 하나이므로 인덱싱 축을 **슬롯**으로
바꾼다(Claim 10, claims.md:187-207).

`embeddingGatherKernelDecode`([`src/kernels.cu:347-369`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/kernels.cu#L347-L369))
는 `blockIdx.x` 를 슬롯으로 삼는다
([`src/kernels.cu:349`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/kernels.cu#L349)).
슬롯의 마지막 토큰 하나만 임베딩하면 되므로 블록 하나가 슬롯 하나를 담당한다.
prefill 계열 `embeddingGatherKernel`([`src/kernels.cu:32-53`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/kernels.cu#L32-L53))
이 프롬프트의 토큰들에 대응하는 것과 대비된다.

`ropeKernelDecode`([`src/kernels.cu:371-405`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/kernels.cu#L371-L405))
는 단일 블록 런치 `<<<1, num_threads>>>` 로 현재 위치 하나만 회전한다
([`src/kernels.cu:397`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/kernels.cu#L397)).
prefill 계열 `ropeKernel_llama3` 가 프롬프트 전체 위치에 회전을 적용하는 것과
달리, decode 는 위치 하나만 신경 쓰면 되므로 블록을 하나만 띄운다. RoPE
테이블을 사전 계산하느냐 호출마다 재계산하느냐까지 더한 대비는 다음 절에서
다룬다.

`softmaxKernelDecode`([`src/kernels.cu:408-458`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/kernels.cu#L408-L458))
는 `blockIdx.x * MAX_SEQ_LEN` 스트라이드로 행을 찾는다
([`src/kernels.cu:413`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/kernels.cu#L413)).
prefill 의 `softmaxKernel` 이 `num_tokens` 스트라이드를 쓰는 것
([`src/kernels.cu:262`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/kernels.cu#L262))
과 레이아웃 가정이 다르다. decode 버퍼가 슬롯 수×`MAX_SEQ_LEN` 크기로 잡혀
있다는 가정이 여기에 깔려 있다(trace.md:228-230).

다음 표는 두 계열의 대비를 한눈에 보여 준다.

## RoPE: 사전 계산 테이블과 호출마다 재계산

prefill 과 decode 는 RoPE 주파수를 얻는 방식에서도 갈린다(Claim 11,
claims.md:209-226).

prefill 계열은 사전 계산 테이블을 쓴다. `init_rope_frequencies`(호출
[`src/main.cpp:572`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/main.cpp#L572))
가 `d_inv_freq`, `d_cos_table`, `d_sin_table` 세 디바이스 배열을 할당·채우고
([`src/kernels.cu:96-152`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/kernels.cu#L96-L152)),
`ropeKernel_llama3` 는 테이블을 참조만 한다
([`src/kernels.cu:173-200`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/kernels.cu#L173-L200)).

반면 `ropeKernelDecode` 는 호출마다 `theta = 1/pow(500000, 2i/64)` 를 다시
계산한다
([`src/kernels.cu:371-384`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/kernels.cu#L371-L384)).
주파수 상수 `500000.0` 과 헤드 절반 `32` 를 하드코딩한다
([`src/kernels.cu:377-378`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/kernels.cu#L377-L378)).

한계: decode 계열의 재계산은 TODO 로 남아 있고(trace.md:231-233), 두 경로의
수치 일치는 실행 검증되지 않았다(claims.md:224-226). decode 커널이 왜 사전 계산
테이블을 쓰지 않는지, 두 경로가 정확히 같은 회전을 만드는지는 GPU 실행이 있어야
확인된다.

## decode 의 K/V 기록: 배치 투영과 블록 분산

decode 는 슬롯들의 K/V 를 배치 하나로 투영한다. `k_proj_batched_buffer`·
`v_proj_batched_buffer` 에 K/V 투영을 모은 뒤
([`src/main.cpp:802-842`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/main.cpp#L802-L842);
버퍼 할당
[`src/main.cpp:689-693`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/main.cpp#L689-L693))
슬롯별로 KV cache 블록에 흩는다(Claim 12, claims.md:227-245).

흩는 규칙은 [`src/main.cpp:851-873`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/main.cpp#L851-L873)
이다.

- `token_in_block_idx == 0` 일 때만 `free_blocks` 에서 새 물리 블록을 꺼내
  쓴다
  ([`src/main.cpp:856-865`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/main.cpp#L856-L865)).
- 그 외에는 기존 블록의 위치에 `cudaMemcpy`(D2D)로 기록한다
  ([`src/main.cpp:866-872`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/main.cpp#L866-L872)).

즉 decode 는 블록 하나가 채워질 때만 할당하고, 그 다음 토큰들은 이미 잡힌
블록에 덮어 쓴다. 매 레이어마다 `block_table` 전체를 `block_table_gpu` 로 H2D
동기화하는데
([`src/main.cpp:876`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/main.cpp#L876))
이것은 TODO 로 남아 있고
([`src/main.cpp:551`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/main.cpp#L551)),
그 비용은 측정되지 않았다(claims.md:242-244).

KV cache 의 블록 레이아웃과 `pagedAttentionKernel` 의 읽기 경로는 6편이
소유한다(guide.md:198-199). 여기서는 decode 스텝이 K/V 를 어떻게 쓰는지만
보여 줬다.

## 이 편이 확정한 것

- decode 계열 커널은 시퀀스 길이 1(슬롯당 토큰 1개)을 전제로 인덱싱 축을
  슬롯으로 바꾼다. `embeddingGatherKernelDecode` 는 `blockIdx.x` 를 슬롯으로
  삼고, `ropeKernelDecode` 는 단일 블록으로 현재 위치 하나만 회전하며,
  `softmaxKernelDecode` 는 `MAX_SEQ_LEN` 스트라이드를 가정한다.
- prefill 의 RoPE 는 `init_rope_frequencies` 가 사전 계산한 테이블을 참조하지만,
  `ropeKernelDecode` 는 호출마다 `theta = 1/pow(500000, 2i/64)` 를 재계산하고
  상수 `500000.0`·`32` 를 하드코딩한다.
- decode 는 슬롯별 K/V 를 배치 버퍼에 모은 뒤, `token_in_block_idx == 0`
  일 때만 `free_blocks` 에서 새 블록을 할당하고 그 외에는 기존 블록에 D2D 로
  기록한다.

## 한계와 미해결

- **실행 검증 없음.** 이 시리즈를 쓰는 환경에는 NVIDIA GPU 도 CUDA 툴체인도
  없다. 어떤 커널도 실행되지 않았고, 위 순서·상태 주장은 전부 소스 인용으로만
  뒷받침된다. 모든 편의 `required_evidence.runtime` 은 0 이다(guide.md:75-87).
- **레이아웃 가정 미검증.** `softmaxKernelDecode` 의 `MAX_SEQ_LEN` 스트라이드는
  prefill `softmaxKernel` 의 `num_tokens` 스트라이드와 다른 레이아웃 가정이며
  실행으로 확인되지 않았다.
- **수치 일치 미검증.** `ropeKernelDecode` 의 주파수 재계산은 TODO 로 남아
  있고, prefill 테이블 경로와 수치가 일치하는지 검증되지 않았다.
- **동기화 비용 미측정.** decode 는 매 레이어마다 `block_table` 전체를 H2D
  복사한다. 이 비용은 이 시리즈의 측정 원칙(성능 수치 없음)에 따라 측정하지
  않았다.
- **테스트는 정적 인용만.** `python/decode_test.py` 는 series.yaml 의
  code_scope 이며 required_evidence.tests 가 1 이지만, claims.md 에 이 테스트를
  직접 다루는 claim 은 없다. decode 계열 검증은 실행 없이 정적 인용으로만
  충족한다(briefs.md:150-151).
- **슬롯 해제·블록 반납은 7편.** decode 루프의 종료 검사는 이 편에서 순서만
  인용했고, EOS/EOT 토큰 처리와 `free_blocks` 반납 절차는 7편이 소유한다.
