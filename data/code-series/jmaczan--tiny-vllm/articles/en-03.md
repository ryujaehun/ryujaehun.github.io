# tiny-vllm Chapter 3 · Tokenizer, Embedding, and the First Token

Chapter 2 covered how `loadWeights` uploads the entire raw byte blob of a
safetensors file to the GPU in one chunk and then splits tensor pointers by
offset (`src/main.cpp:96-145`). Among those tensors, `embed_tokens` was a
pointer that had not yet been consumed. Chapter 3 follows the path where that
pointer is first used: turning the hardcoded prompt tokens into embedding
vectors and sampling the first generated token.

The implementation claims of this chapter converge on three threads. The
prefill path that gathers prompt tokens into embeddings supports Claim 3 (in
part), the path that gathers the last token in decode and picks the next token
on the CPU supports Claim 4 (in part), and the fact that the prompts are
hardcoded as token ID vectors from the start supports Claim 9 (in part).
Following the series' evidence rules, every claim cites a source path and line
range from the pinned commit (`guide.md:11-16`).

## Files and scope covered in this chapter

The target files for chapter 3 in `series.yaml` are `src/main.cpp` and
`python/tokenizer.py` (`series.yaml:10-12`). However, none of the evidence
claims (Claims 1–10) that this chapter may use supports anything inside
`python/tokenizer.py`. The actual account therefore comes entirely from
`src/main.cpp` and from `src/kernels.cu`, which receives its operations.
`python/tokenizer.py` belongs to the repository's set of Python reference
implementations (`evidence/recon.md:13`), but the tokenizer algorithm, vocab
handling, and special-token rules have no evidence behind them, so this chapter
does not describe them.

This chapter does not cover the inside of the transformer block
(RMSNorm·GEMM·attention). It only looks at the **two ends**: the prompt tokens
becoming embeddings, and those embeddings going through the final logits to
become the first token. The middle layer computations are the subject of
chapters 4 onward.

## The prompt is already a token

Before looking for the tokenizer, there is a fact to confirm. The program's
prompt is not a string but a hardcoded **token ID vector**
(`src/main.cpp:584-594`). Counting the elements, the four prompts are 17, 14,
13, and 14 tokens respectively (`evidence/trace.md:69`).

- PROMPT 0 — length 17 (`src/main.cpp:585`)
- PROMPT 1 — length 14 (`src/main.cpp:588`)
- PROMPT 2 — length 13 (`src/main.cpp:591`)
- PROMPT 3 — length 14 (`src/main.cpp:594`)

Consequently, there is no string→token conversion step in the C++ execution
path. The includes in `main.cpp` are only `iostream`, `numeric`, `fstream`,
`cuda_to_hip.h`, `queue`, `json.hpp`, and `kernels.cuh` (`src/main.cpp:1-8`),
and there is no socket or server layer. This means that even though the
repository has a separate Python tokenizer (`python/tokenizer.py`), this C++
program's input is already tokenized. This is the point that Claim 9
summarizes as "four fixed prompts in the queue" (`evidence/claims.md:99`).

The remaining two paths covered by this chapter take this token ID vector as
their starting point. Prefill turns the entire prompt into embeddings, while
decode turns one last token per slot into an embedding.

## embeddingGather: turning token IDs into vectors

The beginning of prefill (`src/main.cpp:150-553`) is the three steps that turn
tokens into embeddings.

1. **Prompt pop** — pop a prompt from the queue and occupy a slot (`:152-155`).
2. **Tokens to GPU** — copy the prompt token IDs into a device buffer (`:157`).
3. **`embeddingGather`** — gather the token IDs into embeddings (`:158`;
   `src/kernels.cu:42-53`).
4. **Copy to `hidden_state`** — move the gathered embeddings into the layer
   input buffer (`:160-163`).

The `embeddingGather` kernel gathers 2048 embedding elements per token, in a
batch of 1024 threads×2 (`src/kernels.cu:42-53`). The launch configuration is
blocks equal to the number of tokens and threads of 1024
(`evidence/trace.md:91-92`). The embedding table is the `embed_tokens` pointer
assigned by offset in chapter 2 (`src/main.cpp:132-145`).

The overall flow is as follows. Only the middle layer section is deferred to
chapter 4; this chapter connects the entrance and the exit.

```
token ID vector (gpu_input_tokens, :157)
        │  embeddingGather (:158; kernels.cu:42-53)
        ▼
input_embeddings (:620)
        │  copy (:160-163)
        ▼
hidden_state (:623)
        │  layers 0..15 — rmsNorm/RoPE/attention/MLP (from chapter 4)
        ▼
final rmsNorm (:494) → logit GEMM (:509-527) → D2H (:529) → CPU argmax (:533-543)
```

The fact that `embed_tokens` appears twice here shows the boundary of this
chapter. Once it is used as the input embedding in the entry gather (`:158`),
and once as the output projection matrix in the exit logit GEMM (`:509-527`).
Claim 3 records that prefill generates tokens via a logit GEMM after the final
`rmsNorm` (`evidence/claims.md:28`), and Claim 2 records the shape of that
logit GEMM as `m=VOCAB_SIZE, n=prompt_len, k=EMBEDDING_LENGTH`
(`evidence/claims.md:23`).

## The two gathers of prefill and decode

The decode loop only needs an embedding for one token per slot, so it uses a
different gather from prefill. Decode first copies each active slot's last
token and sequence length to the GPU (`src/main.cpp:749-757`), then calls
`embeddingGatherDecode` (`:759`; `src/kernels.cu:358-369`, kernel `:347-356`).
The block count of this kernel is the number of active slots
(`evidence/trace.md:141-142`).

| Item | prefill `embeddingGather` | decode `embeddingGatherDecode` |
|---|---|---|
| Call site | `src/main.cpp:158` | `src/main.cpp:759` |
| Wrapper | `src/kernels.cu:42-53` | `src/kernels.cu:358-369` |
| Input | each token of the prompt | the last token of each active slot |
| Grid blocks | number of tokens (`evidence/trace.md:91-92`) | number of active slots (`evidence/trace.md:141-142`) |
| Threads | 1024 (`evidence/trace.md:91-92`) | no evidence |
| Amount gathered | 2048 elements per token, 1024 threads×2 | 1 token per active slot |
| Owning claim | Claim 3 (in part) | Claim 4 (in part) |

While the prefill gather happens for the whole "prompt length" at once, the
decode gather happens for the "number of slots alive in this iteration." The
fact that the batch size is exactly the number of gather blocks is the starting
point of the batching structure revisited in chapters 6 and 7.

## From logits to the first token: CPU argmax

The exit after embeddings pass through the layers differs between prefill and
decode. However, the computation that picks the next token happens on the
**CPU** in both cases.

Prefill performs a final `rmsNorm` (`src/main.cpp:494`) followed by a logit
GEMM (`:509-527`), copies the logits to the CPU (`:529`), then picks the first
token by CPU argmax on the last token row (`:533-543`). The result is printed
(`:544`), and `generated_tokens`, `last_generated_tokens`, and
`current_prompt_len` are updated (`:546-548`). The first token stored in
`last_generated_tokens` becomes the gather input (`gpu_last_tokens`,
`:749-757`) of the next decode iteration.

Decode performs a final `rmsNorm` (`:974`) and logit GEMM (`:976-994`) after
the layers, copies the logits to the CPU (`:996`), then does an argmax per slot
(`:1000-1012`). This CPU argmax casts bf16 values to float before comparing
(`:1003-1010`). If the selected token is EOT/EOT_ID or the sequence reaches
`MAX_SEQ_LEN-1`, the slot is freed (`:1015-1031`); otherwise
`last_generated_tokens` and `generated_tokens` are updated and the length is
incremented by one (`:1032-1037`).

Claim 4 summarizes this structure as "batch the active slots together and run
the argmax on the CPU" (`evidence/claims.md:39`). The asymmetry that the
embedding gather is a GPU kernel while token selection is a CPU loop is the
key observation of this chapter.

## Verification path

The gather kernels and CPU argmax cited in this chapter have no corresponding
tests. The only unit test in the inventory is `tests/test_softmax.cu`
(`evidence/recon.md:12`). Therefore "does the gather read the correct embedding
row" and "does the argmax pick the correct token" are not confirmed by this

## Limitations

- This repository was not executed, so the runtime behavior of the gather and
  argmax could not be verified (`evidence/recon.md:4`). This chapter's
  procedural account is based on the source and trace notes.
- `python/tokenizer.py` is within the scope of chapter 3, but since none of
  Claims 1–10 address its internals, this chapter does not even cite the call
  relationship. The fact that "there is no string→token conversion in the C++
  path" comes from the source where the prompts are hardcoded as token ID
  vectors (`src/main.cpp:584-594`); it does not mean the tokenizer is absent.
- "2048 elements per token, 1024 threads×2" for `embeddingGather` is the
  phrasing of Claim 3 (`evidence/claims.md:34`), and the per-thread element
  mapping was not cited with a line-by-line breakdown. Only the launch
  configuration of blocks=number of tokens, threads=1024 is confirmed by the
  trace notes (`evidence/trace.md:91-92`).
- The thread count of decode's `embeddingGatherDecode` is not in the trace
  notes, so it was left blank in the table. Only blocks=number of active slots
  is confirmed (`evidence/trace.md:141-142`).
- The CPU argmax requires a D2H copy every decode iteration, and the source
  acknowledges this as a TODO (`src/main.cpp:531-532`, `:686`). This cost is
  only a structural observation, not something measured in execution time
  (`evidence/claims.md:47`).
- If `prompt_len > 1024`, prefill does not run the `causalMask`/`softmax`
  kernels and only prints a message (`src/kernels.cu:241-244`, `:295-298`).
  The prompts in this commit are 17 tokens or fewer, so this branch is never
  reached, but it remains a limitation of the general prefill path
  (`evidence/claims.md:35`).
- `embed_proj_cpu` is allocated with `MAX_BUFFER_SIZE*VOCAB_SIZE`, but prefill
  only copies `prompt_len*VOCAB_SIZE`, so the remaining rows may contain
  residual data from a previous slot (`src/main.cpp:681-682`, `:529`). This is
  an unresolved item left in the trace notes (`evidence/trace.md:240-242`),
  and this chapter does not claim anything about its impact.
- The tokenizer, vocab, and special-token rules are not described because there
  is no evidence for them. Format conversion and quantization paths that are
  absent from the repository are also not covered.

## Summary

Chapter 3 followed the path where the `embed_tokens` pointer is first consumed.
The prompts are not strings but four hardcoded token ID vectors (17·14·13·14)
(`src/main.cpp:584-594`), and there is no string→token conversion in the C++
path. Prefill gathers the prompt tokens into embeddings with `embeddingGather`
and puts them into `hidden_state` (`:158`, `:160-163`; `src/kernels.cu:42-53`),
then copies the final logits to the CPU and picks the first token with argmax
(`:509-543`). Decode gathers the last token of each active slot with
`embeddingGatherDecode` (`:759`; `src/kernels.cu:358-369`) and determines the
next token with a per-slot CPU argmax (`:1000-1012`).

The point of this chapter is that "both the input and the output are token IDs,
and the two ends between them are handled by the embedding gather and the CPU
argmax." The asymmetry remains that the embeddings are gathered by a GPU kernel
while token selection is a CPU loop. The next chapter fills in the middle that
this chapter left empty: the rmsNorm·RoPE·GEMM path through which
`hidden_state` passes through the layers.
