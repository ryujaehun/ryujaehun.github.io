# tiny-vllm Chapter 4 · Building the transformer block from RMSNorm, RoPE, and GEMM

Chapter 3 covered the state just before `hidden_state` enters the 16 layers.
This chapter reads what happens inside that doorway on a single pass through
the layer loop: the order in which computations are performed. The prefill
layer loop (`src/main.cpp:164-493`) starts with an input rmsNorm, goes through
attention and the SwiGLU MLP, and closes with a residual; after the final layer
come the final rmsNorm and the logits GEMM (`:494-548`).

The chapter's implementation claims converge on three points. The
transpose trick that aligns row-major memory with cuBLAS's column-major
convention is Claim 2, the overall execution order of the layer is Claim 3, and
the GQA constant reusing heads within that order is Claim 7 (reference).
Following the series' evidence rules, every claim cites source paths and line
ranges from the pinned commit (`guide.md:11-16`).

## Files and ranges covered in this chapter

Chapter 4's target files in `series.yaml` are `src/main.cpp` and
`src/kernels.cu` (`series.yaml:13-15`). The narrative focuses on the layer loop
(`:164-493`) inside `prefill` (`src/main.cpp:150-553`) and the final cleanup
after it (`:494-548`). `src/kernels.cu` appears as the location of the kernels
that the loop calls.

This chapter treats attention as one step in the layer order, deferring the

constant needed by the attention step are verified in this chapter.

## The full order of one pass through the layer loop

`prefill` gathers the prompt tokens into embeddings with `embeddingGather` and
copies them into `hidden_state` (`src/main.cpp:158`, `:160-163`), then runs
through 16 layers with `layer=0..15` (`:164-493`; `evidence/trace.md:94`). The
order within each layer matches exactly what Claim 3 lays out
(`evidence/claims.md:28`).

```
hidden_state (layer input)
  │  rmsNorm (:166)
  ▼
rms_norms
  │  Q/K/V projection GEMMs (:177-240)
  ▼
q_proj · k_proj_temp_buf · v_proj_temp_buf
  │  RoPE (:244-245)
  ▼
  │  KV scatter (:247-288) ──────────▶ kv_cache (Chapter 5)
  ▼
attention: score GEMM (:301-327) → causalMask (:329) → softmax (:331)
           → scores×V (:343-371)   (details in Chapter 5)
  ▼
attn_scores_v
  │  o_proj GEMM (:377-396)
  ▼
  │  residualAdd (:399) → post-attn rmsNorm (:401)
  ▼
SwiGLU MLP: gate (:414-432) · up (:435-453) · silu (:459) · down (:470-489)
  │  residualAdd (:492)
  ▼
next layer (layer+1) / final rmsNorm if last layer (:494)
```

After the loop closes, the final `rmsNorm` (`:494`) → logits GEMM (`:509-527`)
→ D2H copy (`:529`) → CPU argmax (`:533-543`) → state update (`:546-548`)
follow in order.

## The cuBLAS transpose trick: interpreting row-major memory as column-major

Before starting the Q projection, the first computation of the layer, one reads
the single principle shared by every GEMM in this program. The source stores
data in row-major memory shaped (token, dimension), but cuBLAS follows the
column-major convention. The source resolves this mismatch not by transposing
but by **switching perspectives**. A comment spells out the trick
(`src/main.cpp:168-176`).

```
actual row-major data:  inputs (prompt_len, 2048),  w_q (2048, 2048)
cuBLAS perspective:     inputsᵀ (2048, prompt_len), w_qᵀ (2048, 2048)

intended:  Q = inputs * w_qᵀ
via trick: Qᵀ = w_qᵀ * inputs       ← CUBLAS_OP_T(w_q) · CUBLAS_OP_N(inputs)
output (column-major): (2048, prompt_len)
```

The key point is that the trick's conclusion is "you don't need to transpose
the output again" (`src/main.cpp:173-176`). Because cuBLAS views the output as
column-major, the mathematical `Qᵀ` has the same layout in actual memory as a
row-major array shaped `(num_tok, EMBEDDING_LENGTH)`. In other words, a single
GEMM yields the target array in place. Claim 2 summarizes this principle as
`Q^T = w_q^T * inputs` (`evidence/claims.md:18`).

The Q projection call carries the trick straight into its arguments.
`cublasGemmEx` specifies `CUBLAS_OP_T, CUBLAS_OP_N` with
`m=EMBEDDING_LENGTH, n=prompt_len, k=EMBEDDING_LENGTH`
(`src/main.cpp:177-196`). Here the first argument `weights.w_q[layer]` is the
one being transposed, and the second argument `rms_norms` (the rmsNorm result)
is the one used as-is. The dimensional rationale for the Q projection is
recorded in Claim 2 (`evidence/claims.md:22`).

## rmsNorm: a kernel that normalizes 2048 dimensions

rmsNorm is applied to the layer input first (`src/main.cpp:166`). The same call
is repeated after attention (`:401`) and after the final layer (`:494`), so it
is not explained again in this chapter. The wrapper `rmsNorm` is at
`src/kernels.cu:84-94` and the kernel `rmsNormKernel` at `:55-81`
(`evidence/trace.md:95`).

The kernel assigns 1024 threads to the 2048 elements of each token
(`src/kernels.cu:55-81`), reduces the sum of squares into a shared array via
tree combination (`:57-75`), then divides by the RMS value and multiplies by
the weight (`:78-79`). The three call sites use the per-layer
`input_layernorm` (`src/main.cpp:136`), `post_attention_layernorm` (`:140`),
and the final `norm` (`:133`), weights assigned by offset in Chapter 2.

## Q/K/V projection: where the dimensions split

The normalized `rms_norms` feeds three projection GEMMs. Q uses
`m=EMBEDDING_LENGTH=2048` (`src/main.cpp:177-196`), while K and V use
`m=KV_DIM=512` (`:201-219`, `:222-240`), all in the transpose trick's
`CUBLAS_OP_T/CUBLAS_OP_N` call form. The dimension difference between Q and
K/V is recorded by the trace memo (`evidence/trace.md:96-99`).

The output buffers also split according to dimension. The Q projection result
is written to `buf_2048_1`, a buffer later shared with the scores×V output
(`attn_scores_v`) (`src/main.cpp:628-629`, `evidence/trace.md:79-80`). K and V
are written to the temporary buffers `k_proj_temp_buf` (`:636`) and
`v_proj_temp_buf` (`:639`), from which they are scattered into the KV cache
across layers (`evidence/trace.md:74-75`).

That all three GEMMs use bf16 weights and compute with `CUBLAS_COMPUTE_32F`
(`:194-196` etc.) is a side observation about how data is stored as it passes
through the layer.

## RoPE: fetching position information from the cos/sin table and applying it

Right after the Q and K projections, RoPE is applied to both buffers.
`rope(q_proj, prompt_len, EMBEDDING_LENGTH)` (`src/main.cpp:244`) and
`rope(k_proj_temp_buf, prompt_len, KV_DIM)` (`:245`). V gets no RoPE. The
wrapper is at `src/kernels.cu:202-222` and the kernel `ropeKernel_llama3` at
`:173-200`.

The cos/sin table RoPE uses is built once at startup. `main` calls
`init_rope_frequencies(HEAD_DIM, MAX_SEQ_LEN, 500000, 32, 1, 4, 8192)`
(`src/main.cpp:572`); the function computes `inv_freq`, applies the Llama3 NTK
scaling (`src/kernels.cu:100-124`), fills `[max_seq_len, head_dim]`-shaped
`cos_table`/`sin_table`, and copies them to the device (`:129-151`). The tables
are kept in the global pointers `d_cos_table`/`d_sin_table` (`:22-24`), and the
kernel reads the per-position `(cos, sin)` pair to rotate the two elements
(`:194-199`). The arguments at `main.cpp:572` line up with the parameter order
of `init_rope_frequencies` (`src/kernels.cu:96-98`) as `rope_theta=500000,
factor=32, low_freq_factor=1, high_freq_factor=4, original_max_len=8192`.

## The attention slot and GQA constants

The KV scatter after RoPE (`src/main.cpp:247-288`) is outside this chapter's
scope (Chapter 5). Two things are verified about the attention step here.

First, the head structure. Q has 32 heads, K/V have 8, and the ratio constant
is `GQA_Q_TO_K_RATIO=4` (`src/main.cpp:20-24`). In the attention score loop the
mapping is `k_head_idx = i / GQA_Q_TO_K_RATIO` (`:303`), and in the scores×V
loop `v_head_idx = i / GQA_ATTN_SCORES_TO_V_RATIO` (`:346`), so 4 consecutive
Q heads share 1 K/V head. This GQA structure is Claim 7 (`evidence/claims.md:71`,
head mapping rationale `:74-76`).

Second, the score scale. `attn_alpha` in the score GEMM is defined as
`1.0f / 8.0f` (`src/main.cpp:649`, `evidence/trace.md:108-110`). It is the
inverse square root of `HEAD_DIM=64` (`1/8`). Scores are computed as a
`(prompt_len, prompt_len)` matrix (`:301-327`), then go through `causalMask`
(`:329`; `src/kernels.cu:239-255`, kernel `:224-237`) and `softmax` (`:331`;
`src/kernels.cu:293-309`, kernel `:257-290`), then the scores×V GEMM
(`:343-371`). What each step does within this one-line flow is filled in by
Chapter 5.

## o_proj · residual · SwiGLU MLP

The attention output `attn_scores_v` passes through the `o_proj` GEMM and is
written to `buf_2048_2` (`src/main.cpp:377-396`). `buf_2048_2` is a buffer
shared with the MLP's down projection output (`:656-657`,
`evidence/trace.md:79-80`). Then `residualAdd(hidden_state, o_proj,
prompt_len)` adds the input back (`:399`; `src/kernels.cu:319-329`, kernel
`:311-316`), the post-attn rmsNorm follows (`:401`), and its normalized result
becomes the MLP input.

The MLP has a SwiGLU structure in five steps. gate (`src/main.cpp:414-432`) and
up (`:435-453`) are transpose GEMMs of identical form with `m=HIDDEN_DIM=8192`;
`silu` overwrites the gate in place with `SiLU(gate)*up` (`:459`;
`src/kernels.cu:341-344`, kernel `:331-338`). A down projection
(`src/main.cpp:470-489`) is applied to the result, and `residualAdd` adds the
input back again (`:492`), closing the layer. The trace memo summarizes these
five steps (`evidence/trace.md:118-121`).

## Final rmsNorm and logits GEMM

Once the 16 layers finish, the final `rmsNorm` (`src/main.cpp:494`, weight
`norm`) is applied and the logits GEMM runs. Logits multiply `embed_tokens`
(the embedding table, the pointer at `:132` assigned in Chapter 2) transposed,
which by the transpose trick becomes a `CUBLAS_OP_T/CUBLAS_OP_N` call with
`m=VOCAB_SIZE, n=prompt_len, k=EMBEDDING_LENGTH` (`:509-527`). The dimensional
and transpose rationale for the logits GEMM transposing `embed_tokens` and
multiplying with `m=VOCAB_SIZE` is recorded in Claim 2 (`evidence/claims.md:23`).
The source comment leaves behind the row-major/column-major reasoning for how
`logits^T = embed_tokens * rms_norms^T` comes about (`:496-507`).

Logits are copied to the CPU (`:529`), and the next token is selected from the
last token row (`:533`) by a CPU-loop argmax (`:533-543`). The result is
printed (`:544`) and the state is updated (`:546-548`). The asymmetry Chapter 3
observed — "embeddings via GPU kernels, token selection via CPU loop" —
persists after passing through the layers.

## Verification path

The rmsNorm, GEMM, and attention kernels cited in this chapter have no

makes in which order"; it does not claim that the numerical results are

## Limitations

- The numerical correctness of the transpose trick is not confirmed by tests.
  The only kernel unit test is `tests/test_softmax.cu`
  (`evidence/claims.md:24`).
- For `prompt_len > 1024`, the `causalMask`/`softmax` kernels do not run and
  only print a message (`src/kernels.cu:241-244`, `:295-298`). The prompts in
  this commit are 17 tokens or fewer, so this is not reached, but it remains a
  limitation of the general prefill path (`evidence/claims.md:35`).
- The GQA ratio (4) is hard-coded as a constant, so a change to the model
  structure requires recompilation (`src/main.cpp:20-24`,
  `evidence/claims.md:78`).
- The layer loop range is written as `src/main.cpp:164-493`. The closing brace
  of the for loop is at `:493`, and the trace memo uses the same range
  (`evidence/trace.md:94`).
- `attn_alpha = 1/8` appears to be the inverse square root of `HEAD_DIM=64`,
  but the only rationale is the source constant (`src/main.cpp:649`); the
  formula derivation is left to Chapter 5.
- This chapter makes no performance claims. Expressions such as "bottleneck"
  or throughput have no basis and are avoided.

## Summary

Chapter 4 read the execution order of one pass of `hidden_state` through the
16 layers (`src/main.cpp:164-493`). Each layer proceeds input rmsNorm (`:166`)
→ Q/K/V projections (`:177-240`) → RoPE (`:244-245`) → KV scatter (`:247-288`)
→ attention (`:301-371`) → o_proj (`:377-396`) → residualAdd (`:399`) →
post-attn rmsNorm (`:401`) → SwiGLU MLP (`:414-492`), and after the last layer
come the final rmsNorm (`:494`) → logits GEMM (`:509-527`) → CPU argmax
(`:533-543`).

The principle running through all of it is the cuBLAS transpose trick.
Interpreting row-major memory as column-major lets a single
`CUBLAS_OP_T/CUBLAS_OP_N` call yield the target array without transposing
(`:168-176`, `:177-196`, `:509-527`; `evidence/claims.md:18-23`). Q and K/V
split into 2048/512 dimensions (`evidence/trace.md:96-99`), and with the GQA
ratio of 4, Q's 32 heads share K/V's 8 heads (`src/main.cpp:20-24`, `:303`,
`:346`). Notably, the trick repeats in the same form all the way to the logits
GEMM. The next chapter moves into the attention scores and KV cache that this
chapter only briefly touched on.
