# tiny-vllm Chapter 7 · static batching

Chapter 6 read prefill and decode as two distinct units of work. This chapter tackles the stage those two paths ride on — the **batch** — head-on. tiny-vllm's batch is a fixed pair of slots governed by `BATCH_SIZE=2`. The source comment explains this constant in exactly one line: "just here to have batching"(`src/main.cpp:29`). This chapter covers how the batch is fixed at 2, the lifecycle a slot travels from occupancy to release, and the point at which release returns KV blocks.

The chapter's primary claim is Claim 9 (`BATCH_SIZE=2` fixed-slot batching); the way decode batches active slots at once is pulled in as a reference to Claim 4. Following the series' evidence rules, every claim is cited with the fixed commit's source paths and line ranges (`guide.md:11-16`).

## Files and scope covered by this chapter

Chapter 7 of `series.yaml` targets a single file, `src/main.cpp`(`series.yaml:22-24`). The claims and evidence used are as follows.

- **Claim 9 (primary)** — `BATCH_SIZE=2` fixed-slot batching. The initial loop prefills the queue's first 2 prompts into slots 0 and 1, and on a termination condition (EOT/EOT_ID or `MAX_SEQ_LEN-1`) releases the slot and returns its blocks to `free_blocks`. Evidence: `src/main.cpp:29`, `:695-708`, `:1015-1037`, `:584-594`(`evidence/claims.md:90-100`).
- **Claim 4 (reference)** — decode batches active slots together at once, processing them as a batch of `n=num_active_slots`. Evidence: `src/main.cpp:722-737`, `:763-842`.

An important boundary is the part of Claim 9 that reads "when a free slot appears, prefill is filled in immediately even during decode"(`src/main.cpp:726-737`). That is the subject of continuous batching, so it is deferred to Chapter 8(`briefs.md:177`). This chapter describes only the slot fixity and lifecycle.

## The batch's skeleton: two slots and a queue

The batch's skeleton comes from constants. The number of slots is fixed at `BATCH_SIZE=2`(`src/main.cpp:29`), and the maximum sequence length at `MAX_SEQ_LEN=2048`(`src/main.cpp:12-38`; `evidence/trace.md:27`). This batch is nothing more than two places called "slots." Whether a slot is occupied is tracked by the 2-element `is_slot_free` array(`:597`), and each slot carries three pieces of state: `generated_tokens`, `last_generated_tokens`, and `current_prompt_len`(`:599-601`). Since the batch size is a compile-time constant, the batch width (number of active slots) discussed in this chapter can never exceed 2.

The input is a hardcoded queue. Four prompts, 17/14/13/14 tokens long, are pushed onto `queue`(`src/main.cpp:584-594`; `evidence/trace.md:69`). With only 2 batch slots and 4 prompts, the queue is not consumed all at once and lingers behind. The initial prefill loop(`:695-708`) takes 2 prompts from the queue and places them in slots 0 and 1. This is where the batch's "static" character is determined.

## Initial prefill: filling slots 0 and 1

The initial prefill is a short loop. It iterates `for slot in 0..BATCH_SIZE` and, while `!queue.empty()`, calls `prefill` on the free slots(`src/main.cpp:695-708`). Since `BATCH_SIZE=2`, this loop places the queue's prompts 1 and 2 into slots 0 and 1(`evidence/trace.md:84-85`). Prompts 3 and 4 remain in the queue at this point.

The prefill function marks the slot occupied as soon as it takes a prompt out of the queue(`src/main.cpp:152-155`). An occupied slot has `is_slot_free` set to `false`(`:155`), and once prefill finishes, `current_prompt_len[slot]` is set to the prompt length(`:548`). This completes the first phase of the slot lifecycle. From here, these slots are batched together in the decode loop.

## Decode: batching active slots at once

The decode loop(`src/main.cpp:720-1039`) rebuilds the list of active slots on every iteration. `active_slots`/`active_tokens` regather the slots to be processed in the current iteration(`:722-737`). Mixed into this reconstruction step is the part that immediately prefills the queue's prompts into free slots; the details of that continuous batching are covered in Chapter 8.

The number of active slots is exactly this iteration's batch size. `embeddingGatherDecode` gathers input embeddings using a block count equal to the **number of active slots**(`:759`; `src/kernels.cu:358-369`), and the Q/K/V projection GEMMs run with `n=num_active_slots`(`:763-842`). The structure Chapter 6 described as decode "binding 1 token per slot and processing them together" forms the batch here. Since there are only 2 slots, `num_active_slots` can never exceed 2, whatever value 0, 1, or 2 it takes. This is precisely the point where the batch size being "static" shows itself: the width of the computation is bounded from above not by the queue's state or the number of requests, but by the compile-time-fixed number of slots.

When `num_active_slots==0`, the loop-termination decision occurs. If the queue is empty it `break`s(`:739-744`); if the queue still has items it `continue`s(`:745`).

## Termination and slot release

At the end of each decode iteration, a per-slot termination check runs(`src/main.cpp:1015-1037`). If argmax is `END_OF_TEXT_TOKEN_ID`(128001) or `EOT_ID_TOKEN_ID`(128009), or `current_prompt_len == MAX_SEQ_LEN-1`(=2047), the slot is released(`evidence/trace.md:169-171`); otherwise, the generation state is updated and `current_prompt_len` is incremented by 1(`:1032-1037`).

Slot release resets four pieces of state at once(`:1015-1031`).

| State | On release | Evidence |
|---|---|---|
| `is_slot_free[slot]` | restored to `true` | `:1017` |
| `free_blocks` | pushes the slot's physical blocks | `:1025` |
| `block_table` | resets the released slot's row to -1 | `:1026` |
| `block_table_gpu` | H2D re-sync | `:1030` |

This is where the batch and memory meet. The `free_blocks` stack from Chapter 5(`src/main.cpp:577-578`) owns the slot's KV blocks, and slot release returns those blocks to the stack. In other words, a slot is simultaneously a unit of computation and a unit of KV memory. Resetting the block table row to -1(`:1026`) marks that the physical block no longer belongs to this sequence. The subsequent `block_table_gpu` re-sync(`:1030`) makes the GPU-side table aware of the same fact.

## Slot lifecycle

Summarizing the two slots' lifecycles in a state table gives the picture of static batching.

| Stage | Slot 0 | Slot 1 | Evidence |
|---|---|---|---|
| Initialization | free | free | all `is_slot_free` are `true`(`:597`) |
| Initial prefill | P1 occupied | P2 occupied | `:695-708`, occupancy `:155` |
| Decode iteration | token generation, `current_prompt_len` +1 | token generation, +1 | `:1032-1037` |
| Termination condition | EOT/`MAX_SEQ_LEN-1` reached | EOT/`MAX_SEQ_LEN-1` reached | `:1015-1031` |
| Release | returns to free, blocks returned | returns to free, blocks returned | `:1017`, `:1025` |

Viewed as a timeline, the two slots each end their lifecycles independently.

```
Queue:  P1(17)  P2(14)  P3(13)  P4(14)          ← 4 hardcoded prompts (:584-594)
        │       │
        ▼       ▼
Initial prefill : P1·P2 into slots 0·1  (:695-708)
        │       │
        ▼       ▼
Decode iteration : 1 token per slot per iteration  (:720-1039)
        ▼       ▼
Slot 0: tok→tok→…→EOT ──────→ release (:1015-1031)
Slot 1: tok→tok→…→EOT ──────→ release
                                  │
                                  ▼
                  queue empty, active 0 → break (:739-746)
```

The point where the batch size is fixed can be highlighted with the following diagram. The slot pool (2 places) is the upper bound of the computation width along the batch dimension.

```
                 BATCH_SIZE=2 (:29)
                   ┌──────────┐
                   │  Slot 0   │──┐
                   │  Slot 1   │──┼─→ active_slots reconstruction (:722-737)
                   └──────────┘  │      → num_active_slots ∈ {0,1,2}
                                 ▼
                 embeddingGatherDecode  blocks = active slot count (:759)
                 Q/K/V GEMM             n=num_active_slots  (:763-842)
```

`num_active_slots` is the batch size, and its value is bounded by the slot count. Since the computation width along the batch dimension cannot exceed `BATCH_SIZE=2`, the batch is fixed to the slot count rather than to the number of requests.

## Limitations

- `MAX_NEW_TOKENS_GENERATED`(`src/main.cpp:12`) is only declared and never used in a loop condition. The decode loop exits only when the queue is empty and `num_active_slots==0`(`:739-746`), so even after the queue empties, the loop continues until every slot reaches its termination condition(`evidence/claims.md:100`).
- Slot release happens only on a termination condition. When the next queue prompt enters a slot after release is outside this chapter's scope; Chapter 8 describes it.
- The initial prefill loop carries the `!queue.empty()` condition(`:695-708`), so if the queue is empty, the decode loop starts with free slots left over.
- The word "static" in this chapter refers only to a batch structure with a fixed slot count; it does not mean "a batch that starts at once never changes until completion." Active slots are reconstructed every iteration(`:722-737`).
- This chapter makes no performance claims. Whether `BATCH_SIZE=2` is a good size, or how long it takes to process the 4 prompts in total, has no evidence in Claims 1–10, so it is not written here.

## Summary

This chapter read tiny-vllm's batch as a fixed skeleton of "2 slots." The batch size is set at compile time to `BATCH_SIZE=2`(`src/main.cpp:29`), and the initial prefill loop places the queue's 2 prompts into slots 0 and 1(`:695-708`). The decode loop reconstructs the active slots every iteration(`:722-737`) and, using their count as the batch size, runs the Q/K/V GEMMs with `n=num_active_slots`(`:763-842`). A slot is released at EOT/EOT_ID or `MAX_SEQ_LEN-1`(`:1015-1031`), and release simultaneously restores `is_slot_free`, returns the physical blocks, resets the block table row to -1, and re-syncs the GPU table(`:1017`, `:1025`, `:1026`, `:1030`).

This structure is the starting point for Chapter 8. The moment a slot is released is exactly the moment blocks are returned to `free_blocks`(`:1025`), and the `block_table_gpu` re-sync happens right after(`:1030`). Chapter 8 picks up the continuous batching in which the next queue prompt immediately enters the released slot, and the per-layer block table re-sync (Claim 10). This chapter covers the batch's fixity; Chapter 8 covers its reuse.
