# tiny-vllm 2장 · Safetensors와 Llama 가중치 적재

1장은 `main()`의 최상위 9단계만 훑고, 두 번째 단계인 `loadWeights(weights)`의
내부를 이 장으로 넘겼다. 그 호출은 실패하면 `main`이 `return 1`로 끝나는
지점이다(`src/main.cpp:566-569`). 이 장은 `loadWeights`(`src/main.cpp:79-147`)를
열어, Llama 가중치가 어떤 형식으로 디스크에 놓여 있고 어떻게 GPU 메모리로
올라가는지를 따라간다.

이 장의 구현 주장은 Claim 1 하나에 모여 있다. 시리즈의 증거 규칙대로 모든
주장은 고정 커밋의 소스 경로와 줄 범위로 인용하고, README 설명은 보조 근거로만
둔다(`guide.md:11-16`). 1장이 `main()`의 지도였다면, 2장은 그 지도에서
"가중치 로드" 상자를 처음으로 확대한다.

## 이 장이 다루는 파일과 범위

`series.yaml` 2장의 대상 파일은 `src/main.cpp`와 `include/json.hpp`다
(`series.yaml:7-9`). 실제 구현은 `src/main.cpp`의 `loadWeights`(`:79-147`)에
있고, `include/json.hpp`는 이 함수가 safetensors 헤더의 JSON을 파싱할 때 쓰는
서드파티 단일 헤더다.

`include/json.hpp`는 25830줄로 저장소에서 가장 큰 파일이다
(`evidence/recon.md:15`). Claim 1은 이 헤더의 파싱 세부를 검증 범위 밖으로
명시한다(`evidence/claims.md:14`). 따라서 이 장은 `json.hpp`의 내부 구현을
서술하지 않고, `loadWeights`가 JSON 헤더를 읽고 해석하는 지점만 인용한다.

이 장은 또한 가중치 로딩을 실제 `model.safetensors` 파일로 실행해 검증하지
않는다. Claim 1의 한계가 그 점을 못 박는다(`evidence/claims.md:14`). 소스에
드러난 절차를 읽을 뿐, 메모리 배치를 런타임에 확인한 것처럼 쓰지 않는다.
저장소에 없는 포맷 변환·양자화 처리도 다루지 않는다.

## safetensors: 헤더가 텐서 배치를 설명하는 형식

코드를 읽기 전에 파일 형식부터 잡자. safetensors는 텐서 데이터를 자체
직렬화하지 않고, "어디에 무엇이 있는지"를 헤더에 적어 두는 컨테이너에 가깝다.
`loadWeights`가 가정하는 배치는 세 부분이다.

```
┌────────────────────┬──────────────────────────┬─────────────────────────────┐
│ 8바이트 헤더 길이 N │ JSON 헤더 (N바이트)       │ 원시 텐서 바이트             │
└────────────────────┴──────────────────────────┴─────────────────────────────┘
                      │
                      └─ 텐서 이름 → { dtype, shape, data_offsets: [begin, end) }
                         특수 키 __metadata__ → 문자열 메타데이터 (텐서 아님)
```

- **8바이트 헤더 길이** — JSON 헤더가 몇 바이트인지 알려준다. 소스는 이 값을
  `uint64_t`로 읽는다(`src/main.cpp:96-97`).
- **JSON 헤더** — 텐서 이름을 키로, 각 텐서의 `dtype`·`shape`·
  `data_offsets`를 값으로 담는다. `data_offsets`는 `[begin, end)` 반열림
  구간이며, 원시 바이트 구역의 시작을 0으로 둔 상대 위치다. 이 해석은 코드가
  `data_offsets`의 종료값을 할당 크기로 쓰는 방식에서 나온다(아래).
- **원시 텐서 바이트** — 헤더 뒤에 이어지는 실제 가중치 바이트다. 텐서들이
  이 구역 안에 연속으로 놓인다.

`__metadata__`는 텐서가 아니라 헤더에 딸린 문자열 메타데이터 키다.
`loadWeights`는 맵을 만들 때 이 키를 건너뛴다(`src/main.cpp:108-111`).

## loadWeights: 준비부터 H2D 복사까지

`loadWeights`의 실행 순서는 다음과 같다. 1장에서 확인한 `main()`의 두 번째
단계가 여기서 펼쳐진다.

1. **GPU 확인** — `checkGPUStatus()`를 먼저 호출한다(`src/main.cpp:81-84`).
   정의는 `:40-62`에 있고, 디바이스 수가 0이면 `1`을 반환해 로딩을 중단시킨다.
2. **파일 열기** — `model.safetensors`를 바이너리로 연다(`:87-93`). 실패하면
   `1`을 반환한다.
3. **헤더 길이 읽기** — 8바이트를 `uint64_t`로 읽어 JSON 헤더 크기를
   얻는다(`:96-97`).
4. **JSON 헤더 읽기·파싱** — 헤더 바이트를 읽어 파싱한다(`:99-101`).
5. **이름→오프셋 맵과 `max_offset`** — 각 텐서의 `data_offsets`를 모아 맵을
   만들고, 종료값 `data_offsets[1]`의 최대치를 `max_offset`으로 저장한다
   (`:103-118`; 최대치 계산 `:105-115`). `__metadata__`는 여기서
   제외된다(`:108-111`).
6. **GPU 할당** — `cudaMalloc`으로 `model_weights`를 `max_offset` 크기로
   잡는다(`:120-121`).
7. **원시 바이트를 CPU 버퍼로** — 가중치 원시 바이트를 CPU 벡터로 읽는다
   (`:123-125`).
8. **H2D 복사** — CPU 버퍼를 GPU로 한 번에 복사한다(`:127`).
9. **텐서 포인터 배정** — 각 텐서 포인터를 오프셋 기준으로 설정한다
   (`:132-145`).

이 순서에서 `max_offset`의 의미가 핵심이다. 모든 텐서의 종료 오프셋 중 가장
큰 값이므로, 원시 바이트 구역 전체를 담는 크기다. 그래서 6번의 할당 하나로
모든 텐서를 수용하고, 8번의 복사 한 번으로 전부 GPU에 올릴 수 있다.
Claim 1이 "원시 바이트 전체를 1회 H2D 복사"라고 요약하는 지점이다
(`evidence/claims.md:8`, `src/main.cpp:120-127`).

## 오프셋에서 텐서 포인터로

8번까지 마치면 GPU에는 `max_offset` 크기의 평평한 바이트 덩어리 하나가 있다.
9번은 이 덩어리 위에 이름을 붙이는 단계다. 각 텐서의 시작 오프셋을 기준으로
포인터를 계산하면, 별도의 텐서별 복사 없이 `model_weights + begin` 형태의
포인터가 나온다. `:132-145`가 배정하는 텐서 묶음은 다음과 같다.

| 텐서 | 역할(다음 장 이후) | 근거 |
|---|---|---|
| `embed_tokens` | 토큰 임베딩 gather, 최종 로짓 GEMM | `src/main.cpp:132-145` |
| `norm` | 최종 RMSNorm | `src/main.cpp:132-145` |
| `input_layernorm` (레이어별) | attention 전 RMSNorm | `src/main.cpp:132-145` |
| `post_attention_layernorm` (레이어별) | MLP 전 RMSNorm | `src/main.cpp:132-145` |
| `mlp_down_proj` / `mlp_gate_proj` / `mlp_up_proj` (레이어별) | SwiGLU MLP | `src/main.cpp:132-145` |
| `w_k` / `w_o` / `w_q` / `w_v` (레이어별) | attention Q/K/V/o 투영 | `src/main.cpp:132-145` |

Claim 1은 `:132-145`의 배정 목록을 `embed_tokens`, `norm`, 그리고 레이어별
`input_layernorm`/`mlp_*`/`w_k/w_o/w_q/w_v`로 정리한다(`evidence/claims.md:13`).
`post_attention_layernorm`은 같은 범위를 세분해 추적한 `trace.md`가 추가로
기록한 항목이다(`evidence/trace.md:44-46`).

이 시점의 포인터는 아직 쓰이지 않는다. `loadWeights`는 주소만 준비하고,
가중치는 이후 prefill의 투영·MLP·최종 로짓 GEMM에서 읽힌다. 예를 들어
`embed_tokens`는 prefill 마지막의 로짓 GEMM에서 전치 대상으로 등장한다
(`src/main.cpp:509-527`). 그 소비 지점은 4장 이후의 주제다.

## 검증 경로

이 장이 인용한 로더에는 대응하는 테스트가 없다. 인벤토리에서 유일한 단위
테스트는 `tests/test_softmax.cu` 하나뿐이다(`evidence/recon.md:12`). 따라서
"오프셋 기반 포인터 배정이 실제 파일에서 올바른 텐서를 가리키는가"는 이
시리즈의 근거로 확인되지 않는다. 이 장은 로더의 정확성을 주장하지 않는다.

## 이 장에서 다루지 않는 것

- `include/json.hpp` 내부 구현 — 서드파티이고 Claim 1이 범위 밖으로 둔다
  (`evidence/claims.md:14`).
- 실제 `model.safetensors` 파일의 메모리 배치를 런타임 검증한 결과.
- 저장소에 없는 포맷 변환·양자화 처리.
- 토크나이저와 임베딩(3장), transformer block(4장), attention과 KV
  캐시(5장), paged attention(10장).

## 한계

- 이 저장소를 실행하지 않아 `loadWeights`의 메모리 배치를 실제 파일로
  검증하지 못했다(`evidence/recon.md:4`). 이 장의 절차 서술은 소스와 추적
  메모를 근거로 한다.
- `json.hpp`는 25830줄 서드파티 헤더이며, JSON 파싱의 세부 동작은 검증 범위
  밖이다(`evidence/recon.md:15`, `evidence/claims.md:14`). 이 장은 호출
  지점(`src/main.cpp:99-101`)만 인용한다.
- 텐서 포인터가 시작 오프셋(`data_offsets[0]`)을 기준으로 계산된다는 서술은
  "오프셋 기준 배정"이라는 Claim 1의 표현과 파일 형식 관례에서 나온 것이다.
  `:132-145`의 텐서별 정확한 오프셋 인덱싱은 이 장에서 줄 단위로 분해해
  인용하지 않았다.
- `__metadata__`를 건너뛴다는 사실은 소스로 확인되지만(`src/main.cpp:108-111`),
  "텐서가 아니라 메타데이터 키이기 때문"이라는 이유 설명은 형식 해석이다.
- 로더 전용 테스트가 없어 오프셋 기반 배정의 정확성은 테스트로 뒷받침되지
  않는다. 유일한 테스트는 `tests/test_softmax.cu`다
  (`evidence/recon.md:12`).
- 저장소에 없는 포맷 변환·양자화 경로는 서술하지 않는다.

## 정리

2장은 `main()`의 "가중치 로드" 상자를 열었다. `loadWeights`는 safetensors
파일의 8바이트 헤더 길이를 읽고(`src/main.cpp:96-97`), JSON 헤더를 파싱한 뒤
(`:99-101`), 각 텐서 `data_offsets`의 최대 종료값을 `max_offset`으로 잡는다
(`:103-118`). 그 크기로 GPU 메모리를 한 번 할당하고(`:120-121`), 원시 바이트를
CPU로 읽어(`:123-125`) 한 번의 H2D 복사로 올린 다음(`:127`), 오프셋 기준으로
텐서 포인터를 배정한다(`:132-145`). `__metadata__`는 텐서가 아니므로
제외된다(`:108-111`).

이 설계의 요점은 "한 덩어리로 올리고 주소만 나눈다"는 것이다. 다음 장은 이
포인터 중 `embed_tokens`를 사용해 하드코딩된 프롬프트 토큰을 임베딩으로
바꾸고, 첫 토큰을 향한 순전파를 시작한다.
