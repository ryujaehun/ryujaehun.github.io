# 5. The decode path that produces a single token

Every path and line number in this article refers to the tree at the fixed
revision `e25bf1994efa90bc98b721ba7c527402f86fbeaf`. Notation is in
`file:start-end` form, and these are source citations, not execution results.
This series was written in an environment without an NVIDIA GPU or CUDA
toolchain, so no kernel was executed. Therefore all claims below are source

## The question of this chapter

Why does decode use a different kernel variant from prefill? The code scope is
three files: `src/kernels.cu`, `src/main.cpp`, `python/decode_test.py`. The
minimum evidence for this chapter is 4 code citations, 1 test, and 0 executions.

This chapter depends on part 3, `prefill-path`, because decode only holds up in
contrast to prefill. This chapter owns the term decode step and the question
"what differs from prefill". KV storage layout and block table indexing belong to
part 6, cuBLAS transpose flags and column-major layout to part 4, slot/queue
lifetimes and termination conditions to part 7, weight loading and buffer
sizes/aliasing to part 2, and build boundaries and entry points to part 1. Here
we focus on which kernels decode calls differently and why, and how the new
token's K/V is appended to the cache.

`python/decode_test.py` is a test asset included in this chapter's code scope,
but this chapter's evidence contains no claim about its behavior. This chapter
does not run that file, and decode-family verification is also constructed only
from static citations.

## Where decode runs after prefill

prefill processes the `prompt_len` tokens of a queue's prompt all at once in the
`prefill` function (`src/main.cpp:150-553`). decode, by contrast, computes only
one token per active slot on each iteration inside `main`'s `while (true)` loop
(`src/main.cpp:720-1039`). This loop is the execution path this chapter follows.

The head of each iteration reconstructs the slot state. It clears `active_slots`
and `active_tokens` (`src/main.cpp:722-723`), then iterates over the slots and
fills empty slots with the next prompt from the queue
(`src/main.cpp:724-737`). This refill is the point where `prefill` is called
again (`src/main.cpp:726-734`), and slot/queue lifetimes are owned by part 7.
Then it uploads the active slot list, each slot's last token, and the sequence
length computed as `current_prompt_len[slot] + 1` to the device
(`src/main.cpp:749-757`). The `+1` means the KV of the token just generated is
already recorded in the cache, so it is included in the length.

This chapter's focus is the fact that this loop calls **different kernels** than
prefill. The kernels defined exclusively for decode are separate in
`src/kernels.cu`.

## Decode-family kernels and the contrast with prefill

The decode section of `src/kernels.cu` (`src/kernels.cu:346-523`) contains four
functions separate from the prefill section (`src/kernels.cu:26-344`).

- `embeddingGatherKernelDecode` (`src/kernels.cu:347-356`) and the wrapper
  `embeddingGatherDecode` (`src/kernels.cu:358-369`)
- `ropeKernelDecode` (`src/kernels.cu:371-384`) and the wrapper
  `ropeDecode` (`src/kernels.cu:388-405`)
- `softmaxKernelDecode` (`src/kernels.cu:408-439`) and the wrapper
  `softmaxDecode` (`src/kernels.cu:442-458`)
- `pagedAttentionKernel` (`src/kernels.cu:461-523`) and the wrapper
  `pagedAttention` (`src/kernels.cu:525-527`)

Of these, the first three are variants that replace the prefill counterparts, and
`pagedAttentionKernel` is a decode-only attention with no prefill counterpart.
All four functions are declared in `src/kernels.cuh:23-28`.

The following table summarizes where the two families diverge.

answered by this table.

- Decode-family kernels assume a sequence length of 1 (one token per slot) and
  simplify indexing. `embeddingGatherKernelDecode` takes `blockIdx.x` as the
  slot (`src/kernels.cu:349`), and `softmaxKernelDecode` assumes the
  `MAX_SEQ_LEN` stride layout (`src/kernels.cu:413`).
- `ropeKernelDecode` rotates only the current position, not all positions
  (`src/kernels.cu:371-384`).

Below we look at each variant in order.

## Embedding: `blockIdx.x` is the slot, not the token

prefill's `embeddingGatherKernel` has one block handle one token. It picks the
input token ID by the block index and determines the output row with
`workIndex = blockIdx.x * 2048 + threadIdx.x` (`src/kernels.cu:32-40`). The
launch is `embeddingGatherKernel<<<num_input_tokens, 1024>>>`, so `blockIdx.x`
is exactly the token position (`src/kernels.cu:45`).

decode's `embeddingGatherKernelDecode` has the same shape but a different
meaning. Its input is not an array of token IDs but the per-slot last-token
array `gpu_last_tokens`, and `blockIdx.x` points to the slot
(`src/kernels.cu:347-349`). The output is also stacked in slot order, so the
`blockIdx.x` in `workIndex = blockIdx.x * 2048 + threadIdx.x` is the active slot
index, not a token position (`src/kernels.cu:350`). The call site is
`embeddingGatherDecode(gpu_last_tokens, num_active_slots, hidden_state, ...)`
(`src/main.cpp:759`), where `num_active_slots` becomes the block count
(`src/kernels.cu:361`). In other words, decode keeps the "one block per token"
structure but swaps the token axis for the slot axis.

## RoPE: only the current position, recomputed on every call

decode's RoPE diverges from prefill at two points. First, it rotates only one
position at a time. `ropeKernelDecode` is launched with a single block
(`src/kernels.cu:397`), and each thread rotates the two elements at
`2 * threadIdx.x` and `2 * threadIdx.x + 1` (`src/kernels.cu:379-382`). The
rotation angle is computed only for the single `position_in_sequence` passed as
an argument (`src/kernels.cu:378`). The call site calls
`ropeDecode(&q_proj[slot * EMBEDDING_LENGTH], current_prompt_len[active_slot], ...)`
and
`ropeDecode(k_proj_batched_buffer + slot * KV_DIM, current_prompt_len[active_slot], ...)`
for each active slot (`src/main.cpp:847-848`). The position argument is the index
of the token this slot will generate this time, that is, `current_prompt_len`.

Second, decode recomputes the angle every time. `ropeKernelDecode` contains the
following computation.

```cpp
int double_i = 2 * (threadIdx.x % 32);
float theta = 1.0 / (pow(500000.0, ((float)double_i / HEAD_DIM)));
float angle = position_in_sequence * theta;
```

Citation: [`src/kernels.cu:376-378`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/kernels.cu#L376-L378)

Here `500000.0` and `32` are hardcoded literals (`src/kernels.cu:376-377`). The
comment directly above states that precomputing and reusing this value remains a
TODO (`src/kernels.cu:375`). prefill's `ropeKernel_llama3`, by contrast, receives
`d_cos_table`/`d_sin_table` as arguments and only reads
`cos_table[token_idx * head_dim + pair_idx * 2]` (`src/kernels.cu:173-200`). This
table is built once at the start of `main` by
`init_rope_frequencies(HEAD_DIM, MAX_SEQ_LEN, 500000.0f, 32.0f, 1.0f, 4.0f, 8192)`
and uploaded to the GPU (`src/main.cpp:572`, `src/kernels.cu:96-152`, allocation
and H2D at `src/kernels.cu:146-151`). The difference is that prefill references
the table while decode recomputes the same constants inside the code.

## Gathering K/V into batch buffers and scattering them into blocks

decode's K/V projection groups the slots into rows and handles them with a single
cuBLAS call. The K projection is called with `n = num_active_slots` and writes
its output to `k_proj_batched_buffer` (`src/main.cpp:802-821`), and the V
projection likewise writes to `v_proj_batched_buffer` (`src/main.cpp:824-842`).
The two buffers are allocated for decode only, with size `BATCH_SIZE × KV_DIM`
(`src/main.cpp:684-693`). After RoPE is applied per slot (`src/main.cpp:844-849`),
the new token's K/V is copied into the corresponding block of the paged KV cache
(`src/main.cpp:851-873`).

The point where this copy differs from prefill is that it handles only one token
at a time. For each slot it takes the new token's position in the sequence as
`current_prompt_len` and splits it into a logical block and an offset within the
block (`src/main.cpp:855-857`). If the block does not exist yet, it takes one
from the back of `free_blocks` and writes it into `block_table`; otherwise it
reuses the existing block (`src/main.cpp:858-865`).

```cpp
int logical_block_idx = seq_len / BLOCK_SIZE;
int token_in_block_idx = seq_len % BLOCK_SIZE;
int block = block_table[active_slot * N_LAYERS * MAX_BLOCKS_PER_SEQ + layer * MAX_BLOCKS_PER_SEQ + logical_block_idx];
if (token_in_block_idx == 0)
{
    int physical_block_idx = free_blocks.back();
    free_blocks.pop_back();
    block = physical_block_idx;
    block_table[active_slot * N_LAYERS * MAX_BLOCKS_PER_SEQ + layer * MAX_BLOCKS_PER_SEQ + logical_block_idx] = block;
}
```

Citation: [`src/main.cpp:856-865`](https://github.com/jmaczan/tiny-vllm/blob/e25bf1994efa90bc98b721ba7c527402f86fbeaf/src/main.cpp#L856-L865)

Allocation happens only when the offset within the block is 0, that is, only for
the first token of a new block (`src/main.cpp:859-865`). K is recorded with
`cudaMemcpy` D2D at the block start plus
`token_in_block_idx * KV_DIM * sizeof(__nv_bfloat16)`, and V at that point plus
`V_OFFSET` (`src/main.cpp:866-872`). `V_OFFSET` is
`BLOCK_SIZE * KV_DIM * sizeof(__nv_bfloat16)` (`src/main.cpp:33`), and one block
occupies `BLOCK_BYTES` for K and V together (`src/main.cpp:34`). The meaning of
this block layout and the `block_table` logical index arithmetic is owned by
part 6.

prefill does the same work in `BLOCK_SIZE`-token chunks. For each token range it
allocates a block and copies the whole chunk at once (`src/main.cpp:251-288`).
decode is as if that chunk were reduced to a single token. After recording, it
synchronizes the entire `block_table` H2D to `block_table_gpu`
(`src/main.cpp:876`). This full copy carries a TODO comment to "make it smarter
so we don't copy the whole thing unnecessarily" (`src/main.cpp:551`).

## Attention is handled by `pagedAttentionKernel`

prefill builds the score matrix, masks the future with `causalMask`
(`src/main.cpp:329`), and calls `softmax` (`src/main.cpp:331`). decode has
neither of these two calls. decode's attention is over with a single
`pagedAttention` (`src/main.cpp:878`). This kernel receives `kv_cache`,
`block_table_gpu`, `gpu_seq_lens`, and `gpu_active_slots` together
(`src/kernels.cu:461`), iterates over the blocks to compute scores
(`src/kernels.cu:478-485`), accumulates the weighted average with warp reduction
and online softmax (`src/kernels.cu:486-519`), and writes the output
(`src/kernels.cu:522`). Masking future positions is replaced by iterating only
up to the sequence length, without a separate mask. The internals and
inputs/outputs of this kernel are owned by part 6.

One fact is worth pointing out here. `softmaxDecode`/`softmaxKernelDecode`,
declared as part of the decode family (`src/kernels.cuh:25`,
`src/kernels.cu:408-458`), are never called anywhere in the decode path of
`src/main.cpp`. decode's probability normalization is handled by the online
softmax inside `pagedAttentionKernel`. This kernel's `MAX_SEQ_LEN` stride
assumption (`src/kernels.cu:413`) presupposes a different layout from prefill
softmax's `num_tokens` stride (`src/kernels.cu:262`), but it is not used in the
current call graph.

## The remaining layers and the logits

After attention, the computation uses the same kernels as prefill. The output is
written to the same buffer as the input q projection, `buf_2048_1`
(`src/main.cpp:878`), and that buffer immediately becomes the input to the O
projection (`src/main.cpp:892`). After the O projection come `residualAdd`
(`src/main.cpp:902`), post-attention RMSNorm (`src/main.cpp:904`), SwiGLU's
gate·up·`silu`·down (`src/main.cpp:907-969`), and `residualAdd` again
(`src/main.cpp:971`), completing one layer. The only difference from prefill is
that these calls receive `num_active_slots` instead of `prompt_len` as the token
count.

After passing through 16 layers come the final RMSNorm (`src/main.cpp:974`) and
the `embed_tokens` logits (`src/main.cpp:976-994`), then after the D2H copy
(`src/main.cpp:996`) the CPU finds the argmax per active slot and prints it
(`src/main.cpp:1000-1014`). If the generated token is `<|end_of_text|>` (128001)
or `<|eot_id|>` (128009), or if `current_prompt_len == MAX_SEQ_LEN - 1`, it
empties the slot and returns the blocks (`src/main.cpp:1015-1031`); otherwise it
accumulates the token and increments the length by 1 (`src/main.cpp:1032-1037`).
This termination/slot handling is owned by part 7.

## Limitations of this chapter

- This series was written in an environment without an NVIDIA GPU or CUDA
  toolchain, so not a single kernel was executed. All claims about decode kernel
  indexing, reduction, and copies are source citations with no execution
  verification.
- The minimum evidence for this chapter is 4 code citations, 1 test, and 0
  executions. Kernel execution time, throughput, and memory usage are not
  measured, and this chapter contains no performance figures that could be read
  as measured values.
- `softmaxDecode`/`softmaxKernelDecode` are declared and defined but not called
  in the decode path of `src/main.cpp`. This chapter states this fact based on
  the source call graph and did not verify it by execution.
- `softmaxKernelDecode`'s `MAX_SEQ_LEN` stride assumption (`src/kernels.cu:413`)
  differs from prefill softmax's `num_tokens` stride (`src/kernels.cu:262`). The
  consistency of the two layout assumptions was not verified by execution.
- `ropeKernelDecode`'s angle recomputation remains a TODO (`src/kernels.cu:375`).
  The numerical agreement of the two RoPE paths, decode and prefill, was not
  verified by execution.
- decode copies the entire `block_table` H2D on every layer
  (`src/main.cpp:876`, TODO `src/main.cpp:551`). This cost is not measured.
- decode's K/V copy and block allocation (`src/main.cpp:851-873`) depend on the
  number of active slots and the per-slot length. There is no execution
  verification of concurrency or contention.
- The order this chapter explains rests on the compile-time constants
  `BATCH_SIZE = 2` (`src/main.cpp:29`), `MAX_SEQ_LEN = 2048`
  (`src/main.cpp:28`), and `BLOCK_SIZE = 16` (`src/main.cpp:32`). If these values
  change, the indexing and buffer sizes change with them.
- The weight file is `model.safetensors` of the gated model
  `meta-llama/Llama-3.2-1B-Instruct`, so actually running decode remains a
  follow-up task.
