# tiny-vllm Chapter 5 · Attention and the KV cache

Chapter 4 read attention as only "one step in the order" while walking through
a single pass of the layer loop. What it briefly verified then was the head
structure and the score scale constant alone. This chapter revisits that step,
centered on the memory the attention step actually reads and writes: the KV
cache. How prefill scatters the prompt's K/V into the cache
(`src/main.cpp:251-288`), how decode overwrites it one token at a time
(`:851-873`), and which head layout attention uses to consume that K/V
(`:301-371`) are this chapter's share.

The chapter's implementation claims converge on three points. The cache's
physical structure is Claim 5, the prefill/decode scatter paths are Claim 6,
and the head reuse rule is Claim 7. Following the series' evidence rules, every
claim cites source paths and line ranges from the pinned commit (`guide.md:11-16`).

## The KV cache: a fixed 2 GiB block pool

The KV cache is allocated once at startup as a full 2 GiB. The constants that
fix its size and block unit live at `src/main.cpp:32-37` (`evidence/claims.md:54`).

```
BLOCK_SIZE        = 16              // number of tokens one page (block) holds
KV_DIM            = 512             // dimension of one K/V head group
V_OFFSET          = BLOCK_SIZE * KV_DIM * sizeof(bf16)   // = 16384
BLOCK_BYTES       = V_OFFSET * 2                         // = 32768, the K and V planes
KV_CACHE_SIZE_BYTES = 2 * 1024^3                         // = 2 GiB
MAX_BLOCKS_PER_SEQ  = MAX_SEQ_LEN / BLOCK_SIZE           // = 2048 / 16 = 128
NUM_BLOCKS          = KV_CACHE_SIZE_BYTES / BLOCK_BYTES  // = 65536
```

Putting the block's geometry in order: one block places a K plane holding
`BLOCK_SIZE=16` tokens × `KV_DIM=512` dimensions × bf16 (2 bytes) at offset
`+0`, and a V plane at `+V_OFFSET`. Since `V_OFFSET` is exactly the K plane's
byte size (`src/main.cpp:33`), the whole block spans the two planes combined
for `BLOCK_BYTES = V_OFFSET * 2 = 32768` bytes (`:34`). These 32768 bytes fit
into 2 GiB exactly 65536 times (`:37`), so a total of `NUM_BLOCKS=65536` blocks
fit in the cache. The layout of keeping K and V in one block carries straight
through the rest of this chapter as the two offsets K (`+0`) and V (`+V_OFFSET`).

The allocation and ownership structure is built at `src/main.cpp:574-581`.

- `kv_cache` is allocated with `cudaMalloc` as the entire 2 GiB in one piece
  (`:576`).
- `free_blocks` is filled with `0..NUM_BLOCKS-1` (65536 entries) via `std::iota`
  and serves as a stack of physical block indices (`:577-578`).
- `block_table` is a CPU vector of size `MAX_SEQUENCES * N_LAYERS *
  MAX_BLOCKS_PER_SEQ`, all initialized to `-1` (`:579`).
- `block_table_gpu` is allocated at the same size (`:580-581`).

This structure is Claim 5: the cache reserves the entire 2 GiB regardless of
usage, with `free_blocks` owning the physical blocks and the CPU `block_table`
carrying the per-sequence, per-layer logical→physical block mapping
(`evidence/claims.md:51`). Note that because this cache uses a "page
reservation" scheme, the 2 GiB is allocated regardless of the amount actually
used (`evidence/claims.md:57`).

```
kv_cache (2 GiB, physical block pool)
┌─────────┬─────────┬─────────┬─────────┬───┐
│ block 0 │ block 1 │ block 2 │ block 3 │ … │
└─────────┴─────────┴─────────┴─────────┴───┘
  inside block 0: K plane (+0) · V plane (+V_OFFSET)   (16,384 B each)

free_blocks (physical block index stack)    block_table (CPU, all -1)
┌─────────────────────────┐               ┌──────────────────────────────┐
│ … 65534 65535 │ ← pop    │               │ slot×N_LAYERS×128 + layer×128 │
└─────────────────────────┘               │  + logical_block_idx          │
  pop: main.cpp:268-269, :861-862          │  = physical block (or -1)    │
  push: main.cpp:1025                      └──────────────────────────────┘
```

## Logical block → physical block: what block_table does

`block_table`'s index is computed as `slot * N_LAYERS * MAX_BLOCKS_PER_SEQ +
layer * MAX_BLOCKS_PER_SEQ + block_idx` (`src/main.cpp:265`, `:271`, `:858`,
`:864`). In other words, which physical block each logical block corresponds
to, per sequence (slot) and per layer, is captured in this single table. The
initial value `-1` means "not yet allocated". The KV scatter reads the physical
block number from this table (`:265`, `:858`); when it is `-1`, it pops a new
physical block from `free_blocks`, assigns it, and records the number
(`:268-271`, `:861-864`). Once the physical block number is fixed, the cache
address comes from a simple multiplication: `kv_cache + block * BLOCK_BYTES`
(`:280`, `:285`, `:866`, `:870`).

When a slot is freed, the physical blocks it had been using return to
`free_blocks` (`src/main.cpp:1025`, `evidence/trace.md:181`). This return path
is covered together with slot lifetime in Chapters 7 and 8; this chapter only
leaves the point that "the free_blocks stack is the sole owner of physical
blocks".

## The prefill KV scatter: filling block by block

prefill scatters the prompt's K/V into the cache block by block, per layer. The
loop runs from `token_idx = 0` up to `prompt_len` in `BLOCK_SIZE` steps
(`src/main.cpp:251-288`, `evidence/claims.md:64`).

The order inside the loop is three steps.

1. **Determine the number of tokens to copy** — the remaining token count is
   clamped to `BLOCK_SIZE` (`:253-257`), because the last block may be shorter
   than 16.
2. **Secure a physical block** — the logical block number is set with
   `block_idx = token_idx / BLOCK_SIZE` (`:264`), and the physical block is
   read from `block_table`. If it is `-1`, a value is popped from `free_blocks`
   and recorded (`:266-272`); if it is already allocated, `assert(false)` is
   thrown (`:273-277`). The source comment takes it that the block must always
   be empty during prefill ("block must be -1 during prefill", `:275`).
3. **D2D copy** — K is copied to `kv_cache + block*BLOCK_BYTES` (that is,
   `+0`) and V to `+V_OFFSET`, each `num_tokens_to_copy * KV_DIM *
   sizeof(bf16)` bytes, via `cudaMemcpy(...DeviceToDevice)` (`:280-287`).

The prefill half that Claim 6 organizes is exactly this path: prefill pops
physical blocks in `BLOCK_SIZE` units and D2D-copies K (`+0`)/V (`+V_OFFSET`)
(`evidence/claims.md:61`). The point that the copy unit is "one block plane"
rather than a token is the key difference from the decode that follows.

## The decode KV scatter: filling token by token

decode overwrites only **one token**'s K/V into the cache per active slot, per
layer (`src/main.cpp:851-873`, `evidence/claims.md:65`). The order inside the
per-slot loop is as follows.

1. **Position computation** — from `seq_len = current_prompt_len[active_slot]`
   (`:855`), the logical block and the token position within the block are
   pinned down.
   ```
   logical_block_idx = seq_len / BLOCK_SIZE     (:856)
   token_in_block_idx = seq_len % BLOCK_SIZE    (:857)
   ```
2. **A new block only at a block boundary** — only when
   `token_in_block_idx == 0` is a block popped from `free_blocks` and recorded
   in `block_table` (`:859-865`). Otherwise the physical block already written
   in `block_table` is used as-is. In other words, one block's lifetime
   continues until it is filled with all 16 tokens it receives, and allocation
   happens once every 16 tokens.
3. **Overwrite at the token position** — K/V are D2D-copied to the address
   ```
   kv_cache + block*BLOCK_BYTES (+ V_OFFSET) + token_in_block_idx*KV_DIM*bf16
   ```
   respectively (`:866`, `:870`). Since it is one token, the copy amount is
   only `KV_DIM * sizeof(bf16)` (`:868`, `:872`).

The decode half of Claim 6 is exactly this path: only when
`seq_len % BLOCK_SIZE == 0` is a new block popped; otherwise the corresponding
token position of the existing block is overwritten (`evidence/claims.md:61`).
The copy amount and the allocation frequency both shrink in the direction
opposite to prefill — prefill writes "one block plane", decode writes "one
token".

Placing these two scatter paths side by side makes the difference in the
filling behavior clear.

```
prefill (one layer, entire prompt)        decode (one layer, 1 active slot)
token_idx: 0..prompt_len, in 16s          seq_len = current_prompt_len[slot]
┌─────────────────────────────┐           ┌───────────────────────────────┐
│ block 0  K/V 16 tokens D2D  │           │ logical_block = seq_len/16    │
│ block 1  K/V 16 tokens D2D  │           │ token_in_block = seq_len%16   │
│ …                            │           │ pop/record only at token 0   │
└─────────────────────────────┘           │ K/V 1 token (512×bf16) D2D    │
  address: block*BLOCK_BYTES(+V_OFFSET)   └───────────────────────────────┘
  (:251-288)                               address: …+token_in_block*KV_DIM
                                            (:851-873)
```

Once the scatter is done, `block_table` is re-copied to `block_table_gpu`
(`:876`) and then `pagedAttention` is called (`:878`). How the decode attention
reads this cache is covered in Chapter 10; this chapter only points out the
link that the cache built by the scatter is exactly attention's input. The
indexing mix — the scatter path runs off the CPU's actual slot index
(`active_slot`), whereas the paged attention kernel maps active positions to
actual slots via the `gpu_active_slots` mapping — is noted by the trace memo
(`evidence/trace.md:235-239`).

## Attention: reusing heads with GQA

The reason K/V is piled into the cache is that attention consumes those values.
What this chapter verifies about attention is the head reuse rule, namely
Claim 7 (`evidence/claims.md:71`).

The head constants live at `src/main.cpp:20-24`. Q has `NUM_Q_HEADS=32`; K/V
each have `NUM_K_HEADS=NUM_V_HEADS=8`, and the ratio constants are defined as
`GQA_Q_TO_K_RATIO=4` and `GQA_ATTN_SCORES_TO_V_RATIO=4`. In other words, 4
consecutive Q heads share 1 K head and 1 V head.

The prefill attention step proceeds in the order score GEMM
(`src/main.cpp:301-327`) → `causalMask` (`:329`; `src/kernels.cu:239-255`,
kernel `:224-237`) → `softmax` (`:331`; `src/kernels.cu:293-309`, kernel
`:257-290`) → scores×V GEMM (`:343-371`) (see the layer pipeline in Chapter 4).
The score GEMM determines, per Q head, the K head to share with `k_head_idx =
i / GQA_Q_TO_K_RATIO` (`:303`). The source comment leaves the score
computation's form as `attn_score_head = Q_head * K_head^T / sqrt(64)` (`:298`).
The scale constant `attn_alpha = 1.0f / 8.0f` corresponds to this `sqrt(64)=8`
(`:649`). What is notable in this loop is that it reads `k_proj_temp_buf +
k_head_idx * HEAD_DIM` as the K operand (`:305`) — the prefill score GEMM uses
the K/V in the temporary buffers as-is, not the cache just scattered. The cache
scatter is what stores the values in advance for later stages — especially for
decode to read from the cache.

The scores×V GEMM applies the same mapping to V. It picks the V head with
`v_head_idx = i / GQA_ATTN_SCORES_TO_V_RATIO` (`:346`) and reads V from
`v_proj_temp_buf + v_head_idx * HEAD_DIM` as well (`:349`). The output is
`(num_tok, 64)` per head, so combining the 32 heads gives `(num_tok, 2048)`
(`:342` comment).

The decode-side attention is the reader, so the mapping lives inside the
kernel. `pagedAttentionKernel` uses the same ratio with `kv_head_idx =
q_head_id / GQA_Q_TO_K_RATIO` (`src/kernels.cu:468`). This kernel walks the
physical blocks along the block table and reads K·V (`:480-485`); the kernel as
a whole is Chapter 10's share. Here only the point that prefill and decode
**share the same ratio constant (4)** is confirmed as Claim 7
(`evidence/claims.md:71`).

```
Q heads 32 ────────────── K/V heads 8
 0 ─┐                      0
 1 ─┤  / GQA_Q_TO_K_RATIO    │
 2 ─┤  (=4)                  │
 3 ─┘                       ┘
 4 ─┐                       1
 … ─┤                        …
28 ─┐                       7
29 ─┤
30 ─┤
31 ─┘
  k_head_idx = i/4  (:303)   v_head_idx = i/4  (:346)
  paged attention: kv_head_idx = q_head_id/4  (kernels.cu:468)
```

## Limitations

- The cache constants are defined twice, at `src/main.cpp:32-37` and
  `src/kernels.cu:16-19`, and the source acknowledges the duplication with a
  TODO (`src/kernels.cu:6`; `evidence/claims.md:57`). The 2 GiB is a
  reservation allocation independent of usage.
- The scatter is entirely D2D `cudaMemcpy`, not a kernel
  (`evidence/claims.md:67`). The prefill `assert(false)` branch
  (`src/main.cpp:273-277`) is assumed not to be reached on the normal path.
- The GQA ratio (4) is hard-coded as a constant, so a change to the model
  structure requires recompilation (`src/main.cpp:20-24`,
  `evidence/claims.md:78`).
- The decode scatter reads the block table with the CPU's actual slot index,
  while the paged attention kernel reads it with an active-position mapping —
  the two indexing schemes are mixed, so care is needed when tracing
  (`evidence/trace.md:235-239`).
- That `attn_alpha = 1/8` is the inverse square root of `HEAD_DIM=64` is an
  observation that the source comment (`src/main.cpp:298`) and constant
  (`:649`) agree on, not a numerical verification result.
- This chapter makes no performance claims. The scatter's "block-unit /
  token-unit" only describes a structural difference in work and copy count;
  execution time and throughput have no basis and are not used.

## Summary

This chapter read the KV cache that attention consumes along three threads.
First, the cache's physical structure. A `BLOCK_SIZE=16` × `KV_DIM=512` × bf16
block is split into a K plane (`+0`) and a V plane (`+V_OFFSET`) forming
`BLOCK_BYTES=32768` bytes, and the entire 2 GiB is reserved as
`NUM_BLOCKS=65536` physical blocks (`src/main.cpp:32-37`, `:574-581`; Claim 5).
Second, the scatter paths. prefill pops and D2D-copies block by block
(`:251-288`); decode pops a new block only when `seq_len % BLOCK_SIZE` is 0 and
overwrites the token position (`:851-873`; Claim 6). Third, the head reuse
rule. Q's 32 heads share K/V's 8 heads at ratio 4, and the prefill score GEMM
(`:303`), scores×V (`:346`), and paged attention kernel (`src/kernels.cu:468`)
all use the same mapping (Claim 7).

The key point is that paged attention's data structure is prepared in this
chapter and its kernel in Chapter 10. `block_table`, which maps logical blocks
to physical blocks, and `free_blocks`, which owns the physical blocks, are the
two axes of that data structure, and the next chapter continues with a
comparison of the prefill and decode bottlenecks that looks at this structure
again from a runtime perspective.
