# 논문을 읽히는 기술 블로그로 쓰기

첨부한 논문을 바탕으로 한국어 기술 블로그 본문을 작성한다. 독자는 어텐션과 GPU의 기본 개념을 알지만 이 논문의 약어와 구현은 모르는 개발자다. 논문의 모든 항목을 옮기는 것보다 핵심 설계가 왜 필요한지 이해시키는 것을 우선한다.

## 글의 흐름

목차는 논문에 맞게 정한다. 아래 항목을 각각 고정된 절로 만들거나 같은 내용을 여러 번 요약하지 않는다.

1. 도입: 독자가 겪는 구체적인 문제를 두세 문장으로 설명한다. 핵심 방법과 가장 의미 있는 결과를 잇는다. 첫 문단에는 약어·수식·실험 수치를 몰아넣지 않는다.
2. 배경과 작은 예시: 새 용어를 쓰기 전에 필요한 이유부터 설명한다. 작은 입력이 어떻게 바뀌는지 보여주고, '설명용 예시'라고 표시해 측정 결과와 구분한다.
3. 방법: 문제 → 설계 선택 → 효과 순서로 연결한다. 핵심 메커니즘은 충분히 설명하되 부록의 증명과 모든 구현 상수를 본문에 나열하지 않는다.
4. 결과: 독자의 판단에 필요한 대표 실험을 고른다. 표 앞에서 비교 질문을 제시하고 표 뒤에서 해석한다. 커널 성능과 전체 시스템 성능을 구분한다.
5. 한계와 적용 판단: 중요한 제약 3~5개를 중심으로 어떤 환경에서 쓸 만한지 설명한다. 저자의 한계와 리뷰어의 추론을 구분한다.

## 문장과 밀도

- 문단은 하나의 질문에 답하며 대체로 2~4문장으로 쓴다. 긴 문장에 여러 메커니즘을 이어 붙이지 않는다.
- 전문용어는 처음 등장할 때 쉬운 뜻을 설명한다. '마스크 물질화', '일급 병목', '대칭 기판', '지렛대' 같은 번역투 대신 실제로 무엇을 저장하고 계산하고 전송하는지 쓴다.
- 도입 요약은 짧은 한 문단이면 충분하다. 별도 TL;DR, 핵심 아이디어, 결론 표에 같은 설명을 반복하지 않는다.
- 숫자는 주장을 판단하는 데 필요한 것만 고른다. 관련 없는 모델 크기·비용·학습 데이터 항목을 채우거나 '원문 미보고' 목록을 만들지 않는다.
- 강조는 문단에서 가장 중요한 한 곳 정도만 사용한다. 수식은 말과 작은 예시로 설명한 뒤 꼭 필요할 때 넣는다. 증명·세부 구현·보조 비교는 생략하거나 접힌 참고 절로 옮긴다.
- 본문은 대체로 4~7개의 주요 절로 구성한다. 분량 목표보다 인과관계 설명을 우선하며, 설명을 줄여 약어만 남기는 요약문을 만들지 않는다.

## 사실과 근거

- 원문에서 확인한 내용만 사실로 쓴다. 수치·baseline·하드웨어·context·측정 지표를 함께 제시하고 서로 다른 실험 조건을 섞지 않는다.
- 중요한 정량 주장과 논쟁적인 해석에 실제 §/Table/Figure/Appendix 위치를 단다. 같은 실험을 설명하는 문단이나 표에는 근거를 묶어 한 번 적어도 된다. 모든 문장 끝에 '(근거: ...)'를 반복하지 않는다.
- 원문에 없는 결과나 근거 번호를 만들지 않는다. 필요한 수치가 없으면 해당 주장 가까이에 불확실함을 밝힌다. 직접 인용은 최소화한다.
- 독립적으로 검증되지 않은 비교, 최고값의 조건, 적용 범위를 제한하는 가정은 남긴다. 과장된 소제목을 쓰지 않는다.

## 눈에 보이는 예시를 먼저 설계한다

- 독자가 무엇이 들어와서 어떻게 달라지는지 말할 수 있는 작은 예시를 먼저 정한다. 추상적인 구성요소 이름만 나열한 흐름도로 대신하지 않는다.
- 예시에 입력, 남는 상태, 바뀌거나 버려지는 항목, 출력을 명시한다. 캐시·메모리·통신을 줄인다는 주장은 어느 모델·장치·단계의 것인지 분리한다.
- 토큰·행렬·작업 배정·데이터 이동 중 논문에 맞는 모양을 고른다. 문장 예시는 실제 토큰 분할과 다를 수 있음을 밝히고, 거절·생략·실패 시 남는 결과도 보여준다.
- 색·위치·숫자 변화의 뜻을 본문에 설명한다. 수용률·수용 길이·지연·처리량을 섞지 않고, 배수마다 비교 대상을 적는다.
- 원문 그림은 구현 연결과 실험 근거로 사용하고, 작은 설명용 예시는 이해를 위한 별도 자료로 구분한다. 생성하지 않은 SVG·이미지 경로는 만들지 않는다. 파일 생성이 허용되지 않으면 같은 상태 변화를 표나 Mermaid에 직접 담는다.

## 시각 자료와 형식

- 동작이 보이지 않는 추상어 나열을 피한다. '마스크 물질화·마스크 인지 스케줄링·마스크 유발 부하 불균형이 일급 병목' 대신 '가릴 칸의 표를 만들고 계산할 블록을 고르는 데 시간이 들며, GPU마다 작업량이 달라 기다림이 생긴다'처럼 쓴다.
- 시각 자료는 용어 상자를 화살표로 연결하는 데서 끝내지 않는다. 작은 실제 모양의 입력, 생략되는 칸, 변환 전후 좌표나 작업 배정의 차이를 보여준다. 측정값이 아닌 예시는 명시하고, 서로 독립된 예시를 한 실행의 연속 단계처럼 보이게 하지 않는다.
- 도식 바로 뒤에서 독자가 어느 칸·색·값의 변화를 볼지 설명한다. 모바일에서도 라벨을 읽을 수 있게 하고, 전체 파이프라인에 넣지 않은 단계는 범위를 밝힌다.

- 원문 그림이 제공되면 설명에 필요한 그림을 본문 맥락에 배치하고 Fig. 번호나 페이지를 적는다. 경로를 만들거나 읽히지 않는 그래프 수치를 추정하지 않는다.
- 그림이 없으면 작은 Mermaid나 비교 표로 핵심을 설명한다. 보통 1~3개면 충분하며 같은 내용을 반복하는 도식은 생략한다.
- 원문 표 전체는 파이프라인이 별도로 붙인다. 본문에는 필요한 비교만 다시 구성하고, 모든 표를 복사하지 않는다.
- Markdown 본문만 출력한다. 제목은 front matter가 담당하므로 같은 제목을 본문에 반복하지 않는다. 질문 목록·빈칸·작업 보고는 출력하지 않는다.

## 수식 쓰기 규칙 (반드시 지킬 것)

- 인라인 수식은 `$...$`, 블록 수식은 빈 줄로 분리한 `$$`를 사용한다. 수식 안에 Markdown 강조나 `\_` 이스케이프를 넣지 않는다. 산문의 달러 비용은 백틱으로 감싼다.

마지막으로 도입만 읽어도 무엇이 문제이고 무엇이 달라지는지 이해되는지, 각 절이 새로운 설명을 더하는지, 수치와 한계가 원문과 일치하는지 확인한다.
